# Batch 7 — the plan (2026-09-11)

Written after the homework (docs/BATCH_7_HOMEWORK_2026_09_11.md) and the user's question
about the test harness: *the shell that finds and runs Pure test functions is a product
feature, not test code.* That changes the order of batch 7. It is now three steps, each
landing through one full gate chain, each with a check that says when it is done.

## What we are fixing, in one paragraph

Today the code that discovers `<<test.Test>>` functions in a model and runs them lives in
a test-only file (`MinimalCorpus.java`, 926 lines), tangled with the code that assembles
the engine's test corpus from the checkout. A user of the platform cannot run their own
Pure tests, because the runner is not part of the product. And the plan for batch 7 was
to move that whole file into a new module for things that read the engine's checkout,
which would have buried the runner further. So: first pull the runner out into the
product, then move what is left, which really is checkout-reading code, into the new
module, and only then enforce the rule that core never depends on upstream.

## Step 7a — the test runner becomes part of the product

**Where.** A new package in core's main tree, `com.legend.test`. It reads the compiled
model only. It never reads a file from the engine's checkout and never knows the
checkout exists.

**What it contains.**

1. **Discovery.** Given a model, list every function marked `<<test.Test>>`. For each
   one, record its package, its markers (`ToFix`, `ExcludeAlloy`), and the package's
   setup functions (`<<test.BeforePackage>>` with no parameters). Order the list the way
   the engine's own suite does: by package tree, then by name. Discovery reports
   everything and excludes nothing; whoever calls it decides what to skip. The rules come
   from the engine's test framework and the `test` profile, which the prelude already
   carries like every other platform declaration.
2. **Running.** Given a test case and a database connection factory, run it and return
   one result: pass, fail, or skipped, the number of verdicts reached, and a reason. The
   rules inside, all of which exist today in the harness and none of which mention the
   engine:
   - one database session per package, its setup functions run once, in order;
   - a setup that fails fails every test in its package, with the setup named;
   - a test whose body seeds its own inline data gets a private workspace instead of
     the shared session;
   - the body is resolved, typed, and executed through the compiler; each assert the
     platform adjudicates becomes a verdict through the listener that already exists in
     main; the first failed assert is the reason;
   - a body that reaches no verdict function is skipped, with that said;
   - a body that reaches a verdict the platform did not adjudicate is a failure, never
     a quiet pass.
3. **An observer.** One small interface the runner calls at the moments the harness
   instruments today: a verdict was reached, a verdict was declined to the text channel,
   a verdict was refereed, a SQL statement was executed. Every method has a no-op
   default. The harness attaches its strength census and its referee through this; a
   user attaches nothing.

**What the harness keeps.** `MinimalCorpus` becomes a caller: it assembles the sources
from the checkout (that code is already separate, in `Corpus.java`), builds the model,
asks the runner for the tests, applies its own exclusion policy (`ToFix`,
`ExcludeAlloy`, the engine-implementation file keys), runs each test with the referee
observer attached, and keeps the rosters, the census, and the strength ledger. Its
declared / excluded / discovered counts are read off the runner's report instead of
being decided inside it.

**The referee.** The replay oracle and the H2 verifier live in a main package called
`harness` today, and the executor takes the oracle as a parameter. In this step they
attach through the observer and nothing else changes. Whether they can leave main
entirely is measured in 7b.

**Done when.**
- Both corpus rosters are byte-identical to today's (nothing the harness reports may
  move: this is a relocation of logic, not a change of it).
- A new unit test in core builds a five-line model with two `<<test.Test>>` functions
  and one setup, runs it through the runner against DuckDB, and gets one pass and one
  fail with the expected reasons. No checkout anywhere. That test is the proof the
  runner is a product surface.
- `MinimalCorpus.java` is shorter by the lines that moved, and contains no session,
  setup, or verdict logic.

## Step 7b — the `spec` module

**What moves.** The 15 files the homework lists, in their two test-only packages,
package names unchanged: the corpus harness (six files, thinner after 7a) and the tools
package (nine files: every generator and every parity test that reads a checkout).

**What has to change for the move to be invisible.**
1. A new Maven module `spec`, depending on the installed core jar (as
   `parser-equivalence` does), on core's test jar for the claims registry, and on the
   two JDBC drivers the harness executes against. Core gets a test-jar goal.
2. The seven places the generators read or write files in core's tree by a path relative
   to the module get one shared root constant pointing at `../core`.
3. Two rows in the JDBC census that name the corpus files by path move to the new path;
   the dangling-state guard's module list gains `spec`.
4. Two gate lines: gates 4 and 5 run the corpus test from `spec` instead of `core`. Gate
   1 loses the moved files on its own. CI lanes are numbered by gate and do not change.
5. The referee: if, after 7a, nothing in core's main tree needs the replay oracle except
   the executor's parameter, the oracle becomes an interface in main with the
   implementation in `spec`. If the seam is deeper than that, it stays in main and the
   record says so with the measurement.

**Done when.**
- Every pinned number the moved tests hold lands byte-identical from the new module:
  the rosters, zero signature divergences, the 752 membership rows, the 37 unsupported
  dynafunctions, the 91 manifest paths, the 2,292 own-corpus matches, all of them.
- `mvn -pl core test` runs no test that reads a checkout.

## Step 7c — the boundary, enforced

**The groupId.** Our own artifacts are published under the groupId `org.finos.legend`,
which is the engine's. A rule that says "core may depend on nothing from
`org.finos.legend`" would ban core itself. So the groupId becomes `com.legend` in the six
poms that carry it, and the installed jars are re-installed once. This mirrors the
package rename batch 0 did for the same reason. (If you would rather not rename, the
fallback is a rule listing upstream artifact-name prefixes; it works today and a new
upstream prefix would slip past it silently. The rename is recommended.)

**The rules.**
1. Maven enforcer in `core` and in `spec`: no dependency from `org.finos.legend`, of any
   scope. The build fails, not a test.
2. ArchUnit in `core` and in `spec`: no import of `org.finos.legend`. Today the count is
   zero in both; the rule keeps it there.
3. `classpath-convergence.sh` keeps measuring what the rules enforce, so a rule that
   silently stops firing is still caught.

**Done when.** The enforcer rule is present and the build is green with it; a deliberate
test dependency on an engine jar added to core makes the build fail, then is removed.

## Order and cost

7a, then 7b, then 7c, one chain each. 7a is the design step and the only one that
changes code shape; 7b is a mechanical move whose success is that nothing moves; 7c is
configuration. Together: one new package with three public types, fifteen relocated
files, one new module, six pom edits, two gate lines, and two enforcement rules.

## After batch 7

The PCT lane has its own discovery of the same kind of test functions. Once the runner
is product surface it should become a second caller of it, so one runner discovers and
runs Pure tests everywhere. That is a later batch, noted here so it is not forgotten.

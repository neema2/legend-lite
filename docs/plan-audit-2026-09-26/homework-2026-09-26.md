## 1. The eight `size` rows: our TDS erasure changes overload choice (step 1 / step 3)

**The body.** `meta::relational::tests::mapping::inheritance::relational::testFilterProject`
(pinned engine, `core_relational/relational/tests/mapping/inheritance/testInheritanceRelational.pure:53-58`):

```
let result1 = execute(|Person.all()->filter(...)->project([p|$p.name], ['name']), ...).values;
assertEquals(1, $result1->size());
```

**The reference** (ref-resolutions, lines 55–56): `project` resolves to
`meta::pure::tds::project_K_MANY__Function_MANY__String_MANY__TabularDataSet_1_`, so `$result1`
is `TabularDataSet[1]`, a plain class instance; `size` resolves to
`meta::pure::functions::collection::size_Any_MANY__Integer_1_` and the assertion counts ONE object.
`Relation<T>[1]` does not match a `TabularDataSet` at all (TabularDataSet's linearization does not
contain Relation; `TypeMatch.newTypeMatch` gives NULL).

**Ours** (our-resolutions): the same call resolves to
`meta::pure::functions::relation::size_Relation_1__Integer_1_`. Cause, two places:
- `compiler/spec/TdsErasure.java:29-36` `refineResult`: a result type that mentions TDS is replaced
  by the relation carrier type of an argument, so the legacy `project` produces a relation-shaped
  `$result1`.
- `compiler/spec/InferenceKernel.java:1380-1381`: a `Relation<T>` formal scores 1 for any
  `Type.isRelation(actual)`; and :1362-1364 a `TabularDataSet` formal scores 1 for a relation-shaped
  actual. `PlatformTypes.RELATION_CARRIERS` (:186-188) includes the TDS relation class, so the
  erased value matches `relation::size(Relation[1])` with an exact multiplicity, beating
  `size(Any[*])`.

**Count.** Across the module ours chooses `relation::size` 32 times, the reference 14; the 8 in
the differential are the comparable subset.

**Why it matters.** The two overloads mean different things: `relation::size` counts ROWS,
`collection::size` counts VALUES (one TDS object). The tests pass today by coincidence (the
projected TDS has one row). Any assertion of the form `assertEquals(1, $tds->size())` over a TDS
with zero or several rows would diverge. This is the general lesson the design already states: TDS
erasure is a LOWERING fact (a TDS becomes a relation in SQL) and must not be a TYPING fact, because
typing decides overloads. The legacy `meta::pure::tds::*` functions take `TabularDataSet` explicitly
and need no erasure to be chosen.

**What step 3 does with it.** In the kernel's new matcher, `TabularDataSet` is a class:
`Relation<T>` formals do not match it (no C3 path), `TabularDataSet` formals match it exactly, and
`Any` matches at its distance. `TdsErasure.refineResult` stops rewriting the typed result; the
lowering reads "this value is a TDS" from the type as it already does for relations. Gate: the 8
rows go to zero without touching `size`'s rules, and the 32 → 14 count matches the reference.

## 5. Which tier of the bare-name rule serves Pure source? (step 3)

**Question.** The bare-name rule (`BareNames`, untangle 4b.2) has three tiers: the ENGINE surface
(legend-engine's `Handlers.java` names, each mapped to the FQNs the platform declares), the CORE
import group, and a FORM's owned declarations. The reference resolves Pure source through imports ∪
the core group ∪ Root only; the engine surface is the engine-input language's rule. Step 3 keeps
the engine tier for `LEGEND_LITE` trees and drops it from Pure source — so: which bare calls in Pure
source does the engine tier serve TODAY that nothing else would?

**Method.** The shadow probe writes `BARE-TIER name fqn tier site` rows (`DecisionProbe.bareTier`,
`Shadow.onBareTier`): from the resolver's prelude merge ONLY for an FQN the resolver's own tiers
(the file's wildcards, its package, the core group) had not already put on the node
(`resolver-added`), and from the overload merge point for a name that reached the typer bare
(`merge`). `tools/untangle/bare_tiers.py` classifies each bare name: CORE (every FQN with
declarations is spelled by the core group), FORM, or ENGINE-ONLY (some FQN with declarations is
spelled by the engine tier and by no other). Run with `LL_SHADOW=1` over `//spec:corpus_duckdb`,
`//spec:corpus_h2`, `//spec:spec_tests` (the manifest census) and `//core:core_tests`; receipts
`receipts/plan-audit-2026-09-26/step3/tiers/`.

**A first run measured the wrong thing** and is kept as a receipt (`bare-tiers-first-run-unrefined.tsv`):
without the "not already on the node" condition it reported 40 engine-only names, all calendar
functions and the like — every one an FQN the file's own wildcard import (`import
meta::pure::functions::date::calendar::*`) had already resolved, which the engine tier merely
re-spelled. The marginal probe is the honest one.

**Result, Pure source (both corpus lanes + the census): 48 bare names served beyond the resolver's
own tiers; CORE 40, FORM 4, ENGINE-ONLY 4** by the classifier's buckets. Read by SITE — which FQNs
did the prelude merge ADD — the `resolver-added` rows name SIX names, not four: the four below plus
`flatten` (`relation::variant::flatten`, spelled by the engine tier AND a form's owned declarations;
the classifier buckets ENGINE|FORM as FORM, which hides that the reference sees neither) and
`toString` (`relation::toString`, spelled by the merge's CORE tier but missed by the resolver's own
core-group tier: the resolver's universe holds `Pure.userResolvableFunctionFqns()`, narrower than
`Pure.nativeFunctionsAt` — a hole 3b's index must close by saying which set it takes). Corrected
2026-09-26 after the audit (#11, #12); the receipt rows are unchanged.

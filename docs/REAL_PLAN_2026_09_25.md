# The real plan: from a compiler that checks names to one that holds references

Written 2026-09-25, after the untangle's steps 0–4b landed and were audited. This replaces the
ordering in `UPSTREAM_BOUNDARY_PROGRAM.md` §3 D from step 4c on; that charter's rulings still hold.
The study behind it is `~/legend/platform-architecture/PLATFORM_ARCHITECTURE.md` §11–§14.

> The design this plan builds — the stages, their data, the binder's rules, the one registry — is
> `COMPILER_DESIGN_2026_09_25.md` (2026-09-25). Where that document adds a step (A4: element and
> member binding), it takes precedence over the step list below.

## The words used here

- **Declaration.** The upstream statement that a function exists: its full name, its parameters,
  its return. Every overload is its own declaration. Its identity is the whole signature string
  (`FunctionId`), never a piece of it.
- **The tree.** What the parser produces from text: nested nodes, each naming things by the
  spelling the user wrote (`filter`, `meta::pure::functions::collection::filter`).
- **Binding.** Turning every spelling in the tree into a reference to a declaration, once. A
  **bound tree** holds references; a spelling appears in it only where the user wrote one and no
  declaration exists for it (an error to report).
- **Typing.** Working out the type of every expression and, for a call, which overload it is.
- **A form.** A function the type checker treats specially (`project`, `extend`, `groupBy`), because
  its result type depends on its arguments in a way a plain signature cannot say.
- **Lowering.** Turning a typed program into SQL.
- **The implementation table.** The one list of what the platform implements for each declaration:
  by a SQL rule, by a form, by a refusal with a reason, or not at all.
- **The probe.** A test-lane recorder that writes what the compiler decided at each decision point,
  so a change can be measured before and after (`LL_SHADOW`).
- **The census.** Loading everything upstream declares and typing every body once, so the compiler's
  gaps are a list of numbers that only go down.
- **A pin.** A test that a number does not grow (identity compares, walls, failures). Pins are
  scaffolding: each one has a condition under which it is deleted.

## What in this plan is measured and what is judgement

Measured this session, in the repo or the pinned checkouts: every number in "Where we are"; the
four inliners and the fold table; the dozen ownership mechanisms; that the tree carries spellings
(`AppliedFunction.function` is a String, its candidates are Strings); that upstream's compiler
registers per-function return-type inference keyed by the signature id (`Handlers.java`, 62
registrations, e.g. `project` at 1498–1504); that legend-engine resolves engine input by the handler
surface first (study §14.1). Judgement, not measurement: the step ORDER (chosen so each step shrinks
the next), the SIZES, and the claim that one evaluator can replace the four inliners without loss
(Step C measures that first). Not located: legend-pure's own implicit-import list in the pinned
tree (its main sources name no such list; the engine's `CompileContext.META_IMPORTS` stands as the
core group, and the standard-library census says it suffices today). Any step's homework note
re-measures before the switch.

## Where we are

Two decision points were the goal: which overloads a call may mean, and how the platform runs the
one chosen. The second is owned by the implementation table today (the mint and the inliner read
its rows). The first is not: the function merge point still asks a hand list ("platform-owned") and
a stereotype ("is this a conformance twin?") before letting a body join. Names are resolved by one
rule (`BareNames`), the catalog refuses a bare lookup, and forty-odd string checks were converted
to referent checks — but the tree itself still carries spellings, so every one of those invariants
is enforced by a regex pin rather than by the data structure. Four different pieces of code inline
a function body. A hand-written evaluator folds constants inside the type checker. The type
inference kernel cannot bind generics in 164 upstream bodies, and a dozen registries each hold
part of "what the platform owns".

Numbers today (all measured, all pinned): identity compares 207 + 81 + 64 + 90 sites, mints by
name 143, catalog lookups by name 170, form dispatches by name 21, category checks 13; forms 40;
manifest closure 1,772 files with 32 walls and 1,447 failing bodies; boot census 26 walled, 0
unwalled; stdlib failures 5.

## The principle, in one sentence

After binding, the program never mentions a function by its spelling again; it holds the
declaration, and everything downstream asks the declaration.

## The end state

Six stages, each owning exactly one question, each a separate package with no cycle back:

1. **Load.** The module manifests (`<name>.definition.json`) decide which files exist. No hand lists
   of files. Strict: a file that does not parse is a wall with a reason; no tolerant mode.
2. **Parse.** Text to tree. The parser knows keywords, not functions.
3. **Bind.** Every reference becomes a declaration reference: functions to the declaration table's
   rows, classes and properties likewise. A bare function name is resolved by one rule (the file's
   imports, its package, the core import group; for engine input also the engine's handler surface).
   A name with no declaration is reported here, with its position. Output: a bound tree.
4. **Type.** Types and overloads over the bound tree. A form's special rule is registered against
   the declarations it owns, not a spelling. The kernel binds generics, multiplicity parameters and
   function types by unification, so a form exists only where the rule genuinely differs from a
   signature.
5. **Evaluate and normalise.** One evaluator over typed terms does everything that today is spread
   over four inliners and the fold table: inlining normalise-required functions, plan-time
   evaluation of static values (column lists), constraint and validate desugaring.
6. **Lower.** SQL rules registered by declaration in the implementation table — the one registry.
   Every "does the platform own this" question, from walls to lite surfaces to legacy vocabularies,
   is a row.

When this holds, the identity pins read zero and are deleted, because the tree cannot hold a
spelling to compare.

## The steps, in order

Each step: what changes, what is deleted in the same commit, how we know it is done, size.
The order is chosen so each step makes the next one smaller, not by how easy it is. Every step
runs the same way: a homework note first (what the code does today, measured), the probe or census
before, the switch, the gate, the deletion, the record, the push.

### Step A — Bind the tree (the former 4c and step 5, in that order)

> Homework note, written 2026-09-25 with the reference's rules quoted from its source and the
> differential's numbers: `A1_HOMEWORK_2026_09_25.md`. It puts task #47 (the kernel chooses like
> the reference) before A1, settles that the corpus resolves by imports alone (the implicit import
> group is measured: 29 packages, our core group minus three newer ones), and lists the deletions.

**A1. The overload set is a set of declarations.** The binder attaches to a call the declaration
ids it may mean (today it attaches spellings). The function merge point reads the declaration table
for those ids and nothing else. Deleted in the same commit: the platform-owned hand list, the
conformance-twin stereotype check, the two "suppressed once" console warnings. Gate: the probe's
overload-set rows show zero disagreements against the table; the corpus and conformance rosters
unchanged; the category-check pin falls from 13 by the sites deleted. Size: medium. Risk: the
prelude carries upstream bodies for functions we implement natively; today the stereotype check
hides the twin. In the bound world the declaration table has one row per id and the
implementation table says "native" for it, so the twin's body is simply never chosen. That is the
duplicate-ids work (task #43) landing as a side effect, not a special case.

**A2. The chosen declaration rides through lowering.** The typed call node holds the declaration
(it already holds the `TypedFunction`); every lowering rule is registered under the declaration id
and looked up by it. Deleted: the bare-name registration index (`REGISTERED_BY_BARE`, `KEYS_BY_NAME`)
and the 158 bare registrations become registrations by id; `nativeKeysAt` goes. Gate: catalog
lookups by name 170 → 0; corpus, conformance, stress rosters unchanged. Size: large but mechanical;
the registration sites are enumerable and the probe's PICK rows check every pick before and after.

**A3. Mints spell declarations.** The 143 places where the compiler itself writes a call by name
(`new AppliedFunction("if", …)`) write the declaration. Most are in the typer and the mapping
translator. Gate: mints by name 143 → 0; the parser's own nodes are the only remaining spellings.
Size: medium, mechanical.

After A, the identity pins that count FUNCTION spellings (mints, catalog lookups, the 20
`function()` compares) read zero and are deleted. Measured 2026-09-25: of the 207 accessor
compares the main pin counts, only 20 compare a call's function; 175 compare a CLASS, PROPERTY or
ELEMENT name (`qualifiedName` 83, `fqn` 41, `rawFqn` 32, `fullPath` 19). Binding functions does not
touch those. Binding classes and properties the same way — the binder attaches the class
declaration, the typer holds it — is the second half of step A and is larger than the first; it
gets its own homework note (which of the 175 are element identity, which are type-shape tests the
type checker legitimately makes) before it is scheduled.

### Step B — Forms by declaration (the former 4d)

Each form's checker is reached because the call's declaration is one the form owns, not because
its spelling matched. Deleted: form dispatch by spelled name (21 sites), the remaining spelling
checks inside checkers (`join`'s canonicalisation, `agg`'s equals, the legacy TDS vocabulary by
name). Gate: form dispatches by name 21 → 0; the probe's FORM rows show zero disagreement; rosters
unchanged. Size: medium. This step also settles which language a bare name is resolved in: engine
input gets the handler surface, Pure source does not.

### Step C — One evaluator

Measure first: the probe counts, per corpus test, which of the four inliners and which fold rows
fired. Then one evaluator over typed terms replaces `StaticFold`'s fold table and interpreter, the
folder's two user-call inliners, the typer's normalise-required inliner and the user-call inliner.
Deleted: all four, and the fold-row enum. Gate: the same corpus tests fold the same values (the
probe records fold results before and after); rosters unchanged; the size of the typer falls by the
folder. Size: large. This is where "add a fold row for `contains`" stops being how plan-time
evaluation grows.

### Step D — The kernel

Homework first, like 4b's: take the 164 kernel failures from the manifest census and the forms'
checkers, and classify every failure by the typing rule that is missing (a type variable bound
twice, a multiplicity variable unbound, a function type not unified, a column type not inferred).
Then implement the rules, each with the census number as its gate, and retire each form checker
that existed only because the kernel could not type the call. Gate: kernel failures 164 → 0 in the
manifest census; the count of form checkers shrink-only; rosters unchanged. Size: large, the largest
in the plan, and the one that pays back most: every checker retired is a page of the typer gone.

### Step E — One ownership registry

The dozen "does the platform own this" mechanisms become rows of the implementation table: the
walled bodies, the lite surface and internal sets, the legacy TDS vocabulary, the subsumed
registry, the engine handler surface's declared column, the members a family implements, the
dynafunction column. The claims ledger is deleted. Gate: every reader of a former mechanism reads
the table; the claims generator and its tests are gone; the table's kinds pinned exactly. Size:
medium.

### Step F — Load by manifest (the former step 7)

As already written in the charter's D7: the walls to zero in cost order (four parser gaps, m3
routing, measures and units, three extension types, the M2M features), then the corpus loader
reads the manifest closure, strict, one parse, one build. Deleted: the library and shape file lists,
the prelude's engine-file lists, the one-row membership. Gate: walls 32 → 0; both corpus rosters
unchanged; the chain within budget; the census pinned. Size: large, mostly the M2M features, which
are product work and should be built as features with their own tests.

### Step G — The seams become packages

With the stages real, the three files held at the size guard's edge (the typer, the lowerer, the
scalar rules) split along the stage boundaries — binder, typer, forms; lowering by family — and the
core's package cycle is broken along the same lines (task #6). Not before: splitting a file whose
responsibilities are still mixed just moves the mixture. Gate: no file over the guard by a margin;
zero package cycles; the guard itself can then drop.

## What we stop doing now

- No new fold rows, inliners, or hand lists. A need that would add one is a reason to start the
  step that owns it.
- No new form checkers before Step D's homework exists.
- No carving a helper out of a 3,500-line file to stay under the guard.
- No tolerant loading, ever.
- No deferral without the step that owns it named in the record and a pin that will show it.

## Order and dependencies

A1 → A2 → A3 → B → C → D, with E and F runnable alongside from B on. G last. Each step lands to
main only when the full chain is green; each is its own homework note, probe sweep and record.
A step that needs a special case to go green stops, and the design is wrong.

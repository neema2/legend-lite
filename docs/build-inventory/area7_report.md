## Part B: problems, with evidence

1. **Two live-Postgres tests never run anywhere.** `//warehouse:postgres_live` and `:postgres_live_native` aren't in //gates:local (gates/BUILD.bazel:11-79) or in any lane (gates-run.yml:50-65), and no commit to .github or gates ever named them (Q6). P3-22 made them "ordinary tests" with the goal "Both run in `bazel test //...`" (workplan :1886). Nothing runs `bazel test //...`: the build lane runs `bazel build` (gates-run.yml:163). Their cost today is the opposite of their value. The build lane compiles them and links the native image for `postgres_live_native`, and nobody runs either. WarehousePostgresLiveTest.java:33 claims otherwise.
2. **The local gate builds the native image, and its comment says it doesn't.** gates/BUILD.bazel:3-5 lists "the native image" as CI-only. Q4 and Q5 show //gates:local reaches `//warehouse:server_native` through `//datacube:live_snap_test` (in //datacube:tests, datacube/BUILD.bazel:245, data datacube/BUILD.bazel:640) and through `//datacube:verify_app_test` via `//warehouse:serve`. Workplan P0-13 accepted this for the app lane (:743), so the comment is what's wrong. Either way, every desk running G pays the H-native cost (1.3–1.5 GB, 2–3 min, workplan :69) whenever warehouse code changes. It's not paid on core edits: the image reaches no core.
3. **`//sdlc-server:page` (2 GB TeaVM) and `:git_repository_test` rerun on every engine edit.** `//sdlc-server:rules` depends on the `//core` umbrella (sdlc-server/BUILD.bazel:18). Q2 shows the page's TeaVM classpath includes exec, driver, testdatagen, probe, ide, test and server_lib. The code uses only `PmcdParser`, `SourceInformation` and `Compiler` (CoreGrammar.java:17,23), which are parser, protocol and `:planner`. The narrow target already exists (`//core:plan_side`, core/BUILD.bazel:217-227) but is visible only to //wasm.
4. **`//warehouse:reachability_metadata` (GEN-COMMITTED) depends on the whole test library.** `deps = [":tests_lib"]` (BUILD.bazel:397) means editing any of 14 warehouse test files, //testing, junit or the duckdb_jdbc pin reruns the generator and the //:generated diff in G and checks. It needs only `:server_lib`. It sits in src/test because Duck and AuthenticatedUser are package-private (Duck.java:36, AuthenticatedUser.java:32). A testonly `java_library` with only that source, in the same Java package and depending on `:server_lib`, would keep the access and cut the trigger down to its true one.
5. **Test-only build actions run in a plain `bazel build`.** `//wasm:jvm_answers` and `//wasm:zone_jvm` aren't testonly (wasm/BUILD.bazel:96-136), so `bazel build //...` plans the whole wasm corpus on the JVM even when nothing will be tested. `//wasm:jvm_main` and `:zone_main` likewise. `//wasm:startup` (a timing tool, 0 users) builds a runfiles tree in every build.
6. **`zone_jvm` reruns about 25 times as often as needed.** Its answer depends on LiteralSpelling and the JDK tz database. It depends on the whole `//core:plan_side` through `:boundary` (wasm/BUILD.bazel:43-48, 89-90). It's cheap, so this is low priority.
7. **Everyday `bazel build //...` does three TeaVM compiles and one native link.** `//wasm:planner` (shipped), `//sdlc-server:page` (shipped), `//warehouse:sqlapi_wasm` (a guard nothing ships, Q3 and inv) and `//warehouse:server_native` (shipped, release-grade). None is manual (area7_targets.tsv). The native image and sqlapi_wasm don't belong in a compile-only lane. The two shipped wasm modules arguably do, but they cost 2 GB of heap each (tools/teavm/defs.bzl:13-14).
8. **Small duplications.** `//wasm:teavm_api` and `//sdlc-server:teavm_api` are identical (wasm/BUILD.bazel:22-29; sdlc-server/BUILD.bazel:51-59). The duckdb extension is copied into three identical directories (serve_extensions, launcher_test_serve_site_extensions, //datacube:app_extensions; defs.bzl:126-133). `_posix_launcher` uses host bash (defs.bzl:66). Workplan P4-12 (:2280) already plans to replace these launchers.
9. **Hand-written tools: each one is justified, and one has an exit date.** //tools/teavm has no built-in alternative. //tools/graalvm stands in for an upstream feature (rules_graalvm#602, workplan :959). //tools/gunzip works around a Bazel 9.2 .gz-mtime bug on Windows (warehouse/BUILD.bazel:360-363). //tools/cc records toolchain versions as a cache key, which the built-in cc autoconfig doesn't do. //tools/postgres uses built-in `rctx.download` and `rctx.extract` for a nested archive. `jar_entry` already uses the built-in zipper (defs.bzl:36-40). I found none where a working built-in is being ignored.

## Part C: the right shape

1. **Compile lane (everyday, fast, compiles only).** Keep: depot-server:rules, the sdlc-server libraries and :server, warehouse :sqlapi, :client, :server_lib, :server, wasm:boundary. The two shipped TeaVM modules (`//wasm:planner`, `//sdlc-server:page`) are COMPILE but cost 2 GB each. Put them behind a `wasm` tag or config so "compile all Java" stays about 30 s, and build them in the app/test lanes that consume them. *Evidence:* tools/teavm/BUILD.bazel:6, defs.bzl:13-14. *Depends on:* the area that decides lanes and suites (P5-01, P5-03).
2. **Native lane only:** `//warehouse:server_native`, `:serve*`, `:launcher_test*`, `:tests_native`, `:postgres_live_native`, and the datacube tests that need the binary (`live_snap_test`, `verify_app_test`). Tag them (`native`) or exclude them from the compile lane with `--build_tag_filters=-native`. **Rebuild trigger** = warehouse sqlapi or server sources, //base, //json, the committed metadata, the GraalVM pin, @host_cc. It already reaches no core, so keep it that way (//tools/deps:warehouse_closure_test). Then fix the gates/BUILD.bazel:3-5 comment, or move live_snap_test and verify_app_test out of G (the datacube area decides). *Evidence:* Q4, Q5; workplan :69, :743.
3. **Put the live Postgres tests in a lane:** `//warehouse:postgres_live` in G and app (same profile as :tests, plus @embedded_postgres, which //core:postgres_arm_test already uses in G). `:postgres_live_native` in the native lane. Or delete them, if no one wants them. *Evidence:* Part B #1.
4. **Narrow sdlc-server to the plan side:** make `//sdlc-server:rules` depend on `//core:plan_side`, or on `//core:planner` plus `:parser` and `:protocol`. Widen `plan_side`'s visibility (core/BUILD.bazel:226) to `//sdlc-server:__pkg__`. Then exec-side core edits no longer rerun the page's TeaVM compile or git_repository_test. *Evidence:* CoreGrammar.java:17,23; Q2. *Depends on:* the core area agreeing on plan_side as the public plan-only API.
5. **Generators run only on their true trigger:**
   - `//warehouse:reachability_metadata`: move ReachabilityMetadata.java into its own testonly `java_library` (same package, deps `:server_lib`) and point the java_run at it. True trigger: server_lib/duck or the generator. Keep the diff in //:generated.
   - `//wasm:jvm_answers`, `:zone_jvm`, `:jvm_main`, `:zone_main`: mark them testonly, so they build only when their tests do. Optionally split a tiny `zone` boundary so zone_jvm depends on lowering only.
   - `//warehouse:duckdb_library` and `:duckdb_extensions` already rerun only on a pin bump. No change.
6. **Guards:** `//warehouse:sqlapi_wasm` and its build_test stay out of the compile lane (testonly already), and run in G and app as today. Their trigger (sqlapi, base, json, TeaVM) is already right.
7. **Wiring cleanup:** one shared `teavm_api` (in //tools/teavm, which the pool rules already allow, tools/deps/pools.bzl). Make `//wasm:startup` manual. Drop the per-launcher extension copies when P4-12's `warehouse_run` rewrite lands.
8. **Tools:** keep all six tools/ packages. Delete //tools/graalvm once rules_graalvm#602 ships. Replace //tools/gunzip with fetch-time unpacking once a Bazel release fixes the .gz mtime bug, and prove it on Windows CI (memory: Bazel-native first).

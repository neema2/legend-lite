## 0. Settled answers

1. **The signature text is RENDERED, not verbatim.** Each declaring file is parsed by our parser
   (`Compiler.parseSources(..., Dialect.LEGEND_PLATFORM)`, `G/NativesGenerator.java:319-322` → `ElementParser.parse`, `C/Compiler.java:161`),
   resolved by our resolver (`NameResolver.resolve(parsed, universe, walls)`, `:328`), and re-spelled by the generator's own renderer
   (`render`/`type`/`qualify`, `:434-523`). The key is computed by re-parsing the rendered text with our parser (`parseSignature`, `:369,417-424`)
   and spelling it again (`canonicalKey`, `:404-415`). Visible differences from upstream: stereotypes and doc blocks dropped, every type
   FQN-spelled, primitives forced to `meta::pure::metamodel::type::*` (`:430-432,519-521`), separators normalised (`", "`), and **bodied
   upstream `function`s are written as `native function`** (`:353-355` renders a `FunctionDefinition` through the same `render`, which always
   prefixes `"native function "`, `:438`). Example: upstream `abs.pure:47` `native function <<PCT.function>> meta::pure::functions::math::abs(float:Float[1]):Float[1];`
   vs `Pure.java:2242` (ABS__FLOAT_1) `native function meta::pure::functions::math::abs(float:meta::pure::metamodel::type::Float[1]):meta::pure::metamodel::type::Float[1];`.
   Classes that shape the bytes: `ElementParser`/lexer (param names, the `TypeExpression` tree, `Multiplicity`), `NameResolver`
   (bare-name → FQN: file wildcards, own package, then `CORE_IMPORTS` first match, `C/compiler/NameResolver.java:646-747`),
   `Multiplicity.toString` (`C/protocol/Multiplicity.java:99,122`), `NativesGenerator.render/type/qualify`, and `PreludeGenerator`'s
   `ENGINE_SPEC_ROOTS`, `DECL_HEADER`, `M3_PURE`, `m3Declarations` (the type universe, `G/NativesGenerator.java:279-311`; `G/PreludeGenerator.java:139-155`).

2. **The committed prelude.pure contributes NOTHING to gen_natives' bytes; it is a load-time failure dependency only.**
   - gen_natives calls the `Set<String>` entry, `NameResolver.resolve(model, knownFqns, wallSink)` (`G/NativesGenerator.java:328`),
     which is `resolve(..., preludeOn=false)` (`C/compiler/NameResolver.java:201-204`). The scope's `knownFqns` is the caller's
     `universe` alone (`:262-263`) — built only from upstream text (`G/NativesGenerator.java:287-311`).
   - The prelude reaches `NameResolver` only through static fields: `PLATFORM_TYPE_FQNS`/`PLATFORM_FQNS`/`QUERY_SCOPE`
     (`C/compiler/NameResolver.java:298-357,561-566`) read `Pure.all*()` and `Prelude.classFqns()/enumFqns()/elements()`. Those fields are
     used only by `knownFqns(elements)` (`:398-408`, the prelude-aware entries `:158-187`) and `resolveQuery` (`:538-539`) — neither on
     gen_natives' path. The two prelude-gated branches (`scope.prelude()`, `:663`, `:1755`) are false here.
   - `Prelude` itself only reads and parses the resource (`C/builtin/Prelude.java:39-55`); it calls no resolver.
   - `Compiler.parseSources` does not touch the boot layer (`BOOT` is a lazy `ContentStore`, `C/Compiler.java:254-293`).
   - So: a prelude.pure edit cannot change Pure.java's text; a prelude.pure that fails to parse (or a Pure.java whose committed
     signatures fail to parse, `C/builtin/Pure.java:737-753`) makes `NameResolver.<clinit>` throw and gen_natives fail.
     This settles G1's OPEN (`bazel-plan/.../G1_dossiers.md:104-106`).
   - Experiment: in a scratch worktree add a class and a function to `RES/prelude.pure` (e.g. `Class meta::pure::functions::collection::Zzz{}`),
     build `//spec:gen_natives`, compare with the baseline hash `7865d1b932884ba4` (`docs/build-inventory/program/evidence/homework/outputs.txt`): expect identical. Then

## 1. The upstream-only design

**A. `//spec:native_catalog` (replaces gen_natives and native_declarations).** Inputs: UPSTREAM_TREES only (no membership, no Pure.java,
no compiled core state). Output: a resource `native-catalog.tsv`, one row per upstream function declaration in the scanned roots
(natives: 372; bodied: ~16.1k), columns: `kind (native|function)`, `identity`, `verbatim header text`, `file:line`, `section imports`.

- **Identity without our parser:** upstream's own overload identity is the package plus the signature id
  (`and_Boolean_1__Boolean_1__Boolean_1_`; legend-pure `FunctionDescriptor`, which core already reproduces in `C/model/SignatureMangle.java:8-50`).
  The id uses RAW SIMPLE type names and multiplicities, so it needs no import resolution — only a header scanner that finds each
  parameter's raw type (skip `<…>`, `{…}` = Function, `(…)` = relation type), its multiplicity, and the return. That is a small scanner,
  not our parser; upstream refuses two declarations with one id in a package, so it is a sound key by construction.
- **Verbatim text:** the header up to `;` (natives) or to the body brace (functions), with the section's imports, so core resolves it
  with the real imports. If FQN-spelled text is still wanted in the resource, the resolution must use upstream data only: the type universe
  from the trees (as today, `:287-311`) and the core import group from `ImportsGenerator.metaImports(CompileContext.java)`
  (`G/ImportsGenerator.java:46-60`) — never `NameResolver.CORE_IMPORTS` as compiled.
- **Size:** natives only would fit a class (today `Pure.<clinit>` is 18,016 bytes of 64 KB and 6,299 constant-pool entries, measured by
  `javap -c` on `bazel-bin/core/libbuiltin-class.jar`); the ~16.5k-row catalog would not (≈9 bytes of `<clinit>` per constant → ~150 KB),
  so it is a resource (`EXECUTION_PLAN_2026_09_26.md:661-663`). Today's 974-row dump is 611 KB; ~16.5k rows ≈ 6–10 MB — too big to embed in
  WASM whole. Hence C.

**B. Our part, hand-owned.**
- `C/builtin/Pure.java` becomes hand-written (leaves `_GENERATED`, `core/BUILD.bazel:701`): each member constant names a catalog
  identity, e.g. `public static final NativeFunctionDefinition AND__BOOLEAN_1__BOOLEAN_1 = catalog("meta::pure::functions::boolean::and_Boolean_1__Boolean_1__Boolean_1_");`
  — the key literal is a reference into upstream, the selection is ours; a missing key fails class init (the orphan refusal, moved to load).
  `signature(String)` (`:737`) stays for the 43 Lite constants only (they are ours; or move them to a hand `lite.pure`).
- `AT_*` groups: computed at class init from the registered constants per FQN (`FunctionId.ofAll`), with the 286 referenced AT_ fields
  (32 files) hand-declared as `AT_X = groupAt("fqn")`, or the 32 call sites switched to `Pure.groupAt(fqn)`. Nothing is generated.
- `RES/native-membership.tsv` retires (its rows ARE the constant declarations), and with it `//spec:native_membership_draft`,
  `//core:draft_native_membership` (`core/BUILD.bazel:829-835`) and `NativeSignatureGeneratorTest`'s membership check (it becomes
  "every `catalog(...)` key exists in the catalog", a test reading the same checkout — tenet 4).

**C. The join, in core's build (allowed: a downstream step may read both).** A small action in core joins `native-catalog.tsv` with the
keys the hand Pure.java names (or a hand key list) into the embedded resource (~800 rows), added to the TeaVM `ResourceSupplier`
(`wasm/src/main/java/planner/PreludeResources.java:21-22`). `Pure.<clinit>` parses those texts as it parses its literals today.

**What changes:** `spec/BUILD.bazel:370-389` (gen_natives) and `:416-433` (native_declarations) → one `native_catalog`; `G/NativesGenerator.java`
(drop `compute`, `withOverloadGroups`, `readMembership`, the membership filter at `:283-306`, the Pure.java template), `G/NativeDeclarations.java`
(deleted); `core/BUILD.bazel:701,710-715` (Pure.java not generated, membership not exported); `C/builtin/Pure.java:737-2768`
(constants → `catalog(key)`, groups computed); consumers of gen_natives' output: `//spec:gen_prelude` override (`spec/BUILD.bazel:453,462`),
`//spec:gen_claims` override (`:496,504`), `//core:core_next`, `//core:update_generated_1` — each reads the hand Pure.java instead.

## 2. Feasibility risks

1. **Re-keying 794 rows from our canonical key to upstream ids.** Mechanical from `native-declarations.tsv` (it has file + text), but the two
   identities may not be 1:1 (ours drops the return type, upstream's keeps it; ours is FQN-typed, upstream's simple-named). Settle: compute
   both for all 974 declarations and count collisions each way.
2. **The header scanner vs upstream grammar** (relation types, `⊆` schema algebra, multiplicity params, `<<…>>`, `{doc}`): settle by
   checking the scanner's id against `SignatureMangle.mangle` of our parse for every one of the ~16.5k declarations (a test, not a generator input).
3. **Bodied functions declared `native` in Pure.java (524 rows):** the catalog must carry bodied declarations, so "natives only" is not
   enough; the resource is large. Settle the size by generating it once; decide build-output vs committed.
4. **Verbatim text resolved at boot** needs the upstream type universe in core (today the resolver's universe at class init is the platform's).
   If that is too much, keep FQN-spelled text in the catalog, resolved inside the generator with upstream-only inputs (§1.A).
5. **WASM:** the planner must load the joined resource (`EXECUTION_PLAN_2026_09_26.md:663`, "checked first"). Settle with a TeaVM build
   embedding a resource of that size.
6. **Boot time:** ~800 parses at class load is today's cost already (`Pure.java:737`); unchanged unless the whole catalog is parsed. Settle by timing `Pure.<clinit>` before/after.
7. **Ten upstream natives outside `ENGINE_SPEC_ROOTS`:** an upstream-only catalog should scan whole trees (main sources) rather than our
   root list, or the root list is itself an input of ours. Settle: does any of the 10 parse with our parser (they live in sql/mongodb/elasticsearch/python/deephaven).

### 1.5 Design: generated upstream table + hand-owned decisions, joined at class init

**(a) `core/src/main/java/com/legend/builtin/DynaFn.java`, generated whole from the engine tree alone.**
- Members `ABS("abs", Inference.MAPPED, Dialect.DEFAULT)`: name, inference and dialects only. No Resolution, no FQN.
- `enum Inference`, and `enum Dialect` generated from the set of dialects seen (sorted), so no upstream fact is hand-typed.
- Accessors that are facts: `dynaName()`, `inference()`, `dialects()`, `of(String)`.
- The generator fails on: a file it would bucket `OTHER` (`:62`); two names mapping to one constant (none today: 232 names,
  232 distinct constants, checked; a future `arrayAppend` beside `array_append` would collide); a name not a valid identifier.
- The header javadoc becomes generator template text.

**(b) `core/src/main/java/com/legend/builtin/DynaFnDecisions.java`, hand-owned (new).**
- Holds `enum Resolution { PURE, SHIM, TRANSLATED, UNSUPPORTED }`: platform vocabulary, so not in the generated file.
- Holds the decisions keyed by the generated constants, so a name upstream drops is a compile error:
  `EnumSet<DynaFn> PURE`, `EnumMap<DynaFn,String> SHIM` (→ `Pure.Lite.X`, the 8 rows), `EnumSet<DynaFn> TRANSLATED`, and
  `EnumMap<DynaFn,String> RESIDUE` (`SQL_NULL/TRUE/FALSE` → `Pure.SQL_*.qualifiedName()`, moved out of the generator).
- Absent from all three = UNSUPPORTED. That keeps today's semantics (`DynaFnGenerator.java:131`): a new upstream name is
  handled by nothing, and `UNSUPPORTED_MAX` (`DynaFnRegistryTest.java:49,102`) turns the gate red until a person acts.
  The alternative is a total map; it trades that ratchet for a compile-time totality check.
- Static init joins the two: `resolution(d)`; `fqns(d)` = PURE → `EngineHandlers.fqnsOf(d.dynaName())`, else `RESIDUE`
  (throws, as `:111` does now, if both are empty); SHIM → the Lite constant; else `List.of()`. Also `liteFqn(d)` and
  `withResolution(r)`.
- This is the same call the generator makes today (`:106`), moved from build time to class init. The result is identical
  for a given engine-handlers.tsv, and the stale-table two-step (1.1) disappears.
- Class-init order is safe:
  - DynaFn's constructor references nothing.
  - `DynaFnDecisions` reads `DynaFn.values()`, `EngineHandlers`, `Pure` and `Pure.Lite`.
  - `Pure` refers to DynaFn only in comments (`Pure.java:435,460`), and EngineHandlers not at all.
  - The resource is already loaded at runtime by EngineHandlers, and supplied to both TeaVM builds
    (`wasm/src/main/java/planner/PreludeResources.java:22`, `sdlc-server/.../PageResources.java:15`).
  - The warehouse native image never reaches core (`warehouse/BUILD.bazel:32`).

### 1.6 Risks, each with what settles it
- R1 Equivalence of the join. Before the change, dump `(name, resolution, fqns, inference, dialects)` for every member
  with a 10-line test. Dump again after and `cmp`. Byte-identical is the gate.
- R2 Coupling to the engine-handlers redesign. If gen_engine_handlers becomes upstream-only, its column 3 would carry the
  upstream FQN, declared or not. `fqnsOf` would then need a declared-only filter
  (`!Pure.nativeFunctionsAt(f).isEmpty()`, which DynaFnRegistryTest `:74-77` already asserts). Settle jointly with the
  owner of gen_engine_handlers.
- R3 gen_prelude scans core Java text for FQN tokens (`PreludeGenerator.java:339-353`). Removing DynaFn's literals could
  change `javaDemand`. The index there is spec classes and enums, not functions, so it probably does not. OPEN: settle by
  regenerating `//spec:gen_prelude` after the change and diffing prelude.pure.
- R4 Dialect path conventions (`:52-63`) are a heuristic. Making `OTHER` fatal can fail a bump loudly, which is intended.
  Settle by grepping `E/` for `dynaFnToSql(` files that `dialectOf` maps to OTHER (none today, since the committed enum has no OTHER).

## 5. //tools/engine-runner:vocab

- The scope is the BUILD's `:runner` jar list (`tools/engine-runner/BUILD.bazel:16-44`).
- Experiment: rebuild after a core edit, compare with `babb5145f1b3037b`. Expect identical.

## 6. //tools/reference:ref_imports

- Upstream-only, confirmed by `bazel query 'deps(//tools/reference:ref_imports) except filter("^@", …)'`. That returns
  only `RefImports.java`, `:ref_imports_lib`, `:ref_imports`. The libraries are `_REFERENCE_JARS` (`tools/reference/BUILD.bazel:11-49`).
- The only rdeps are the analysis-only guard edges (`rdeps(//..., …)` → `//tools/guards:*`, `//gates:local`). No consumer.
- **Why ref_dump is not reproducible.** Recorded: P2-14 found anonymous ids and line order differing across runs
  (`bazel-plan/docs/BAZEL_FIRST_CLASS_WORKPLAN_2026_10_03.md:1396,1439`). The code:
  - (i) `ref_dump` writes rows in traversal order: `PackageTreeIterable` + `pkg._children()` (`RefResolutions.java:46-48`),
    unsorted.
  - (ii) It prints `getUserPathForPackageableElement(func)` of resolved functions (`:105`). For lambdas and column functions
    that is `@_<counter>` from `ModelRepository.anonymousIdCounter` (`P/legend-pure-core/legend-pure-m4/…/ModelRepository.java:85,92`).
  - (iii) `AbstractCoreInstance.hashCode()` is `Object` identity (`P/…/m4/coreinstance/AbstractCoreInstance.java:33-37` (`hashCode` → `super.hashCode()`)), so
    hash-keyed collections of instances iterate in a per-run order. That order drives both creation order (the counter)

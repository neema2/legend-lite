### 0.3 What each step really reads (model.py is the only file reader)

- model.py at import reads the layout: `$STRESS_LAYOUT` if set, else the committed
  `core/src/test/resources/com/legend/integration/stress-layout.json` (scripts/corpus/model.py:52-55).
- `model.take_inputs(argv)` sets `DECLARED` from `--inputs` (model.py:66-72); `_pure_files(dir)` then returns only
  declared `.pure` files directly in that dir (model.py:75-79).
- `model.stress_sources()` = declared stress files minus `GENERATED` (the seven "stress" files 92-98) minus `EXCLUDE`,
  plus `DENSE_DIR/<name>` for each dense file when `DENSE_DIR` is set (model.py:90-100).
- `model.load()` reads `linked_files() + stress_sources()` (model.py:1947-1953).
- `query.load()` reads `scripts/corpus/queries.pure` (query.py:399; QUERIES at model.py:44). Called from build.py:152,
  differential.py:161, executed.py:408 and oracle.py's `__main__` (:2729) only.
- No module in any closure opens anything else: `grep read_text|open(|glob|os.environ` over the 29 + 3 mains finds only
  model.py, query.py, density.py:113 (via `stress_sources()`) and density.py:122 (`glob.glob(STRESS)`, relative to
  cwd, in `density.main()` only, which no generator calls), plus differential.py:134 (clearing its own output dir).
- oracle.py reads zone data through `zoneinfo` (oracle.py:1571-1577) from the pinned tzdata, `PYTHONTZPATH=""`.

## 1. //scripts/corpus:gen_dense

1. **Identity.** `//scripts/corpus:gen_dense`, `run_binary` (`_run_binary`, @bazel_lib), scripts/corpus/BUILD.bazel:103-115.
   Tool `:dense_build` (py_binary, :67-71). Program: scripts/corpus/dense_build.py, `main()` at :34-39, `generate()` at :20-31.
2. **What it computes.** It loads the hand-written stress corpus and the linked projects into a Python model, works out
   which tables have seed rows, and writes three extra stress files: a second, feature-rich mapping of already-mapped
   classes (59), extra store features (60), and the combination matrix's model and store (64). Each draws from a seed
   list committed in the Python code, so adding a stress file does not move them (dense_build.py:7-10).
3. **Why it exists.** 143a54bc5 (2026-10-04, P2-01, ported from spike S5): the three files were generated before, but
   by hand; the action makes the committed bytes checkable. It feeds gen_stress (whose 92-98 read 59/60/64) and the
   committed corpus. The reason stands.
4. **Inputs, declared** (QA1, 228 action inputs): our sources: 192 `core/src/test/resources/stress/*.pure` (the
   stress_sources), 31 `projects/<11 linked>/*.pure`, `scripts/corpus/queries.pure`, `scripts/corpus/dense_build.py`;
   other generators: `bazel-out/.../core/stress_layout.json` (`//core:stress_layout`); tools: the `dense_build`
   launcher and its runfiles tree (30 .py of `:corpus` + main, `@pypi//tzdata` 634 files, Python 3.12 toolchain; Q7).
   Upstream archives: 0. Maven pools: 0. Core jars: **0** (Q4 empty). Env: `CORPUS_ROOT=.`, `STRESS_LAYOUT`,
   `PYTHONUTF8=1`, `PYTHONHASHSEED=0`, `PYTHONTZPATH=`, `LC_ALL=C.UTF-8` (BUILD:75-86; QA1).
5. **Inputs, actually read.** See 0.3: the 192 stress sources, 31 project files, `$STRESS_LAYOUT`; Python modules of
   its 14-module closure; tzdata only if an oracle call converts a zone. **Over-declared:** queries.pure (BUILD:90-94
   puts it in `_INPUTS`, shared with gen_stress); 15 library modules. **Under-declared:** none found.
6. **Outputs.** `scripts/corpus/dense/59-dense-mapping.pure` (the dense second mapping), `60-dense-store.pure` (store
   features over store::DB), `64-combinations.pure` (the combination matrix's classes, tables, joins, mappings).
7. **Committed?** Yes: `core/src/test/resources/stress/{59,60,64}-*.pure`. Writers `//core:update_stress_corpus_0..2`
   (aggregate `//core:update_stress_corpus`, core/BUILD.bazel:769-781), diff tests `//core:update_stress_corpus_{0,1,2}_test`
   in `//core:update_stress_corpus_tests`, in `//:generated` (BUILD.bazel:84) and, through `//core:update_stress_corpus`,
   in `//:update_generated` (BUILD.bazel:111).
8. **Who consumes it.** gen_stress (as `--dense`, BUILD:117-132); the three writers and diff tests. The committed
   copies are read by everything that reads the corpus (gen_differential, the five corpus gates, core_tests_lib's
   resources and so the stress suites and corpus_differential_test). Humans: the failure message names
   `bazel run //core:update_stress_corpus` (core/BUILD.bazel:771); dense_build.py:9-10 says "//core:update_generated
   writes the files back", which is **stale** (the writer is `//core:update_stress_corpus`).
9. **Determinism.** Same inputs, same bytes: PYTHONHASHSEED=0 and a fixed tzdata (BUILD:75-86); oracle's clock
   functions refused (143a54bc5 message: "a Bazel action never reads the clock"); exactmath.py replaces platform libm
   (BAZEL_EXECUTION_LOG.md:142-144); byte-identical on Linux, macOS and Windows (throwaway 37248685802,
   BAZEL_EXECUTION_LOG.md:145-146). oracle.py:1850 (`uuid4`) and :1862 (`getuser`) are nondeterministic, but no
   committed stress file or queries.pure calls generateGuid or currentUserId (`grep -l` empty).
10. **Cost.** One Python process; no JVM, database or server. 41 s (S5 E3, workplan:1245). No memory or resource
    setting (run_binary has none).
11. **What reruns it today.** Any of the 30 .py in the tool's runfiles (29 library + main), queries.pure, any of the
    192 hand-written stress files, any of the 31 linked-project files, core/stress.bzl (via the layout), the tzdata pin,
    the rules_python/Python toolchain. Never a core or upstream change (Q4). Surprising ones: queries.pure and 15
    modules outside its closure (for example editing density.py's ratchet constant reruns it).
12. **What SHOULD rerun it.** A change to its 14-module closure, the hand-written stress sources, the linked
    projects, or core/stress.bzl. A corpus/generator change of ours, never engine behaviour.
13. **Who runs it today.** Built by the build lane (not manual). Checks lane and local through `//:generated` ->
    `//core:update_stress_corpus_tests`. Also built by gen_stress (and so by the same suites). The bump's phase 2 runs
    it through `//:update_generated` -> `//core:update_stress_corpus` (Bump.java:148-151), and phase 3 through
    `bazel test //...`. By hand: `bazel run //core:update_stress_corpus` (core/BUILD.bazel:771; build.py:4).
14. **Recommendation: COMMITTED-SOURCE.** Its outputs are committed, engine-free, and change only when our corpus files
    or our Python change. Manual: yes (reached through its writer, its diff tests and gen_stress). Writer: in the
    source-derived update group (the design's renamed `//:update_generated`, C and D), not a bump-only update (it is
    cached through a bump anyway). Diff test: the everyday gate's generated-source group (`//gates:generated_source`;
    today `//:generated`), as D8 decided (workplan:233-244). Narrowing: drop `queries.pure` from its srcs (split
    `_INPUTS`); give dense_build a py_library of its 14-module closure, so a ratchet-constant edit in density.py,
    executed.py or stacking.py stops rerunning it.
15. **Open questions.** (a) Does any of the 14 modules ever reach oracle code that converts zones on the dense path,
    so that tzdata is really needed? Settle: run the action with `@pypi//tzdata` removed. (b) dense_build.py:9's stale
    writer name: fix in the code line.

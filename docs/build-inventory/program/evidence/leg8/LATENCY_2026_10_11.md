# Leg 8's cost check: compile latency before and after the one parser (2026-10-11)

Leg 8's design asks for the boot's parse time before and after the one parser (`docs/PROTOCOL_PROGRAM_2026_10_05.md`
leg 8, step 1: "the boot's parse time measured before and after, `//core:compile_latency`"); the DataCube + Python
line asked again when `//studio:demo_test` ran at 57 s of its 60 s budget on its branch (under a load of 12 to 26).
Before: main at `37a3edb2c`, just before leg 8's landing. After: main at `741f24f9a`. One run each, one after the other,
on one machine, its load average about 10 to 13 (other sessions' builds): a check that the change did not slow the
compiler, not a benchmark.

| | before (`37a3edb2c`) | after (`741f24f9a`) |
|---|---|---|
| `bazel run //core:compile_latency -- --corpus stress --passes 2`: the model (7,610 elements), parse and build | 4,808 ms | 3,332 ms |
| the first case, cold | 364 ms | 183 ms |
| pass 1 (4,736 cases, the model's demand caches empty) | 10,197 ms | 7,384 ms |
| pass 2 | 4,767 ms | 3,884 ms |
| per case, total: p50 / p95 / p99 | 0.59 / 2.10 / 3.92 ms | 0.49 / 1.65 / 2.74 ms |
| cases ok / skipped / failed | 4,723 / 2 / 11 | 4,723 / 2 / 11 (the same failures) |
| `//studio:demo_test` (uncached) | 18.7 s | 16.2 s |
| `//query:build_test` (uncached) | 10.9 s | 9.1 s |

The one parser did not make compiling slower; the demo test's 57 s on the DataCube line's machine is that machine's
load, not the change (16 to 19 s here on either side).

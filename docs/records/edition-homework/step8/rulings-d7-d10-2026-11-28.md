## D7: a last step's `format`

**What legend-pure does (READ, legend-pure 5.99.0).** `PureStringFormat.format` (the compiled engine,
`legend-pure-runtime-java-engine-compiled/.../processors/support/PureStringFormat.java`) and `Format.format` (the
interpreter, `.../interpreted/natives/essentials/string/toString/Format.java`) read a template the same way:

| Directive | What is written | Rounds? |
|---|---|---|
| `%s` | `CompiledSupport.pureToString(arg)`; the interpreter calls `toString_Any_1__String_1_` | no |
| `%r` | the Pure function `toRepresentation` (`toRepresentation.pure`:40-47): a Number its `toString`, a String quoted and escaped, a date `%` and its `toString`, a Decimal its `toString` and `D` | no |
| `%d` | an Integer's digits | no |
| `%f` | `FormatTools.appendFloatString(builder, <the Float's toString text>)`, precision -1: **the text appended as it is** (`FormatTools.java`, `appendFloatString(StringBuilder, String, int)`, first branch) | **no** |
| `%.Nf` | the same method with precision N: pads with zeros, or rounds half-even through `BigDecimal` | **yes** |
| `%0Nd` | zero-padded Integer | no |
| `%t`, `%t{pattern}` | a date, by the pattern | no |

**A finding for the user.** The decision page said "`%f` would round in Java". Read in both engines, bare `%f` does
not round: it writes the Float's own `toString` text, exactly what `%s` writes for a Float. Only `%.Nf` rounds. The
ruling says `%f` is recorded as a difference, and that is what is built: neither `%f` nor `%.Nf` is lifted. Lifting
bare `%f` would cost one more letter in the reader's test (`PrintedFormats.Read.floats`) and no rounding; it is the
user's to say.

**What was built: ruling (b), within a small reader.** `edge/PrintedFormats` (about 190 lines with its notes) reads a
literal template's directives as legend-pure reads them, only to know which argument stands under which directive.
At legend-pure's doors, where a program's last step is `format(<a literal template>, [arguments])`:

- each argument that is a computed Float (declared type Float, no literal) under `%s` or `%r` is read as a value's
  print: run as a query of its own, the double printed by the edge's one Float printer (`PureValueText.pureFloat`);
- its text is put in the argument's place as a String literal and its directive made `%s` (a text under `%r` would
  be quoted);
- the database then fills the template as before, and still computes every other argument and raises every refusal.

So Java prints and decides nothing else: no rounding, no template filling in Java. The body door
(`UpstreamPrints.read`, PCT's channel B and the corpus) lifts a `format` that is an assert's own argument; a query
door (`UpstreamPrints.readLastFormat`, PCT's channel A) lifts one that is the query's last statement.

**Left to the run, lite's own text, recorded (register S434 as amended):** `%f` and `%.Nf` (the ruling); a Float
literal (the lowering writes a literal's text from its written digits); a Float held in a `Number` or an `Any`; a
template that is no literal; a call whose arguments are not one value each, or not as many as the template's
directives; an argument from an unrepeatable source (the clock, a draw, a pick from unordered rows: the guard a
value's print is held to); and a `format` that is no last step (`format(...)->length()`, `format(...) + ';'`): used
further, its text is lite's own in the middle of a program.

## D8: `trim` fixed; four differences recorded

**`trim`.** legend-pure's `trim` is Java's `String.trim` (`CoreHelper.java`:1236 `return str.trim();`, the
interpreter's `Trim.java`:51), which strips every character up to U+0020 at either end. Lite's SQL stripped spaces
alone (`'\ta\n'->trim()->length()` was 3 on DuckDB, H2 and SQLite, recorded 2026-11-26). The lowering now gives the
database's own trim the set of white-space characters at most U+0020: a tab, a line feed, a vertical tab, a form feed,
a carriage return and a space (`lowering/Scalars`, `TRIMMED`).

- *What is left, and why (a choice of this session, for the user's eye):* the other control characters at most
  U+0020 (U+0000 to U+0008, U+000E to U+001F) are not in the set. Written raw in the SQL of every statement that
  trims, they would put an escape, a bell or a backspace in the statement's text, for a character no ordinary text
  begins or ends with; U+0000 cannot be written in a literal on Postgres at all. Adding them is one line.
- *At legend-engine's door:* legend-engine sends `trim(%s)` (`extensionDefaults.pure`:297, no database overrides it),
  the database's own trim, spaces alone on the databases read. After the fix lite answers Pure's way there too, the
  tenet's default (AGENTS.md, upstream fidelity: where legend-engine departs from Pure's own definition lite answers
  Pure's way and records it). The alternative, a row of legend-engine's table that keeps the database's own trim
  inside a store query, is the user's to ask for.
- `ltrim` and `rtrim` are other functions with another set in legend-pure (commons-lang's `stripStart` and
  `stripEnd` with a null set, `Character.isWhitespace`: `CoreHelper.java`:1241 and 1246) and are not changed: found
  on the way, no row yet, named in the landing note.

**The four differences** are register rows S437 to S440, each with upstream's code read (file and line) and lite's
answer run on DuckDB, H2 and SQLite (`edge_cases_answers.tsv`, the `tail.*` and `float.*` cases).

**The year below 1000, checked first (READ).** legend-pure writes a year as the bare number, unpadded:
`DateFormat.java`:240 (`safeAppendable.append(date.getYear());`, an `int`, through `SafeAppendable.append(int)`,
`Integer.toString`), where the month and the day go through `appendNonNegTwoDigitInt`. A date literal with such a
year parses: the lexer takes one or more digits for the year (`M4Fragment.g4`:23) and `DateFormat.parsePureDate`
reads them with `Integer.parseInt` (lines 327-338), bounded only by `java.time.Year`'s range. Lite's Java print
writes `999-03-04T10:20:30.5+0000` for such an instant, the same form
(`PureRelationTextTest.aComputedDateTimeIsItsSecondsAndTrimmedFraction`). So a year below 1000 at a last step is no
difference; what lite's own SQL text writes for such a year in the middle of a chain was not measured on any
database (no recorded test holds one) and S435 says so.

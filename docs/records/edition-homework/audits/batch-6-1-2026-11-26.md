## BLOCKERS

### B1. `inFold` still answers a String needle against date and time elements by raw Java equality: a wrong fold. CONFIRMED
`compiler/spec/LiteralUnroll.java:452-458`. `comparedHere(value)` lets a `TypedCString` needle through. The `anyMatch`
then compares `scalar(e)` against the needle's raw value with no check that the two are the same kind (`cls`). The
`contains` arm (l.511-512) and `equalityFold` (l.424) both make that check; `inFold` does not. `literal()` holds a
date's scalar as a **String**: `TypedCDate` gives `canonicalText()` (l.93, `PureDateLiteral.spelled`, e.g.
`"2014-02-01"`, `"2014"`), `TypedCTime` gives `String.valueOf(...)` (l.97), and `TypedCLatestDate` gives `"%latest"`
(l.99).
- The Typer accepts the input. `EqualityClasses.of` reads the element type `Any` as "known only at run time", so no
  crossing is marked. TaggedListTest compiles the same shape with a date needle.
- Input: `|'2014-02-01'->in([%2014-02-01, 1])`. The fold answers **true**. Pure, and lite's equality rule (different
  types are never equal), answer **false**. `|'2014'->in([%2014, 'x'])` and `|'%latest'->in([%latest, 1])` fold to
  true the same way.
- The bug predates this batch (the old `inFold` had the same `anyMatch`). The batch rewrote this function, though, and
  its javadoc now says only String, Boolean and enumeration values are compared, which the code does not hold to.
- Fix: in the `anyMatch`, require `literal(e)` to be a `Scalar` with the needle's `cls` (as `contains` does).
- Missing test: the input above, expected `false`.

### B2. Removing the Integer `==` fold breaks the tier-1 recursion unroll for every `size() == n` or `$n == 0` guard. Mechanism CONFIRMED, reach PLAUSIBLE
`LiteralUnroll.java:423-427` no longer folds `TypedCInteger == TypedCInteger`. The size arm (l.495-498) still turns
`$l->size()` over a spelled list into a `TypedCInteger`, so `$l->size() == 0` is now left as a call.
`UserCallInliner.literalArms` (l.1313-1326) prunes an `if` only when its rewritten condition is a `TypedCBoolean`.
Otherwise it rewrites BOTH branches, so the recursive branch is inlined again. At the empty literal,
`literalSize (0) < enclosing (0)` is false, `inlineCall` throws the recursion wall (l.775-786), the catch at l.850-857
turns it into a standing `TypedUserCall`, and SQL lowering later refuses it.
- `NormalizeFolds.fold` (l.95-104) still folds Integer `==`, but only in `deepFoldInlined`, after the callee body has
  been reduced (`UserCallInliner.java:825`). That is too late for the `if` inside the recursion.
- Input: a user function
  `f(l:Integer[*]):Integer[1] { if($l->size() == 0, |0, |$l->at(0) + f($l->tail())) }` applied to `[1, 2, 3]`. Before
  the batch it unrolled to SQL. Now it is refused ("recursion cycle ... recursive functions cannot lower to SQL").
- It also breaks the WORLD_MAP rule. `docs/WORLD_MAP.md:84-87` lists "spelled-integer compare such as `size() == 1`" as
  STRUCTURAL, ratified 2026-09-03. That tenet was not amended.
- The batch is inconsistent with itself: it keeps the Integer ORDERING arm (l.484-492), so `size() > 0` still folds
  while `size() == 0` does not.
- The same mechanism means a dead `if` arm is now rewritten (inlined) wherever its guard is an Integer `==`, for
  example the platform's own `prelude.pure:3765-3789`
  (`if($this.x->size() == 1, |$this.x->toOne()->elementToPath(), |[])`). NormalizeFolds prunes it afterwards. But if
  rewriting the dead arm throws a `TypeInferenceException`, that exception is not caught (only `NotImplementedException`
  is), and the query fails where it used to compile (PLAUSIBLE).
- I found no core test with a literal recursion under a `==` guard. The corpus and PCT rounds are where this would show.
- Fix options: keep the Integer `==` fold (it is exact and structural, and WORLD_MAP names it), or ask the owner.
  Deleting it needs the unroll's `if` to fold `size() == n` some other way first.

### B3. Membership in a written list with ONE same-type element that is a run-time parameter is refused at render. CONFIRMED
`lowering/TaggedLists.java:587-594` builds `new SqlExpr.Call(SqlFn.IN, [needle, e1, ...])`. Every dialect reads a
two-argument `IN` whose second argument is a `PlanParam` as a LIST parameter:
- `AnsiSqlRenderer.inList` (l.1368-1373) goes to `anyOf`, which throws "plan parameter ... is not a list parameter"
  (l.2416-2422).
- `BigQuery.in` (l.1891), `MariaDb.in` (l.2149), `SQLite.in` (l.1926) and `Snowflake.inArm` (l.1637) throw
  `listParameter` or a DialectCapability.

A `[1]` query parameter lowers to a scalar `PlanParam` (`planner/QueryParameters.slot`, l.52-55).
- Input: `{s:String[1] | 'a'->in([$s, 1])}`, or `{n:Integer[1] | $x.age->in([$n, 'unknown'])}`. Each is refused on
  every database. The old channel-array path bound `[?, NULL]` and answered.
- Fix: emit `EQUAL` when one element remains, or give IN-over-a-list-parameter its own MIR shape (`Membership` exists)
  so a two-argument `IN` is never ambiguous.
- Missing test: either input, expected an answer.

## SHOULD-FIX

### S1. `sameWrittenLists` is a bare chain of `=` and AND, with no COALESCE: it answers NULL where the old path answered false or true. CONFIRMED (code); inputs PLAUSIBLE
`TaggedLists.java:103-112`. An element typed `[1]` is NULL at run time for:
- a nullable column mapped to a `[1]` property;
- a property read through an outer join or association (`$p.firm.name`);
- a column of a row read through a left join.

Input: `filter(p | !([$p.name, 1] == ['x', 1]))` over a row whose name is NULL.
- Old (`sameListByKinds`, `NOT (… IS DISTINCT FROM …)` on arrays): false, so `!` gives true and the row is kept.
- New: `name = 'x' AND 1 = 1` is NULL, `NOT NULL` is NULL, and the row is dropped.
- Projected, the column is NULL where Boolean[1] was false.

`contains` (l.594) wraps its IN in `COALESCE(…, false)`. The equality does not, so the two disagree. At minimum, wrap
the result in `COALESCE(…, false)`. Then say whether `[NULL, 1] == [NULL, 1]` (true before, false after) is intended.

### S2. SQLite answers the new date-time comparisons by their TEXT: DuckDB now says true where SQLite says false. CONFIRMED
`SQLite.timestampLit` (l.763-766) writes `'2020-01-01 10:00:00'` and `'2020-01-01 10:00:00.000'`, "its fraction as
written". `keptFraction` keeps written zeros up to 9 digits. Only the judges' casts normalize the text
(`variantAwareCast`, l.1340-1360).
- Before: the fold answered `%…T10:00:00 == %…T10:00:00.000` false on every database.
- Now: DuckDB, H2, MariaDB (`CAST AS DATETIME(6)`), BigQuery (`DATETIME '…'`) and ClickHouse (`toDateTime64(…, 6)`)
  answer true. SQLite answers false (`'… 10:00:00' = '… 10:00:00.000'` as text).
- The same holds for the written-list IN, for `sameWrittenLists`, and for the `%2020-01-01T10` hour form.
- This is the known slice-6.5 work (`docs/records/database-recheck-2026-11-26/START_HERE.md:71-73`). The batch makes
  the databases disagree on the product's own `==` before it lands. `OneValueWithinOneTypeTest` runs only on the
  platform (DuckDB), so nothing shows it.
- Say so in the record, or keep SQLite's old answer by refusing on SQLite until 6.5 lands.

### S3. The mixed-list ORDER of two date-times at one instant changed, with no register row. CONFIRMED
`lowering/MixedEncoding.java:337-338` clamps the precision tie-break at HOUR, so `%2025-02-10T00` and
`%2025-02-10T00:00:00` now tie. Before, the coarser came first, as legend-pure's `DateFunctions.compare` orders them
(O2's D1).
- `[%2025-02-10T00:00:00, %2025-02-10T00]->sort()` now keeps the list's order; Pure orders the hour form first.
- `[%2025-02-10T00, %2025-02-10T00:00:00]->max()` now answers the first; Pure answers the second.

S399 (`docs/SEMANTICS_REGISTER.md:275`) rules equality, not order. Under AGENTS.md's upstream-fidelity tenet, a
divergence that is not a ruled row is a defect. It should be posted and given a row (or S399 extended by the owner).
- Also, `TaggedLists.sort` orders by the comparable alone (l.289-291, `list(p ORDER BY comparable[p])`). Ties are not
  guaranteed to keep the list's order inside the aggregate, so `->sort()->at(0)` over a tie may differ by database.
  The root egress re-sorts by position, so that path is stable (PLAUSIBLE).

## NOTES

- **NumberLiterals** (`NumberLiterals.java:149-153`): the bound is right.
  - `whole = precision − scale` (at least 0), plus `scale`, at most 38. So 38 whole digits pass, 39 are refused.
  - `0.001` gives whole 0, scale 3. `1.0e40` (unscaled 10, scale −39) gives whole 41: refused.
  - `1.5e-40` gives scale 41: refused. Negatives and zero are fine.
  - Not covered: the bound is on the literal alone. Against a Decimal value of scale s > 0, a 38-digit whole literal
    needs DECIMAL(38+s, s) to compare. DuckDB then compares in DOUBLE (inexact), and others may overflow. "Never a
    database's overflow" (l.147-148) is not fully true (PLAUSIBLE).
  - Missing boundary test: `|let a = 1.5D; $a < 12345678901234567890123456789012345678;` (38 digits) should give
    0 crossings.
- **Decimal hash:** `hash` over a mixed list hashes each element in its own slot (`TaggedLists.hash`, l.652-658). On
  DuckDB, HASH of DECIMAL(2,1) 1.5 and DECIMAL(3,2) 1.50 may differ, so two lists now `==` may hash differently
  (PLAUSIBLE).
- **Refs and Strings:** a `TypedPackageableRef`/`TypedTypeRef` element is kind `String` (`MixedEncoding.java:128-132,
  416-418`). So `'my::C'->in([my::C, 1])` answers true on the new IN path, as it did on the channel path (not new).

    which is the old path, not a guess.

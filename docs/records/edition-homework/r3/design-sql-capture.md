# SQL capture across doors: design (read-only research, 2026-11-25)

## 0. Short answer

- Build two `bazel run` tools and one optional env-gated hook.
  - `//core:capture_sql` covers the two fixed query sets, `channel_a` and `core`, under every query door.
  - `//spec:capture_sql_corpus_{duckdb,h2}` covers the relational corpus's test bodies under the body doors.
  - The optional hook goes inside PCT channel B, which can only be reached through its own lane.
- All of it plans and none of it runs. The one exception is channel B, which runs because its lane runs.
- Each tool writes a sorted TSV to a path given as an argument. The file is never pinned.
- Every hook point already exists: `TypedQuery.executionPlan(runtime, features, style)`, `TestExecution.planBody(typed, runtime, options)`, `PlanJson.write`, `TestPlanJson.write`.
- Hash the plan's statements (every `"statement"` field of the plan JSON, in order). Also hash the whole plan JSON, so a change in the bound slots shows too.
- Before trusting a diff, run the same tree twice and `cmp` the two outputs. Section 3 lists real sources of run-to-run drift.

## 1. The existing harnesses

### Core: product SQL sizes

- **Library.** `//core:lean_sql_baseline_lib`, defined at `core/BUILD.bazel:3221-3242`.
  - It is testonly and visible to `//spec`.
  - Its sources: `leansql/LeanSqlBaseline.java`, `CastCaseCensus.java`, `sql/dialect/PassedTrees.java`, `planner/Lowered.java`.
  - Its deps: `:core`, `:test_backends`, `//json`, `//testing`. It does NOT depend on `:edge`.
  - `src/test/java/com/legend/leansql/*.java` is excluded from `core_tests_lib` (`core/BUILD.bazel:638`).
- **Test.** `//core:lean_sql_baseline_test` (`core/BUILD.bazel:3244-3264`) runs `LeanSqlBaselineTest.theProductsSqlIsHeldToItsBaseline`.
  - Its inputs come in as runfile properties: `-Dlegend.lean_sql.{baseline,channel_a,core}=$(rlocationpath ...)`.
  - They are read with `com.legend.testing.Runfile.property(...)`.
- **Updater.** `//core:update_lean_sql_baseline` (`core/BUILD.bazel:3372-3379`) runs `LeanSqlBaseline.main`.
  - It reads and writes under `$BUILD_WORKSPACE_DIRECTORY/core/src/test/resources/lean-sql/`.

### What `LeanSqlBaseline` does

- **`measure(sets)`** (`LeanSqlBaseline.java:173-239`), used for `channel_a`. It iterates as follows:
  - For each `Databases.implemented()` database that is relational (MongoDB is skipped, `:314`), and for each line `{"model","expression"}`:
  - `Compiler.compileModel(withRuntime(model, type))` is cached per model, per database.
  - Then `Compiler.query(ctx, expression)` and `.executionPlan(StorelessRuntime.RUNTIME, Set.of(Feature.CORRECT_SQL_SUBSTRING_INDEXING))`.
  - `withRuntime` (`:346`) is `StorelessRuntime.with(model, type)`, falling back to `onServer(...)`.
- **`measureOwn(set, file)`** (`:244-305`), used for `core`.
  - The file holds `{"model_id","model"}` lines, then `{"model_id","query","runtime"}` lines.
  - Each query runs `Compiler.query(ctx, query).executionPlan(runtime)`, on the query's own runtime.
  - The database is the plan's own: `plan.answerSql().target().database().type()`.
- **Where the SQL text is in hand.**
  - `ExecutionPlan plan` at `:210` and `:277`.
  - `collect(plan.root(), statements)` (`:377-393`) gathers `Sql.statement()` for the TdsResult, Keyed (keys and body), Update, Effect and Check nodes. It skips Load and Constant, and a target's session statements.
  - `PlanJson.write(plan)` is at `:219` and `:285`. A hash can be taken at either point.
- **Door today.** `measure` uses the PRODUCT style with the substring feature on. That is not what the product door passes: `Execution.run` uses `executionPlan(runtime)`, which has no features. `measureOwn` uses PRODUCT with no features.
- **Refusals.** `isRefusal` (`:327`) accepts `LegendCompileException`, `NotImplementedException`, `DialectCapability`, or an `UnsupportedOperationException` thrown from a dialect. Anything else aborts.
- **Close relative.** `com.legend.integration.ProductSqlMeasure measure <cases.jsonl> <out>`, run as `//core:product_sql_measure` (`core/BUILD.bazel:3202-3215`).
  - It already writes every statement's full text per case to `sql-<DB>.jsonl`, for all databases, under PRODUCT with the substring flag.
  - It is the nearest existing tool to this design, but it has no doors.

### Where the inputs come from

- **`channel_a.jsonl`** (2,451 lines, 43 distinct models, keys `model` and `expression`; checked in).
  - It is a snapshot of PCT channel A's unique cases.
  - It was captured by a since-deleted switch, `-Dlegend.capture.channela` (named in `ProductSqlMeasure.java:30`; it no longer exists anywhere in the tree).
  - It is never regenerated by a target.
  - Its git history is truncated: the file first appears in `605affa3` (2026-11-21). The design doc dates the set to 2026-11-12 (`docs/LEAN_PRODUCT_SQL_DESIGN_2026_11_12.md:882`).
- **`core.jsonl`** (4,399 lines: 872 model lines plus 3,527 query lines over 34 runtimes; checked in).
  - It was captured from `//core:core_tests_{integration,planner,server,root}` with `QueryCaptureListener` (`//core:query_capture`, `core/BUILD.bazel:3292-3305`).
  - That listener is a JUnit launcher listener. Under `-Dlegend.capture.queries=FILE` it installs a `planner.PlanningObserver` and appends `{"model","query","runtime"}` for every query planned from text.
  - The output was then deduplicated by model (`model_id`) by hand. 22 temp-file queries and 3 queries with a 1.2 MB payload were dropped (`LEAN_PRODUCT_SQL_DESIGN_2026_11_12.md:892-902`).
  - **`//core:query_capture_test` does NOT produce the set.** It tests that the capture records text only and changes no plan (`QueryCaptureTest.java`).

### Spec: corpus SQL sizes

- **Targets.** `//spec:lean_sql_corpus_{duckdb,h2}` (`spec/BUILD.bazel:246-255`) and `//spec:update_lean_sql_corpus_{duckdb,h2}` (`spec/BUILD.bazel:257-272`, `main_class com.legend.rcorpus.LeanSqlCorpusTest`).
  - The updater's data is `_INPUTS + UPSTREAM_TREES`.
  - Its jvm_flags are `-Drcorpus.backend=<lane>`, the engine and pure `rlocation`s, GMT, en_US, UTF-8 and `-Xmx4096m`.
- **Code** (`spec/src/test/java/com/legend/rcorpus/LeanSqlCorpusTest.java:46-82`):
  - `new MinimalCorpus()`, then for each `corpus.tests()`:
  - `Compiler.resolveQuery(List.copyOf(t.fn().body()), t.imports(), corpus.context())`
  - `UpstreamTestBodies.admitted(Compiler.queryResolved(...))`
  - `TestExecution.planBody(typed, MinimalCorpus.RUNTIME, options)`.
- **Options** (`:134-143`): `new ExecuteOptions(NoEdge.NONE, DataStores.resources(Corpus.RELATIONAL.getParent().getParent()), Set.of()).withJudgeMode(HOST).withStyle(PureText.UPSTREAM)`.
- **SQL text in hand.** `steps(plan.steps(), ...)` (`:93-124`) takes `Run` node statements (no Loads), `FrameRun.check().sql().statement()`, and Branch and Isolated sides. It skips `Verdicts`, the judge's steps.
- **How the database is chosen.** It is a static: `MinimalCorpus.BACKEND` from `-Drcorpus.backend` (`MinimalCorpus.java:487-492`). It is bound into the context's execution overlay (`:302-307`), so it takes one JVM per lane.
- **Caveat: this harness does not plan under the corpus's real door.** The real run uses `ExecuteOptions.recording(new CompatEdge(recorder, stores), stores).withStyle(PureText.UPSTREAM)` (`MinimalCorpus.java:599-615`). `TestPlanner` passes `options.edge()` into `TestDoor.planned(...)` (`testplan/TestPlanner.java:200-203`), so the edge can change the plan. The capture should use CompatEdge.

## 2. The five doors: how to plan the same input under each

These are the shared pieces for the query sets.

- **Model.**
  - For `channel_a`, use `Compiler.compileModel(TestBackends.named(lane).withStorelessRuntime(model))`. That is PCT's own `PctBackend.withStorelessRuntime`, `pct/.../PctBackend.java:66`, which is `StorelessRuntime.declaring(model, type, specificationAndAuth())` (`core/src/test/java/com/legend/testbackend/TestBackend.java:110`). It may differ from LeanSqlBaseline's `StorelessRuntime.with`.
  - For `core`, use `Compiler.compileModel(model)`.
  - Compile once per model and lane, then call `Compiler.query(ctx, text)` once per input. A `TypedQuery` is immutable: `withBody` and `withOptions` return new queries, so all doors can share one typed query.
- **Runtime.** `StorelessRuntime.RUNTIME` (`"storeless::Runtime"`) for `channel_a`; the line's own runtime for `core`.

| door id | its rewrite (exact calls) | style and features | source |
|---|---|---|---|
| `product` | none | `q.executionPlan(rt)`, which is PRODUCT with `Set.of()` | `Execution.java:43-47`, `TypedQuery.java:212` |
| `pct_pure` (channel A, legend-pure) | `q.withOptions(Set.of(PlanOption.DETERMINISTIC_AS_OF))`, then `PureComparisons.asPures(...)`, then `PrintedRelations.lift(..)`: if non-null, plan `lifted.relation()` | `executionPlan(rt, Set.of(), PureText.UPSTREAM)` | `PctPlanRoute.java:144-191` |
| `pct_engine` (channel A, legend-engine) | the same, with `EngineComparisons.asTheDatabases(...)` | `executionPlan(rt, Set.of(), PureText.PURE_V1)` | same |
| `pure_v1_plan` (generatePlan) | `PureV1Routes.checkMeaning(q, ctx, rt, null)`, which is `PureMeaningRewrite.rewrite(EngineComparisons.asTheDatabases(q), ctx, rt, null, PureMeaningRewrite::engine).query()` | `executionPlan(rt, Set.of(), PureText.PURE_V1)` | `PureV1Routes.java:262-289, 330-334` |
| `pure_v1_exec` (execute) | the same `checkMeaning` | `q.projectPlan(rt, PureText.PURE_V1)` | `EdgeServer.java:41-44`, `Execution.java:84-89` |
| `corpus` (on a query) | `UpstreamTestBodies.admitted(q)`, which calls `EngineComparisons.asTheDatabases` and then rewrites asserts | `executionPlan(rt, Set.of(), PureText.UPSTREAM)` | `UpstreamTestBodies.java:51-55` |
| `pct_b` (on a query) | `UpstreamTestBodies.admittedForPure(q)`, which is `admitted(asPures(q))` | the same, plus `DETERMINISTIC_AS_OF` | `ChannelB.java:409-412, 433-453` |
| `pct_lite` (optional) | `withOptions(DETERMINISTIC_AS_OF)` | PRODUCT | `PctPlanRoute` with `Audience.LITE` |

Notes on the table:

- **`checkMeaning` is package-private.** So is `PureMeaningRewrite.rewrite`, and both live in the `:edge` jar (`core/BUILD.bazel:481`). Add a small test-side bridge in package `com.legend.edge`, for example `core/src/test/java/com/legend/edge/CaptureDoors.java`:

  ```java
  public static TypedQuery pureV1(TypedQuery q, ModelContext ctx, String rt) {
      return PureV1Routes.checkMeaning(q, ctx, rt, null);
  }
  ```

  That keeps the product unchanged. The other option is to make `checkMeaning` public, which changes a main source. Every other call in the table is already public.
- **pure/v1 compiles from a protocol lambda,** `Compiler.query(ctx, ProtocolReader.lambda(...))`, not from text. Starting from the same text is an approximation of that route's front end, but it is exact for everything from typing on.

**Test-body doors** (`planBody`, in the spec tool, per corpus body):

- `corpus`:
  - Admission: `UpstreamTestBodies.admitted(typed)`.
  - Options: `ExecuteOptions.recording(new com.legend.edge.CompatEdge(new RawLedger.Recorder(), stores), stores).withStyle(PureText.UPSTREAM)`. The judge is HOST, the constructor's default (`ExecuteOptions.java:28-35`). `stores = DataStores.resources(Corpus.RELATIONAL.getParent().getParent())`.
- `pct_b`:
  - Admission: `UpstreamTestBodies.admittedForPure(typed)`.
  - Options: the same, plus `.withOptions(Set.of(PlanOption.DETERMINISTIC_AS_OF))`. This mirrors `ChannelB.COMPAT_OPTIONS`. Keep the corpus stores so CSV loads plan.
- `product`:
  - Admission: the body as typed.
  - Options: `new ExecuteOptions(NoEdge.NONE, stores, Set.of()).withJudgeMode(JudgeMode.BOTH)` under PRODUCT. This mirrors `ChannelB.LITE_OPTIONS` without the as-of option.
  - Expect many refusals by name. They are recorded, and that is fine.
- **Runtime-dependent read: `UpstreamPrints.read`.** Both the corpus and channel B, under compatibility rules, apply `UpstreamPrints.read(typed, facts.effects(), reads)` (`MinimalCorpus.java:629-633`, `ChannelB.java:417-425`). It runs a read on a session before the body is planned. A plan-only tool cannot do this, so the capture plans `admitted(typed)` without it (section 5).

## 3. The statement text, and what could make it differ between runs

- **The type that holds it.** `ExecutionPlan.Sql(String statement, List<Slot> slots, Target target, SqlQuery tree, List<Region> regions, String stamp, Map content, List<Site> sites)` (`executionplan/ExecutionPlan.java:739`).
  - `statement` is the final text with `?` placeholders.
  - `PlannedSql` (`Sql.planned()`) is what a session sends.
  - `RenderedStatement(sql, binds, regions, ...)` (`sql/dialect/RenderedStatement.java:24`) is the dialect's output before the plan is assembled.
- **Bound parameters are NOT in the text.** They are `slots`. The binding variants are `One`, `Array`, `Key`, `Source` and `Payload` (`ExecutionPlan.java:954`); they cover run-time parameters, keys, sources and `data:` payloads. Literals are inline in the text.
  - Hash the whole `PlanJson.write(plan)` too, because a slot's type or binding can change while the text stays the same.
  - The plan JSON does not write `tree` (javadoc at `:725-731`).
  - The test plan's JSON is `testexecutionplan.TestPlanJson.write(TestPlan)` (`TestPlanJson.java:134`). `TestPlanner` requires it to round-trip (`TestPlanner.java:217`).
- **Execution id and stamp are safe.** The execution id is a UUID minted at run time (`Execution.java:46` and so on) and bound (S304), so it is not in the plan. `stamp` is a parameter name.
- **Statement extraction.** Walk the JSON and collect each `"statement"` string in document order. `PctPlanRoute.statements` (`PctPlanRoute.java:247-267`) already does this. It catches every node kind, Loads and target session statements included, without a hand-written switch.

**Risks of drift between two runs of the same tree, highest first:**

1. **`identityHashCode` in a generated variable name.** `resolver/NavReducer.java:63,75` names a variable `"_e" + System.identityHashCode(...)` in the graph-fetch navigation reduction (called from `GraphEmission.java:2792-2798`). If that name reaches SQL as an alias, the text changes on every run. This is not verified.
2. **Iteration order of `Set.of` and `Map.of`** is salted per JVM. `NameResolver.java:2038-2045` records a past bug of exactly this kind. Any planning code that iterates such a collection into output drifts between runs. There are 58 `Set.of(`/`Map.of(` uses in `lowering/`. They were not audited one by one.
3. **Refusal messages** can embed `Object.toString()` identities or hash-ordered lists. Hash the message only after normalising `@[0-9a-f]{5,8}`, or keep the class separate from the message hash so a refusal-only difference can be told apart.
4. **JVM locale and timezone.** `//core:update_lean_sql_baseline` sets only `-Xmx3g`. Give the capture tools `-Duser.timezone=GMT -Duser.language=en -Duser.country=US -Dfile.encoding=UTF-8`, as `update_lean_sql_corpus_*` does.
5. **Order and cache effects inside one JVM:** the per-database compiled-model cache and the static `Census` counters. Keep the input order fixed (file order) and write the output sorted.

**Existing evidence of determinism:**

- `//pct:pct_channel_b_twice_<suite>` plans each channel B body twice in one JVM and compares the JSON byte for byte (`ChannelB.java:482-505`, `pct/BUILD.bazel:671-690`).
- `LEAN_PRODUCT_SQL_DESIGN_2026_11_12.md:889` says re-measuring reproduces every pin exactly. That only proves the sizes match, not the text.
- Neither covers two separate JVM runs. Hence the mandatory self-check: run twice and `cmp`. Optionally add a `--twice` flag that plans each input twice in-process and logs any mismatch.

## 4. Where the output goes (house pattern)

- **Runnable harness.** `legend_java_binary(testonly = True, tags = ["manual"], main_class = ..., data = [...], jvm_flags = ["-D...=$(rlocationpath ...)"])`, run with `bazel run`. `//core:update_cast_case_census` (`core/BUILD.bazel:3358-3370`) and `//spec:update_lean_sql_corpus_*` follow this pattern.
  - A path argument is resolved against `BUILD_WORKING_DIRECTORY`, as `CapabilityReach.arg` does (`core/src/test/java/com/legend/sql/dialect/CapabilityReach.java:145-148`).
  - That gives a tool output anywhere, never a golden.
- **Tests write to `$TEST_UNDECLARED_OUTPUTS_DIR`** (for example `OnePlanGuardTest.java:175`). The files land in `bazel-testlogs/<pkg>/<target>/test.outputs/` (`docs/GATES.md:116-117`). Use this only for the channel B hook.

## 5. Proposed files and BUILD rules

### A. `core/src/test/java/com/legend/leansql/SqlCapture.java` (new; in `lean_sql_baseline_lib` via its srcs)

```java
public static void main(String[] a) // usage: <out.tsv> [--databases=DuckDB,H2|all] [--twice]
// sets: channel_a (Runfile.property("legend.lean_sql.channel_a")), core (…"legend.lean_sql.core")
static String row(String set, String door, String db, String id, Supplier<Object> plan)
//   plan.get() is an ExecutionPlan -> json = PlanJson.write(p); stmts = statements(Json.parse(json))
//   -> "planned\t" + stmts.size() + "\t" + sha256(String.join("\u0000", stmts)) + "\t" + sha256(json)
//   catch RuntimeException | StackOverflowError e
//   -> (LeanSqlBaseline.isRefusal(e) ? "refused" : "error") + "\t" + e.getClass().getName()
//      + "\t" + sha256(normalised(e.getMessage())) + "\t" + first120(e.getMessage())
```

- **Doors** are the rows of the table in section 2, each a `Function<TypedQuery, ExecutionPlan>`.
- **Input id.**
  - `channel_a`: the 1-based line number plus the first 12 hex digits of `sha256(model + "\0" + expression)`.
  - `core`: the line number.
- **Database.**
  - `channel_a`: the lane looped over. The default is DuckDB and H2; `all` loops over `Databases.implemented()` filtered by `LeanSqlBaseline.relational`.
  - `core`: the plan's target, read on the PRODUCT door's plan, or `refused`.
- **Output.** Sorted lines, one header line `set door database id outcome statements sql_sha256 plan_sha256`, and a per-set and per-door count on stderr.

## 7. Expected size, coverage and cost

**Lines of output:**

- `channel_a`: 2,451 inputs × 7 doors × 2 lanes = 34,314 lines. With `--databases=all` it is 11 lanes, about 189K lines.
- `core`: 3,527 inputs × 7 doors = 24,689 lines, each on the query's own database. The PRODUCT pins show DuckDB 2,918, H2 427, SQLite 327, Postgres 147, others 40-45 each, and 28 refused (`baseline.tsv`).
- `corpus`: about 2,575 discovered bodies per lane × 3 doors, so about 7.7K lines per lane. The discovered count is from `docs/GATES.md:675`, an older measure.
- Total: about 75K lines, around 10-15 MB.

**Not covered, or covered only approximately:**

- `channel_a.jsonl` is a 2026-11-12 snapshot of channel A's cases. PCT cases added since then are absent, and the switch that captured it is gone.
- `core.jsonl` covers only queries compiled from model text and query text (`QueryCaptureListener` sees nothing else). It is missing the 25 excluded queries and any core test added since it was captured.
- **Work planned only at run time:**
  - `UpstreamPrints.read`, the printed relation read before a compatibility body.
  - Keyed-region expansion (`PlanRunner.expand`): the capture sees the template only.
  - The side a branch picks: the capture plans both sides as data.
  - The corpus's fixtures and setups: optional rows in section 5D.
  - The appeals' referee replays.
- **Corpus bodies.** The capture hashes the whole test plan: product statements (the body's `execute()` queries as Run and FrameRun nodes), judge verdict steps and loads. A change confined to the judge's SQL therefore shows up here, though the lean-SQL baseline excludes it.
- **Channel B** is covered only through the optional hook. It needs the upstream trees and the PCT harness.
- **PCT lanes other than DuckDB.** For channel A, the `all` option plans on every dialect with no database. Channel B on H2, Postgres and others is only reached through those lanes' own targets.
- **pure/v1:**
  - The protocol lambda front end is not exercised.
  - Routes with a mapping argument to `checkMeaning` (non-null `mapping`) are not exercised.
  - `parameterValues` binding is not exercised.
- **Other doors outside the five:** lite's own server routes, the `#SQL{}#`/`#IQ{}#`/`#Cypher{}#` islands, DataCube, and MongoDB (non-relational, excluded the way `LeanSqlBaseline.relational` excludes it).

**Cost** (from recorded timings; not re-measured):

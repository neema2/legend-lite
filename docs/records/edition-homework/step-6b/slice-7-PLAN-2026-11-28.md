## 0. The answer on one page

**The question:** today the code that turns a comparison into SQL asks which door the query came through. Where can
that choice be made instead: (a) in the type-checker, or (b) only in a pass after the store resolver?

**The answer: (a), the type-checker.** Three facts decide it, all measured over the whole relational corpus (DuckDB
and H2), PCT (channels A and B) and the edge tests, at each door (section 1):

1. **Every comparison that reaches the lowering was made in one of two places:** the type-checker (which sees the
   query, function bodies, Pure written in mappings, the relational mapping language's code and the comparisons test
   planning builds), or the store resolver. Nothing else makes one. On the DuckDB corpus: 35,947 by the type-checker,
   11,217 by the resolver, none from anywhere else; the same split in every suite (about 101,000 calls lowered with
   a door's table in all).
2. **"Mapping code is not read by the type-checker's hook" is not so.** Relational mapping code passes the same hook
   as everything else (`compiler/spec/Typer.compared`); the hook returns early there on purpose, because the question
   it asks today is only "is this a comparison across types". 23,212 such calls on the DuckDB corpus carried the
   hook's mark.
3. **The comparisons the resolver writes itself do not need the door.** For every one of them (11,217 on DuckDB,
   11,063 on H2, 218 in the edge tests) lite's own rule and the door's rule write the same SQL. The door's rule
   changes the SQL, or lifts a refusal, for 69 calls on the DuckDB corpus (67 on H2), for 4 in PCT's legend-engine
   run and for none at legend-pure's door, and every one of those was made by the type-checker.

**How it is carried: a small mark on the call, written by the type-checker ("which comparison this call is"), not a
twin function.** The reason is not cost alone: about a hundred places between the type-checker and the lowering
recognise a comparison by its function (the resolver rewrites a comparison the program wrote into an `EXISTS` 119
times on the DuckDB corpus), and each must go on treating a door's comparison exactly as lite's. A twin function swapped in by the
type-checker breaks every one until it is taught; a mark breaks none, and a new constructor argument makes the
compiler find every place that rebuilds a call. Section 3 lists what each choice touches. This is the one point where
the edition design as written ("ordinary typed calls") has to change, and it is the user's to rule (question 1).

**The spike** (section 4) does exactly this for all ten comparison families and removes the comparison rows from
both doors' tables. **Result, against the baseline:** every suite passes as before except one edge test that asserts
the very rows the spike deletes. Of about 119,000 statements compared, one moved: in
`meta::pure::tds::tests::extensions::iqrClassifyTest` (DuckDB) the same query is written with its table aliases
renumbered, the one case the probe had predicted (1.6, item 3). The recorded edge files regenerate byte-identical,
and lite's own measure pin holds.

**A question that comes before all of this (question 0):** does the lookup need to leave the lowering at all? The
lookup itself is a clean seam (a table of rule names, asked where a rule is picked) and is the only place that can
serve the rows that need the stamp and the database. What is wrong today is around it: the door's rule is a flag
threaded through lite's equality (nine of its ten branches), the lowering asks in five places and asks a second
question, and it guesses. That is fixed the same way whichever answer the user gives (slice A1). Moving the choice
to the type-checker buys meaning that follows the code and a call that cannot reach the wrong lowerer; it is needed
only if editions per project are a real goal.

**What the next session builds:** section 5, in two parts: the cleanup both answers need (A1, and A2 if the lookup
stays), and the move to the type-checker (B1 to B4), each slice with its test, its guard and what to do if SQL
moves. The three pins of `ComparisonDoorReadsRatchetTest` reach zero after part B; after A2 alone they read 4, 0, 0.

**What goes to the user:** eleven questions (section 8.1). The ones that matter most: whether the choice moves at all
(question 0), the mark instead of a twin function (question 1), and three things this pass found that no earlier note has (section 1.6): core tests that plan
in a compatibility style a query typed with lite's setting, a second place in the type-checker that makes a
comparison without passing the hook, and a trial lowering that reads door code with lite's table.

Measured (1.5): over every suite run, only 1 and 4 ever changed a statement outside lite's own unit tests of the
doors' rule.

### 1.6 Three things found that no earlier note has

   things at two moments: a comparison setting to the type-checker (`TypedQuery.comparing`: `edge/EngineComparisons`,
   `edge/PureComparisons`) and a plan style to the planner (`TypedQuery.plan(runtime, style)`:

## 2. The decision

**(a): the type-checker chooses, for every comparison it types.** A comparison the resolver writes for the store is
the store's own and keeps lite's function at every door. One the resolver derives or rebuilds from a comparison the
program wrote carries that comparison's choice, as it already carries its stamp.

**The facts that decide it** are the three of section 0. In the words of the two reasons given for (b):

- *"Mapping code is not read by the type-checker's hook."* It is read. Relational mapping code is typed by the same
  per-query type-checker, minted at the same place and handed to the same hook; the hook's state for it is `UNREAD`
  and it returns the call (**read:** `Typer.bodyOf`, `Typer.compared`; **run:** 23,212 calls with the hook's mark
  `UNREAD` under legend-engine's setting on the DuckDB corpus). Pure written in a mapping (M2M, `~func`) is typed as
  a body (`BODY`).
- *"The resolver writes its own comparisons."* True, in 14 sites met and 2 more read. They do not need the door: 0 of
  22,498 differ. By reading, they could differ only as an `equal` in a value position inside a store query with
  exactly one optional side, or over a mixed list or a date built to the hour; none of the resolver's sites writes
  such a one in any run (table 1.3a: its equalities stand as the mapping's own `=` or as a positive condition; the
  two `equal` rows with a value position, `ChainNormalizer`'s, are stamped outside a store).

**Why not (b), a pass after the resolver keyed on the function:**
- It moves the read from the lowering to the planner; the planner would hold the door's map at every hand-off to a
  lowerer (five constructions: `Compiler.lowerResolved`, `planner/ProductStatements.configured`,
  `planner/BodyPlanner`, `lowering/SeedableLets`, `edge/EnginePlans`; and `planner/PlanMaker.count`, which restyles
  one; **read**). "Nothing
  after one early point" would still be false.
- It decides by run, not by code. The edition design's point is that meaning follows the code (a lite project that
  calls a legend-engine library must be able to keep both meanings); after the resolver every function is expanded
  into one tree and whose code a comparison was is gone.
- It is not needed: the only thing it catches that the type-checker does not is the resolver's own comparisons, and
  those are the same under both rules.

(b) is the safest for "no SQL moves", because it reproduces today's lookup by id exactly. It is the fallback if a
slice of section 5 meets SQL that moves and cannot be explained (section 5, "if SQL moves").

**What would falsify (a):**
1. a comparison reaching a door's lowering that was made by neither the type-checker nor a listed resolver site
   (the probe's "made by" column shows any other);
2. a resolver-made comparison for which the two rules differ (the probe's difference column; by reading: a resolver
   `equal` in a value position inside a store with one optional side);
3. a real door that types a query under one setting and plans it in another's style (1.6, item 1);
4. the trial lowering changing its answer (1.6, item 3).
1 and 2 were looked for over about 101,000 calls and not met. 3 exists only in lite's own tests. 4 was met once
(1.6, item 3).

**Is the edition design, as written, achievable for comparisons?** Its mechanism is: yes. Its two sentences need
amending, and both go to the user (section 8.1):
- *"turns each edition-dependent construct into ordinary typed calls that mean the same in every edition"*: for
  comparisons the choice is a mark on the call, not another function (section 3).
- *"nothing after the typer can see it"*: true after this slice for which comparison a call is. Not true for where a
  call runs: legend-engine's empty side depends on the stamp (`TypedNativeCall.outsideStore`), which the planner sets
  after typing, and only because the door asks (`planner/ProductStatements.prepared`, `BodyPlanner`, `FramePlanner`:
  six of the nine reads `ArchitectureTest.EDITION_READS` lists). The mark says "the empty side by where the call
  runs"; the stamp says where. Slice 7 does not remove those reads.
- The package the design names, `compiler.spec.edition`, does not exist. What exists and already is "the door's rule
  inside the type-checker" is `compiler/spec/CrossTypeRule` with three implementations
  (`compiler/spec/LiteCrossTypeRule`, `edge/EngineComparisons`, `edge/PureComparisons`), handed in by
  `TypedQuery.comparing`. The plan extends that; it does not build a second thing.

### 3.2 Why M, said plainly

- **A door's comparison and lite's are the same thing to every pass but one.** The inliner's folds, the resolver's
  rewrites and the planners must treat `upstream equal` exactly as `equal`: the resolver's `EXISTS` rewrite of a
  user's `contains` (`Substitution.rewriteCallArms`, `rewriteMembershipExists`) fired on 79 door-typed calls on the
  DuckDB corpus alone (**run**, table 1.3a). A twin is a different function to all of them, so each must be taught,
  and a missed one is a silent change of SQL or of answer at a door. A mark changes nothing for them.
- **The compiler finds every carrier.** The node's five-argument constructor goes; each of the 19 hand rebuilds then
  fails to compile until it passes the reading of the call it was given. `NativeCallStampGuardTest` (which pins every
  construction that carries no stamp) is extended to the reading.
- **One bit serves 74 functions.** The doors' rule is one reading of ten families; declaring 11 to 75 functions to
  say it is the wrong size.
- **Plan handle ids do not move.** The mark is left out of the node's printed form and hash, as the stamp is where it
  is false, so `PlanRows.scopeId` and anything else keyed on a tree's text is unchanged. A twin's name cannot be left
  out.
- **What M costs:** the call is not "an ordinary call that means the same everywhere": its meaning rides beside its
  function. That is already true of the stamp. The honest wording for AGENTS.md is in question 7.

**If the user wants function identity all the same:** the cheapest sound form is M from the type-checker to the
lowering and, inside the lowering only, `Scalars.RULES` keyed by the function and its reading. Nothing before the
lowering changes; it is slice B4 of section 5 either way. Twins swapped in by the type-checker (about 175 recognisers)
is two to four more days and the riskiest; twins swapped by a pass after the resolver is the half page's proposal and
brings back (b)'s defects.

**The orderings under T, not proven:** lite's four `Any`-typed orderings share the rule the 64 overloads have
(`Scalars`' registration loops over both families) and are not read by `HeldKinds`, so they look like the door's
ordering already. But `Scalars.lower` reads a mixed selection's winner as its comparable for both families
(`ORDERINGS`), and the door's row skips that step (`threeNumberTypesAndWrittenDatePrecision` calls the rule
directly). Whether that step ever matters at a door was not met in any run and was not read to the end.

## 5. The plan, in slices

**The acceptance rule, fixed by the user:** no answer and no SQL text at any door may change; lite's own measure
(`bazel run //core:equality_measure`, and `//core:equality_positions_pin_test`) stays as it is; the pins in
`ComparisonDoorReadsRatchetTest` go to zero. (The user has since asked whether the lookup needs to leave the
lowering at all: question 0. If it stays, the first pin's zero is the one part of this rule that changes.)

**How "no SQL text" is checked in minutes, at every slice** (a temporary probe, not a harness): apply
`slice-7-probe-2026-11-28.patch.txt` on the slice's base and on the slice, run the suites of section 1.2 on each, and
compare the per-test digests (`s7probe-sql-*.tsv`: the test, how many statements, their length, one SHA-256 of their
texts in order) with `diff`. Appendix A has the commands. The recorded files (the corpus's rosters and ledgers,
`//gates:edge_net`, the lean-SQL pins, `//core:lean_sql_baseline_test`) are the second net and run in the slice's
full round.

**If SQL moves at any slice: stop, do not re-record.** Run the moved test alone with the probe
(`bazel run //spec:corpus_one -- <duckdb|h2> host <test>`; `--test_filter` for a core or PCT test); the probe's
"made by" and "difference" columns say which call and why. It is one of four things:
1. a rebuild dropped the reading (a construction that builds a call again from one it was given and does not pass
   its reading): fix the carriage;
2. a query typed under one setting was planned in another's style (1.6, item 1): the test is typed under its style's
   setting; a real door doing so is a defect to bring to the user;
3. a resolver-made comparison for which the two rules differ: bring it to the user with its position and both SQLs
   (question 2 decides it);
4. the trial lowering (1.6, item 3) answered differently: bring it to the user.
If it is none of these and cannot be explained in an hour, fall back to (b) for that slice (the reading written by one
pass over the tree in `planner/PlanEnv.configure`'s callers, by the function's id) and say so.

The slices are in two parts, because of question 0 (section 8.1): **part A is the cleanup both answers need; part B
moves the choice to the type-checker.** If the user keeps the lookup in the lowering, the work is A1 and A2 and the
first pin stops at 4, not zero, with the acceptance rule re-worded by the user. If the choice moves, the work is A1,
then B1 to B4, and all three pins reach zero.

### Part A: the cleanup

#### A1: two whole rules; `NumberFamilies` is deleted (both answers)

- **Files:** `lowering/Equalities`: `equal` is the product's rule, whole (the Nil-list answer, the written empty

## 7. How a door's behaviour reaches test planning

**Today** (**read**): three channels.
1. The plan style's facets, asked during planning: `testplan/EngineTextGates.facet` > `PlanStyle.facet(EngineTestText.class)`
   > `edge/EdgeEngineTestText`. **run** (grep): `testplan` reads the plan style 27 times and `planner` 24
   (`.facet(`, `.twoForm(`, `judgesEngineText()`, `.style()`).
2. The `Edge` a harness hands the test door (`testexecutionplan/Edge`, through `ExecuteOptions.recording`): records
   planned as data (`testexecutionplan/Extension`) and calls back at run.
3. The typed body rewritten at the door before planning (`edge/UpstreamTestBodies.admitted`, `admittedForPure`).

**What slice 7 settles.** A comparison test planning builds (an assert as the comparison it means) is typed by the
query's own type-checker (`SpecCompiler.comparedAsInAQuery`), which holds the door's setting. After slice B2 it
carries the door's reading like any other. So for comparisons, test planning never asks a door: it asks the
type-checker the query came with. That is the pattern for everything else: **the door's choice enters once, at the
type-checker; later stages receive typed code and data.**

**The SQL-text assert stays as it is through slice 7.** `EngineTestText.plan` does planning work under the door's
style (it plans the producer's query to legend-engine's SQL text through another facet, collects texts, numbers an
appeal); it is not a recognition that can be written into the typed tree. It is test machinery, and moving it out is
step 9's. Slice 7 removes none of the 27 and 24 reads; it should pin them (a ratchet at today's counts) so they only
shrink.

**A printed assert does not need a second facet, and is not slice 7's.** It belongs to step 8 (re-specified), and
should use channels 3 and 2, not 1:
- the door rewrites the printed side on the typed body it receives into a call of one test function lite owns
  (the unprinted table or value, the print's name, its literal replaces, lines in order or in any order). The step 8
  session reports that recognition reads only the typed body, its lets and its order view (a lead: 8.2);
- test planning plans that function as a side fetched as typed rows, with a judgment that is core data naming the
  print (not an edge class: `testplan` cannot construct one);
- at run, `testexec` hands the typed rows and the columns to the `Edge` the harness gave it, which prints and
  compares. Nothing between the door and the judge knows a door.

What that needs from slice 7: nothing but the rule above (no new facet), and that `comparedAsInAQuery` stays the one
way a call built after typing meets the door's setting. What is open in it is step 8's (8.2): a side shaped as an
`execute()` frame as a host side; the 111 asserts whose recorded kind would change back; helpers that print inside
their own body, which a rewrite of the test body does not reach (it does not reach them today either).

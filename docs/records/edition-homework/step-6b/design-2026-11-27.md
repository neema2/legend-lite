## 0. In one page

**The promise.** One piece of code decides whether two values are the same, wherever the comparison stands, and a
test's assert is that same comparison. Step 6 ("A") delivered the rules and one code for two whole sides; it left a
second code for two single values and a third around them, the test checker's own.

**Why there are three today, in one sentence each.**
- A comparison inside a row is an SQL expression (`lowering.Equalities`, about 480 lines, plus the rules for `in`,
  `contains`, `indexOf`, `removeDuplicates` in `Scalars` and the mixed lists in `TaggedLists`).
- A comparison of two computed lists, maps or tables is a statement over each side's rows
  (`lowering.SideEqualities`, about 2,150 lines, which WAS the test checker's code and was moved, as it stood).
- The test checker plans most asserts itself (`testplan.DatabaseJudge`, `lowering.VerdictSql`, `CanonRider`,
  `JudgmentFacts`: about 3,000 lines), reaching the second code by its own door and adding its own forms for
  "contains", tolerance, each element of a `forAll`, and the record of what failed.

**What they share and do not.** All three answer the same question for one PAIR of values: "these two, of these
types, held this way on this database: the same?" Each answers it in its own words. That is where every measured
disagreement comes from (a Decimal by its spelling in one and by its number in another; a year as text in one and as
a number in another).

**The design.**
1. **One element rule.** A single table says, for each kind of value and each way a database holds it, what is
   compared. Every comparison of two values goes through it: `==` in a row, each pair of a list, each cell of a
   table, each key of an instance, each channel of a mixed list, membership, deduplication.
2. **One layer for shapes** (a list in order, a list in any order, a map, a table), built on the element rule. It
   exists already (`SideEqualities`, the planner's `RootComparison`); it loses its own copy of the element rule.
3. **An assert is the comparison it means.** The test planner turns `assertEquals(a, b)` into the product's
   `a == b` and plans it like any query. The pattern exists for two asserts already. The test checker's own
   comparison code is deleted. Where the product cannot plan a comparison, the database checker says "not judged
   here" and the Java checker judges alone; each such form is listed and the list may only shrink.
4. **The failure's record is read only when an assert fails**, by two more statements (each side as a query), so no
   comparison carries record columns.

**How "done" is checked, by tests that can fail** (section 6): the measure reads zero outside named refusals; a
ledger of comparison codes reads its target; the test planner cannot reach a comparison builder; the deletion list is
gone; the product's SQL size does not go up.

**Size.** About 2,000 to 2,500 lines deleted, about 600 to 900 written; five slices, each verifiable alone;
my estimate is six to eight working days with their verification, not a promise until slice B1 has shown how many
tests the Java checker catches the product on (section 7).

**Yours to rule** (section 8): four decisions.

- **A failed assert's record rides in the verdict's row** today: column 0 the verdict, columns 1 and 2 each side's

## 2. The design

### 2.1 The element rule: one table

**One class** (working name `lowering.SameValue`; it replaces the comparing parts of `Equalities`) with one job:
given two sides, each a Pure kind (or "known only when the query runs"), the SQL that holds it and the fact of how
it is held, write the SQL that says whether the two are the same value, or refuse by name.

It works by a **normal form**. For each kind family there is one typed form in which the database's own `=` is
value-exact; the rule reads each side into that form and compares. A side already in the form is left untouched, so
the SQL of an ordinary comparison (`$x.name == 'a'`, two integer columns) does not change by a character.

| Kind | Normal form | Sides read into it |
|---|---|---|
| Integer, Decimal (exact numbers, one family) | the database's exact numeric type, wide enough for both | a Decimal held as text; a number inside a JSON list |
| Float | the database's double | a Float literal written as a decimal (three databases: recorded) |
| String, Boolean | as held | — |
| Enumeration | its stored value, compared in the store's own space | a decode chain; a mapping's cast |
| A day | the database's date | — |
| A date-time | its instant, a timestamp | one held as the text it prints; SQLite's text |
| A year, a year-month | the text it prints (no database has a type for it) | — |
| A kind known only when the query runs (`Number`, `Date`, `Any`) | a tag naming the family, and that family's form | a mixed list's channel; a JSON value by its JSON kind |
| An instance | its run-time class, then each key by this table (or its identity) | — |

**Different families are never the same**, decided from the two sides' facts where they are known and from the tags
where they are not. The side still has to be evaluated (it may raise): one typed node says "evaluate these, then
false", written by each dialect, in place of today's casting of each value to text behind a mark
(`Equalities.neverEqualButEvaluated`, which the architecture review flagged).

**What it is given beside the two sides**, as data and nothing else:
- the door's policy for numbers (two families, or three types) and for a date's written precision (part of the
  value, or not): today's `NumberFamilies` enum and the doors' date rule, as one small record. The doors pass
  theirs through the table they already have; the rule never asks who is asking;
- whether the comparison stands as a positive condition (the empty-side rule's one input, as today).

**The same table gives two more things**, so they cannot drift from it: the KEY a value is deduplicated, grouped or
looked up by (`removeDuplicates`, `distinct`, `in`, `contains`, `indexOf`: one form per value, stronger than a
pairwise test), and the key it is ORDERED by (the orderings, sort ties, the extremes).

**What is deleted by it:** `Equalities.equal`'s branches for partial dates and text-held dates; `SideEqualities`'
`kindKey`, `EXACT`, `DATE_KINDS`, `besideDecimals`, `instants` and their helpers; the per-channel comparison in
`TaggedLists`; `HeldKinds.readsAs` (a copy of the type-checker's literal rule, and the cause of one known
difference); `Lowerer.computes` (a copy of `LiteCrossTypeRule.harmless`); two of the three copies of the list of
comparing functions.

### 2.2 The shapes: one layer over the rule

A list in order, a list in any order, a map (its entries, whatever order they were written in), a table (its
columns by name, then its rows), a mixed list. This layer exists; it keeps its statement forms and loses every
line that decides how two ELEMENTS compare, which become calls to 2.1.

Two ways it is reached, as today, by one seam (`lowering.WholeComparisons`, which the planner implements):
- **as a statement**, where each side can be planned on its own (a query's answer, an `if`'s condition, an assert);
- **where the comparison reads the row it stands in**, as an expression over the two list VALUES, each element read
  into its normal form first, on a database that holds a list as a typed value. Where a database holds a list as
  text or not at all, it is refused by name. Building list forms for those databases is the database follow-up's
  (its row D8), not this step's.

**Added here, because asserts need them and the product should have them anyway:** membership of one value in a
whole side, and "every element of this side is in that one" (`contains`, `in`, a `forAll` of `contains`), planned as
statements over rows by the same seam. Today only `==` and `hasSameElements` are.

**A side written in the query** (a literal list) is treated as a whole side wherever its elements are not in their
normal form as the database holds the list (a Decimal in a JSON list). Today every written side is left to the
database's own list comparison, "which reads it exactly": measured false on H2 and SQLite.

### 2.3 An assert is the comparison it means

For lite's own door, with the database checker:

| Assert | The product expression it becomes |
|---|---|
| `assertEquals(e, a)`, `assertNotEquals` | `$a == $e`, `!($a == $e)` |
| `assertEq`, `assertNotEq` | `eq($a, $e)` and its negation |
| `assertSameElements` | `hasSameElements($e, $a)` |
| `assertContains`, `assertNotContains` | `$a->contains($x)` and its negation |
| `assertEqWithinTolerance(e, a, t)` | `abs($a - $e) <= $t` (spelled so already inside a `forAll`) |
| `assertEmpty`, `assertNotEmpty` | `$a->isEmpty()` and its negation |
| `assertSize` | `$a->size() == n` (as today) |
| `assert`, `assertFalse` | the condition (as today) |
| an assert inside `forAll` | the `forAll` of that expression |

The expression is typed by the type-checker's rule like any `==` a query's author wrote (so two different known
types are a compile error at the assert, as the user ruled on 2026-11-26), and planned by the product's one road.
The verdict is that query's one Boolean.

**Where the product refuses the comparison, the database checker reports "not judged here"** and the Java checker
judges alone, as the two already do for several forms. Each such form is a line of a list that may only shrink.
This replaces the checker's own forms for: a table's cells against a flat list; sides on two databases; a constant
the host holds; kinds the checker's gate could not place.

**Stay as they are, because they are not equality of two Pure values:** JSON-document equality
(`assertJsonStringsEqual`), TDS equivalence with its tolerances, `assertInstanceOf`, `assertIs` (identity),
`assertError`. Each keeps its own named form; none calls a comparison builder.

**The record of a failure** (what was expected, what came): two statements, each side planned as the query it is,
placed in the test plan as steps that run only where the verdict is false (the plan already has such steps). For an
assert inside a `forAll`, a third names the first element that failed. So a passing assert sends one statement with
no record columns, and the comparison code carries no record plumbing (`Compared.alone`, `Held`, `VerdictSql.typed`
and `typedRow` go).

**What is deleted by it** (the map's section 6, re-read before each is removed): `DatabaseJudge.databaseVerdict`,
`gridColumnPair`, `databaseContains`, the forAll-contains branch, `databaseTolerance`, `databaseEmpty`,
`ARM.perElement`; `SideEqualities.contains`, `containsInstances`, `containsTagged`, `subset`, `perElement`;
`VerdictSql.typed`, `typedContains*`, `typedSubset`, `typedPerElement`, `typedTolerance`, `typedEmpty*`, the record
columns and the canon-text machinery; `JudgmentFacts.typedPair` and its kind gate; `CanonRider`; the equality arms of
`AssertVerdicts.adjudicate`.

### 2.4 The doors

- The doors' rows for the comparing functions stop REPLACING the product's rule and instead hand it their policy
  (2.1). One rule, two policies as data. `HeldKinds` and the whole-side plan then need no "is there a door row?"
  test; the door's policy says whether a column-type refusal applies.
- The doors' test checker stays the Java one alone (the user's rule).
- **Not in this step:** moving a door's meaning of `==` into the type-checker as its own typed call, so that
  nothing after it sees a door at all. That is the edition program's own later step; 6B leaves the door mechanism
  no wider than it found it and makes it narrower (one record of policy in place of a replaced code path).

## 3. What 6B does not do

- List forms for databases that have none (H2, and lists read per row on SQLite, MariaDB, MySQL): the database
  follow-up. 6B refuses by name there and never compares texts.
- SQLite's date-times as text, MariaDB's and MySQL's trailing-space comparison, text ordering by collation, a Float
  literal held as a decimal: each an open row of its own, older than step 6. The element rule gives each ONE place
  to be fixed; 6B fixes SQLite's date-time comparison only if it falls out of the date-time row at no extra cost.
- The Java checker. It is the one comparison in Java the tenets allow, kept independent on purpose: it is what
  shows a product bug as a disagreement.
- Presentation (step 8) and the test machinery's move out of the product (step 9's bulk, which follows 6B because
  it edits the same assert files).

## 6. Done means (each a check that can fail)

1. **The measure** (`tools/equality-measure/run.sh`): no body answers differently as an assert and as its plain
   comparison, except where both refuse with the same words; run on DuckDB, H2 and SQLite; a gate, with its list
   empty of anything else.
2. **The ledger of comparison codes** reads: one element rule; one shapes layer; the Java checker; and the named
   forms that are not equality (JSON documents, TDS equivalence, identity, instance-of).
3. **The test planner cannot build a comparison**: an architecture rule that `testplan` reaches the comparing
   classes only through the planner's entry for a query, and that `VerdictSql` holds no comparison form.
4. **The deletion list is gone**, and the product's own code is smaller than at A (A added about 3,150 lines
   against the pull request's branch).
5. **SQL size**: no product row up; the test checker's SQL on PCT down (no record columns on a passing assert).
6. **Every gate**: CI on every operating system, the database lanes, the review of each slice.
7. **The program's landing step** checks 1 to 3 before anything of step 6 goes to `main` (written there already).

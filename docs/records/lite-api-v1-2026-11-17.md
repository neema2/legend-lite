## 1. What we keep

- **Pure text**: models and queries, as people write them.
- **The V1 protocol trees** (`PureModelContextData`, a lambda's JSON) are lite's own protocol, unchanged. A query travels as its tree, a model as its text.

## 2. The operations: two things, the model and the query

| Operation | Request | Answer |
|---|---|---|
| `model/check` | `{model}` | `{errors: [{kind, message, where}]}`, empty when it compiles. Every error is listed, not only the first. |
| `model/elements` | `{model}` | `{elements}`: the model's protocol elements (data spaces, enumerations, a library's check). |
| `query/parse` | `{text}` | `{query}`: the lambda's tree. Numbers stay exact. |
| `query/print` | `{query, style?}` | `{text}`. `style` is `pretty` (the default) or `standard`. |
| `query/type` | `{model, query}` | `{columns: [{name, type, enumeration?}]}`. `type` is a Pure type name. |
| `query/plan` | `{model, query, runtime}` (the runtime always required: ruled 2) | `{plan}`: lite's plan, which is data: SQL, its parameters' slots and its columns. |
| `query/run` | `{model, query, runtime, params?}` (the runtime always required: ruled 2) | `{columns, rows}`, or Arrow IPC for large results. `params` are bound at run, typed by their declared Pure types. An aggregation-aware query (S361) answers its SQL activity alone (ruled 7, option (a)). |
| `model/createClass`, `model/createAssociation`, `model/createDataSpace` | the action's request | `{changes}`: DataCube's model edits, the files to write in the SDLC's change shape. |
| `ts/item`, `ts/statement` | `{text}`, `{model, query}` | A `#TS` item's text and tree; a `#TS` query as its one statement. |
| `queries/...` | as today | The saved queries and DataCube's saved pages: the same store and the same records, at lite's own route. |
| `user` | none | The current user, from the store. |

Each operation is one call: one planning step, plus at most one run. Nothing is held across calls except a `query/run`'s own transaction.

## 3. One error shape

Every refusal, on every binding, is `{kind, message, where?, raise?}`:
- `message` is lite's own words.
- `where` is a position or a site, where there is one, and nothing else.
- `raise` is given for a `data` refusal alone: the raise's kind, one name of a closed list, spelled in lower camel on
  the wire as every wire name is (`divideByZero`, `indexOutOfBounds`, `sizeNotMultiplicity`,
  `parameterFractionNotKept`, ...): the one catalog's run-time kinds (`error.ErrorKind`, those `isRaise` admits), whose
  enum spelling in the code is internal.

**Amended 2026-11-21 (stage B's BE, the one error model; for the user's word at the BE PR).**
- **`where`.** A `data` refusal's `where` is the raise's position in the query, `[line:col]`, as a compile refusal's is
  (the user's call that day: "what is the expert right thing to do", then "Okay"). Until then it was the site's fixed
  text, which repeated the raise's facts. A raise with no position in the query answers no `where`: one a guard writes
  rather than a call of the query (a `toOne` over rows, a cast's check, a frame's bound, the size and width checks).
  Named details in the answer come after BE.
- **The `raise` names.** The catalog split two kinds, so their wire names changed: `valueNotHeld` became
  `inverseTrigNan`, `parsedNanNotHeld`, `notFiniteNotHeld`, `datePastYears`, `dateOutsideYears` and
  `mixedRankInexact`; `fractionNotKept` became `parameterFractionNotKept` and `secondFractionNotKept`. A client matching
  the old names no longer matches.

**Amended 2026-11-23 (item 3's S6; the user's Q-C = C1 and Q-S6).** An assert inside a function's body that fails with no
message of its caller's is now a raise of its own: a `data` refusal with `raise` `assertTrue` (assert, `fail()`, and the
guards whose sentence would print values: assertEquals, assertNotEquals, assertEmpty), `assertFalse` or `assertNotEmpty`,
its `message` the assert catalog's sentence ("expected true, got false", ...) and its `where` the assert's position.
Until then it carried neither `raise` nor `where`, its message the plan's text. A failure with the caller's own message
keeps that message and still carries no `raise`.

| `kind` | Meaning |
|---|---|
| `parse` | the text does not parse |
| `compile` | the model or query does not type or compile |
| `unsupported` | a construct lite refuses by name (not yet, or by a ruling) |
| `data` | a run's raise: division by zero, an index out of bounds, a size not matching its multiplicity, ... (its kind in `raise`, its site in `where`); the database refusing the work in its own words, a load's file larger than the load admits (no `raise`) |
| `parameters` | a run's parameter values: one missing, or one its declared type does not take (the caller's values, neither data nor a defect; ruled 6) |
| `request` | the request itself is malformed: a key it does not read, a wrong type, JSON nested deeper than 4096 levels (ruled 3) |
| `notFound` | a saved query or saved page the request names does not exist (the user, 2026-11-17 ~23:31) |
| `internal` | a connection that could not be opened or was lost (no `raise`); anything else: a defect, said as one |

A run's failure that is not a raise (ruled by the user 2026-11-18 (PR #118): DATABASE_ERROR and FILE_TOO_LARGE answer
422 `data` with no `raise`; CONNECTION_ERROR answers 500 `internal`): the database
refusing the work in its own words is `data` (422) with no `raise`; a load's file larger than the load admits is `data`
(422) with no `raise`, its path in `message`, not in `where`; a connection that could not be opened or was lost is
`internal` (500), with no `raise`: the environment, not the caller's query. A raise's `where` is its position in the
query, where it has one (amended 2026-11-21, above).

A request is read the same way on every binding, by the one road's reader (`LiteV1Api.read`): JSON nested up to 4096
levels deep (a grid's query nests far past 64), anything deeper refused, kind `request` (2026-11-17: the browser's
binding read at 64 until step 2c, a stray limit; the suite holds a 40-deep tree, and no case at the limit itself,
which Python's own JSON reader of the suite could not read).

There is no `PARSER`/`COMPILATION`, no `code: -1`, no `status: "error"` envelope, and no `errorType`. Over HTTP the status follows the kind:
- 400 for `parse`, `compile`, `unsupported`, `request` (ruled 3) and `parameters` (ruled 6);
- 422 for `data` (ruled 1);
- 404 for `notFound` (the user, 2026-11-17 ~23:31);
- 500 for `internal`.

## 4. Typed results; parameters bound at run

- A result's columns carry their Pure types.
- Cells are typed values:
  - an Integer is ALWAYS an exact JSON number (a cell's JSON type never depends on its value), written exactly by the
    server and read exactly by each of the three bindings; the conformance suite carries 2^63-1 on all three (ruled 7);
  - a Decimal is its exact text (ruled 7);
  - a Float is a double;
  - a DateTime is ISO UTC with `Z` (S312);
  - StrictDate, Decimal, String, Boolean, null;
  - lists and structures typed.
- No legend-engine or legend-pure spelling appears in a product answer.
- A query's parameters are declared in the plan and bound at run, never pasted into its text. Their values are
  `string | number | boolean | null` or a list of them, checked against the plan's declarations (Java's PlanParameters,
  TypeScript's checkParameters, one rule). An Integer parameter takes the 64-bit range on every host: Java a `Long`;
  Python an `int` (a `bool` refused); TypeScript a safe-integer number or a `bigint` (an unsafe number refused by name).
- `query/run`'s answer is JSON rows for a page of results, Arrow IPC (typed columns) for large ones: the binding chooses
  by the caller's ask (`format: json | arrow`), never by guessing (ruled 7).

## 5. One contract, three bindings, one suite

| Binding | Form of each operation |
|---|---|
| the browser (the planner module) | one export per operation |
| the server, `/api/lite/v1/...` | one HTTP POST per operation, JSON in and out |
| Python | one native entry per operation, and one public function per operation in `legend_lite` |

- Each binding is a thin layer over the same product operation (planner `Boundary`, core's routes). No binding adds logic.
- **One conformance suite** of cases (request in, answer or refusal out) runs on all three bindings, the same way the raise-envelope fixture is read today by Java, the tab and Python.
- **A run's parameters** are one shared fixture of `(declared, values, outcome)` cases beside
  `engine-client/test/fixtures/raise-envelopes.json`, read by the Java, TypeScript and Python tests: each value bound,
  or refused by name with the `parameters` kind.

## 6. legend-engine: an opt-in module, chosen by configuration

**One server for now (ruled 6; splitting is a follow-up):**
- one artifact serves lite's routes and the edge's legend-engine routes;
- the product's routes import nothing from the edge;
- the edge mounts its routes as a module of its own;
- a boot test with the edge module off proves lite's routes answer and legend-engine's are absent.

The split later is one more main class.

**Configuration:**
- The app's configuration names its engine:
  - `engine: lite` (the default);
  - or `engine: legend-engine` with a `url`.
- Choosing legend-engine loads the compat module: the legend-engine client, the edge.
- It is **never a fallback**: an app on lite never asks legend-engine, and an app on legend-engine never asks lite.
- legend-engine's API (`/api/pure/v1/...`) stays byte-exact, served by the edge alone (`EdgeServer`, the edge's exports and entries).
- No product module depends on the edge (the build's layer rules).

## 7a. In scope, and not

- **In scope**: §2's operations, whatever the binding.
- **A held model** (`hold`/`release`, `HeldModel`, the planner's handles) is a binding's cache over the same operations: one compile kept for a model's text. It is not a second API. `HeldModel(model)` offers `relation_type`/`plan` over the model it holds.
- **Host-specific, out of this spec** (each host's own page protocol, unchanged by it):
  - a page's data: files, parts, forget, remote, snap, opened, join, source, warehouse;
  - the frames' registry;
  - the page document and its versions;
  - the settings.
- **The model home** (`/sdlc/api/*`, `/depot/api/*`): sdlc-server's and depot's own protocols, which lite serves as they are. It is not lite's API and not legend-engine's.

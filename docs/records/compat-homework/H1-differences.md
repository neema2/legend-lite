## 0. The answer

**Yes: every known difference fits exactly one class, so the architecture can hold all of them.** The classes are
P, R0, R1, X and S, plus J for test-judging machinery. The orchestrator asked for J in a message this session read
only after the first push, so J was applied in a second commit (§1.1). But the architecture holds them only on four conditions. Each condition is a decision or a cost, not a free
consequence of the design.

1. **The R1 set is not small.** The R1 rows need 18 named capabilities (§2), and three of them only switch a product
   optimisation off. A nineteenth, K7 (`scanOrder`), is needed only if compatibility judging keeps legend-engine's
   positional order (S14 and D14, now J).
2. **Many P rows need typed facts the result does not carry today.** That is 13 P rows, plus 2 at a root and 2 J
   rows (§3, risk 3).
3. **The X count depends on the user's (e′) ruling.** 17 register rows and 4 of §4 (b)'s ENGINE cells are X only
   because legend-engine refuses what lite answers.
4. **Rule 4 must be accepted for SQL text that upstream returns as a value.** This covers `toSQLString` and the test
   data generator's `sqls`. Rule 4 makes these S by fiat, and the corpus pays for it.

No row needed a mode, a style object or a hook in the compiler, planner, plan or exec. That holds only if each R1
capability is its own Pure-callable native with its own meaning, never a flag over a subtree (§3, risk 2).

## 3. The five largest risks

**1. SQL text as an answer.**
- **The scale:** legend-engine's relational tests call `toSQLString` 588 times in 64 files (a grep of the pinned
  tree). Its test data generator's `TestDataGenResult.sqls` is pinned by 45 `assertSqlEquals` (S193). Its plans carry
  SQL in `activities[0].sql` (D21) and `sqlQuery`.
- **The classing:** rule 4 makes all of it S. Lite answers its own SQL, and `EngineStyleH2`, `EngineStyleDB2`,
  `EngineStyleComposite` and `RelationalRootForm` (S4, C29) are deleted.
- **What that costs:** for an upstream program that stores or compares that text, it is a difference by rule, not
  by translation. A corpus test that judges SQL text (`toSQLString`, `assertSqlEquals`) can then pass only by its
  answer, never by its text. How many pass today through the engine-text printers was not measured here. The call
  is the user's.

**2. The R1 list is 18 capabilities (19 with K7), and three are switches.**
- **The switches:** K10, K12 and K16 each turn a product optimisation off for the edge alone; K7, which adds an
  order, is a fourth if compatibility judging keeps positional order.
- **What could go wrong:** if any is built as a flag over a subtree rather than a native with its own meaning, the
  core has a mode by another name.
- **What is not measured:** K6's size (the guarded natives lite would need unguarded twins of) and K15's rule (H2
  2.1.214's division scale, not in the pinned trees).
- **The guard needed:** each K must be a Pure-callable native in the product's library that no product code path
  calls, and something should pin the list.

**3. Presenter rows that need typed facts the result does not carry.**
- **The scale:** 13 P rows say `needs:` (S30, S31, S35, S41, S104, S118, S125, S362, S369, D20, C30, O1, O2).
  Two more need a fact at a root (D02, O3), and two J rows need facts at the host judge: S131, whether a side was
  sorted; S195, both statement texts.
- **The facts needed:**
  - a DateTime's written precision (lost for a value the database computed);
  - whether a column is stored or computed, and its Pure type (legend-engine's `pureTypeToDataType`,
    `relationalMappingExecution.pure:878-885`: String to VARCHAR(8192), Integer to BIGINT);
  - the scale legend-engine's SQL gives a Decimal (S104);
  - JDBC metadata (S125);
  - the unrefined static `Number` type (S25, S41);
  - the input's older JSON shape (S30, S31, S35);
  - which cells are object references (S362);
  - the parse's kept spans (S369).
- **The worst case is O3.** legend-engine's scalar envelope names its column `COUNT(*)`, which is H2's label of
  legend-engine's own unaliased SQL. The presenter cannot spell it without reproducing upstream SQL text.
- **The choice for each fact:** it is lite's own (carry it; product meaning), or it is upstream-shaped (then it
  presses on rule 1, or the row stays a ledgered difference).

**4. The (e′) ruling and legend-engine's refusals.**
- **The scale:** under E-R1, 17 register rows and 4 of §4 (b)'s ENGINE cells are X (upstream-refuses). The adapter
  must refuse exactly what legend-engine refuses, per database, in its words.
- **Some refusals are compile-time rules:** S146 needs m3's `FunctionDescriptor` id rule re-implemented in the
  adapter, and S25 needs Pure's static `Number` typing.
- **Under E-R2:** all 21 are S, and ENGINE answers more than legend-engine does.
- **The counts are not one number:** DuckDB's essential manifest holds 146 `expectedError` entries; 11 of them are
  `format`, where the design says 12.
- **Upstream's defects:** O5 (`cell.float`'s 8 digits) and the 12 register `defect` rows (upstream's bugs, not
  copied; S22's `count` over a missing association is 1, among them) stay register rows under either ruling.

**5. The database's version and session, which no input rewrite reaches.**
- **What legend-engine runs:** its patched H2 2.1.214 with `MODE=LEGACY` and `DEFAULT_NULL_ORDERING=HIGH`, and DuckDB
  1.3.0.
- **What lite runs:** H2 2.5.252 with H2's defaults, and DuckDB 1.5.6.
- **What is measured:**
  - `cell.float`: 8 digits against 18 (O5);
  - a Decimal division's scale (S141, rule unread);
  - legend-engine's own H2 functions, where lite's stock H2 computes the answer its own way. `parseJson` on H2 is
    legend-engine's `legend_h2_extension_json_parse`, a Java UDF that reads only a Map and re-serialises it:
    unledgered, D11 and S366. `h2Extension2_1_214.pure` also names its `jaro_winkler_similarity`, `edit_distance`,
    `split`, `split_part` and `reverse_string` UDFs; lite's `H2` dialect writes its own calls (`H2.java:761`,
    `:793`), not compared here.
- **What is not measured:** whatever `MODE=LEGACY` changes beyond null order. S368's rewrite covers only null
  placement.
- **The consequence:** each such case is X (no exact rewrite) or S (a defect), and the H2 corpus could hold many.
  Only a run of legend-engine's own H2 against lite's would count them (the engine runner, slice R).

## 5. Method

- **Units.** One unit per register row, per §4 (b) row (with both audiences' classes), per census group (with its hit
  count; `H1-census-hits.tsv` classes every hit by its group) and per oracle difference.
- **The classes, in the order applied.** The class is the mechanism an UPSTREAM audience needs to get upstream's
  answer:
  - **S**: no audience can observe a difference once the architecture holds. Subtags:
    - `rep`: SQL text, a plan, IR or statement shape (rule 4);
    - `retired`: the difference is gone;
    - `lite-only`: no legend upstream spelling;
    - `defect`: upstream's bug, ruled not copied, so lite answers the same in every audience and the row stays;
    - `same`: lite already gives upstream's answer;
    - `placement`: no meaning, only where the code sits.
  - **P**: only the bytes of a final answer or an error record differ, and the typed result plus the error record
    (kind, location, literal operands; A3) carry what the presenter needs. A missing fact is written `needs:`.
  - **R0**: values, rows or in-query text differ, and an input rewrite over existing product natives computes
    upstream's answer.
  - **R1**: the rewrite needs a new named capability (§2).
  - **X**: refuse by name in the upstream audience, with a subtag as in §1.
  - **J** (the orchestrator's addition): test-judging machinery, meaning how a test's verdict is reached. Its subtag
    names the owner, LITE or COMPAT (§1.1).
- **One class per row.** Where PURE and ENGINE need different mechanisms, the row takes the heavier, in the order R1,
  R0, X, P, S, and names both in its how cell. J goes to a row wholly about a verdict. A row with a verdict half
  and a product half keeps its product class and names its J half (S127, S139).
- **Who did the reading.** The register was read in four slices by sub-agents of this session, each reading every row
  in full against the same rubric and the pinned trees. This session classed §4 (b), the census and the oracle,
  then read the four slices whole and aligned them:
  - D10 follows S365's R0, the product's three-argument `parseDecimal`;
  - D15 follows S368's R0, null placement by sort keys rather than a session setting;
  - C29 follows S4 and S193's reading of rule 4 (SQL text as a value is S, `rep`).
  - Every R1 row's capability is named as in §2 (K1 to K19).
  - The J rows were the P, R0, R1 and S rows this list names; each J row's how cell says what it was.
  - Spot checks of S26, S129, S138 and S147 against the register found the slices' readings faithful.
- **Confidence.**
  - high: upstream read, and the mechanism exists or is plain;
  - medium: upstream read, and the mechanism argued;
  - low: upstream's answer unknown (an S5a cell with nothing in the pinned trees), or the mechanism unproven.

# The TypeScript batch (2026-11-16)

The TypeScript items of the batch PR the user asked for after #105 merged (main 4dfbb5b76c): the planner worker's hang,
and the independent hunt's findings T-A to T-G over the TypeScript hosts. Each fix is tested and red on revert. This
file is the batch's own record; the shared start-here and GATES documents are not edited from a PR branch.

## 0. A planner worker that stops (carried from #105's review)

Studio's planner port (`WorkerPort`, `engine-client/src/legend/wasm-grammar.ts`) had no `onerror`. Since the workspace's
tables take one step at a time, a worker that died held every later load, put, reset and table list behind its
unanswered request.
- The port now handles `onerror` and `onmessageerror`. Every waiting request and every later one is refused as "the
  planner worker stopped: <why>", and the worker is ended.
  - An uncaught error is said by its message, with its file and line when the event carries them.
  - A script that fails to load fires a plain Event with no message, so the worker is named: "the worker at <its URL>
    failed to load or run".
- `engine-client/test/model-data.test.ts`, "a planner worker that stops": on the port, and through `TabTables`.
- `studio/demo/verify.mjs` drives the count-failed cell: NOTES.NOTE's count fails by a harness-only stand-in, and
  PARTY.PARTY is still counted.
- The detail and the reverts: `docs/records/c5-t-recheck-2026-11-15.md`.

## T-A: a project opening late moves no screen's engine

`query/src/app/context.ts` `activate` pointed the screens' engine at a project's database after awaiting it, without
asking whether a newer navigation had overtaken it. Back pressed while a project said "Opening…" left the newer screen
reading the older project's rows when the older one finished, with no error.
- `activate` takes the navigation's "still current" check and asks it again once the database is there; each caller in
  `query/src/app/app.ts` passes its own.
- `query/test/context.test.ts`: P1 slow, P2 opened and pointed, P1 finishing moves nothing.
- Red on revert: the engine moves to P1.

## T-B: a tab DuckDB whose worker fails

DuckDB-WASM's handler of a worker's error logs it and drops the waiting requests without refusing them (read in the
library's `async_bindings.ts`), so a start whose worker or `duckdb-eh.wasm` did not load waited forever.
- `engine-client/src/duckdb-tab.ts` `instantiateDuckDbInTab`: the start listens for the worker's error and is refused,
  "DuckDB's worker failed: <its message>", or "it did not load" for a plain Event.
- Studio kept its first start for the page's life, a failed one included. `studio/src/app/start-once.ts` begins it
  again at the next ask after it fails.
- Tests: `engine-client/test/run-frame.test.ts`, "a tab DuckDB whose worker fails", and `studio/test/start-once.test.ts`.
  Red on revert: "still waiting after 5000 ms", and a failed start kept.
- Measured and not kept: a subclass of the library's bindings refusing every waiting request for the worker's whole
  life (after the start too). It cost the grid 111 bytes gzipped against the listener's 60.
  - Open: a worker error after the start still drops that request in the library. The worker runs on, so later requests
    are answered.

## T-C: a warehouse Snap on a connection of its own, and stoppable

A Snap of a warehouse grid streamed the warehouse's Arrow chunks into the copy inside `store.exclusive` on the tab's one
shared connection, with no signal. A stalled network held every grid's query behind it, and nothing could end it.
- `engine-client/src/snap.ts`: a copy streamed from a remote plane is made on a connection of the store's own (the
  `connect` a host gives `SnapManager`), opened for the copy and closed after it. A store that opens none is refused by
  name. The snap takes a `signal`.
- `engine-client/src/plan-runner.ts`: the stream step hands the plane the host's signal (`HostStreams.signal`). An abort
  ends the request and the step's transaction rolls back.
- DataCube: the browser page's local engine opens another connection to the tab's DuckDB (`LocalEngine.connect`,
  `SnapTarget.connect`), and the grid's close aborts a snap in flight.
- `engine-client/test/snap.test.ts`, "a snap from a remote plane", on real DuckDB: a stalled plane, a query on the shared
  connection answered while the copy waits, the abort ending the snap with no copy left and its connection closed.
- Red on revert, each half: the stream on the shared connection, or the signal not handed to the plane, "still waiting
  after 5000 ms".
- Open: no Cancel button. A snap in flight is stopped by its grid closing; a UI cancel is a design call.

## T-E: the notebook widget's channel (confirmed in part, not fixed)

`datacube/demo/widget-loader.ts`'s fetch over the widget's channel has no timeout.
- A fixed timeout would be wrong: ipykernel answers a comm message only between cells, so a long cell or a long query
  would be failed.
- The calls the cube makes carry its `EpochGuard`'s signal, which the channel honours, so the cube's next interaction
  aborts a call left waiting. Closing the view refuses every waiting call (`ChannelClosed`). Module and chunk files
  already move on after 30 s (`ANSWER_MS`).
- What remains: a kernel that stopped or restarted leaves a call waiting with no message until the next interaction.
  The fix needs the host's "comm closed" event, which differs by host (Jupyter, VS Code, marimo) and is not in anywidget's
  portable API. Left for a ruling.

## T-H: a connection's declared statement timeout, honoured or refused by name

Upstream applies a connection's `queryTimeOutInSeconds` to every statement it runs (legend-engine `SQLResult.java:65-68`,
as the brief cites it; JDBC's `setQueryTimeout`). The plan will carry it on the declared connection inside a target's
`database`, written only when the model declares it; C5-J builds the planner side, so every test here writes the key by
hand into a plan the planner made, or into a plan written whole.
- Read once, by name: `engine-client/src/plan-params.ts` `queryTimeOut(target)` and, beside `planParams`, `planTimeout(plan)`.
  Absent is none; 0 is none, as JDBC reads it; any other value that is not a whole number of seconds (-1, 1.5, "7", null)
  is refused by name, nothing sent.
- The hosts' runner (`plan-runner.ts`): every statement of a target that declares one goes through the host's timed send
  (`PlanSession.runWithin`, `TimedRun`). That covers the answer, the steps, the target's session statements, the
  transaction, the acquisition loads (`establish`), a keyed plan's keys and body, `runLoad` and `inLoadsTransaction`, a
  stream step's statements, and a person's statement (`runAuthored`). A host that hands no timed send has the plan
  refused by name before anything is sent: "its connection stops each statement after N seconds (queryTimeOutInSeconds),
  and this host stops none: it is not run here".
  - Not a statement, so not timed: a stream step's Arrow chunks, inserted by the library's Arrow import. The step's
    signal still ends them.
  - Handing no timed send, so refused by name if their plan ever declared one: the tab's own loads and writes (synthesize,
    Snap's stream and copy, a table Output, a remote mount, an upload). Their target is the tab's platform database, which
    never declares one.
- The answer paths, on the orchestrator's ruling (G7: a path that dropped the key would be a fallback): Studio's and
  Query's pure/v1 execute in the tab (`BrowserEngine.executeText`), DataCube's text plan (`lite-planner.ts` `textPlan`)
  and Query's cube planner read `planTimeout` beside `planParams`. A `Plan` carries `timeout`, and `QueryEngine.run`
  takes the seconds (its fifth argument): one way in for every engine.
- The doors hand the seconds to the engine: the playground's (`doors/authored.ts`), a project's Data rows loaded where
  the engine runs (`doors/project-data.ts` `dataLoaded`), and a project database's load (`project-data.ts`).
- DuckDB-WASM in the tab (`duckdb.ts` `#within`): the statement is sent as a pending query (`send`, through `#batches`, the
  one send), and `cancelSent` stops it when the time is up. The failure is the database's own, "query was canceled",
  never retried; an answer cut short between batches is said, never read as whole. Measured in Chromium: stopped at
  1,009 to 1,026 ms for 1 s, and the connection answers the next statement.
- The warehouse's engine refuses a timed statement, answer or stream by name, nothing submitted: its statement API stops
  none after a time.

**Register row S-batch-1, RULED by the user on 2026-11-16 ("as recommended", relayed by the orchestrator): a statement
that binds values, under a declared timeout, is refused on DuckDB-WASM.** Upstream times every statement. DuckDB-WASM runs a prepared statement to its end in one worker
call: measured, `cancelSent` on a prepared send returned false (nothing pending) and the statement ran to its end (2.5 s).
So `#within` refuses such a statement by name before it is sent: "this database cannot stop a statement that binds values
after N seconds, as its connection's queryTimeOutInSeconds asks: it is not sent". Today only a JSON connection's `data:`
payload binds a value in the tab.

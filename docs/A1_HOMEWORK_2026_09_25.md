# Homework for the first step: overload choice by the reference's rule, and the candidate set as declarations

Written 2026-09-25 before any code. This is what we actually do for tasks #47 and A1, file by
file, with the rules taken from the reference compiler's source (pinned legend-pure, `legend-pure-
core/legend-pure-m3-core/src/main/java/org/finos/legend/pure/m3/…`) and the numbers from the
reference differential (`tools/reference/`, receipts in the study directory).

## 1. Facts established today, from the reference

**1.1 How the reference collects candidates for a call** (`compiler/postprocessing/functionmatch/
FunctionExpressionMatcher.java`, `findMatchingFunctionsInTheRepository` and `getValidPackages`):

- The spelling is split at `::`. The last segment is the function name; everything before it is
  the package, if any.
- Qualified spelling: candidates are every function with that name whose package is exactly that
  package. Nothing else.
- Bare spelling: candidates are every function with that name whose package is in the call's
  IMPORT GROUP, plus the root package. The import group is the source section's, and nothing
  else: not the function's own package, not a handler surface.
- Then the matcher chooses among the candidates (1.3). Zero candidates is a compile error at the
  call; more than one best match is a compile error listing them.

**1.2 The import group's contents** (measured: `RefImports.java` dumped, for every source, the
packages its import group makes visible; 2,108 sources). Twenty-nine packages are visible in
EVERY source, corpus or platform — the implicit imports the Pure parser adds to each section:

```
meta::pure::functions::{asserts, boolean, collection, constraints, date, io, lang, math, meta,
                        multiplicity, relation, string, test, tools}
meta::pure::metamodel, ::extension, ::function, ::function::property, ::import,
                        ::multiplicity, ::relationship, ::type, ::type::generics, ::valuespecification
meta::pure::profiles, meta::pure::router, meta::pure::service, meta::pure::tds, meta::pure::tools
```

Our `NameResolver.CORE_IMPORTS` (generated from the engine's `CompileContext.META_IMPORTS`) is
these 29 plus three the newer engine added (`meta::pure::metamodel::variant`,
`meta::pure::metamodel::relation`, `meta::pure::precisePrimitives`). So the core import group is
the Pure rule, verified against the reference's own graph, and the corpus (Pure source) is
resolved by imports alone. The engine's handler surface applies to engine input (query and model
text over the wire) and to nothing else.

**1.3 How the reference chooses among candidates** (`FunctionExpressionMatcher.getBestFunctionMatch`,
`FunctionMatch`, `navigation/generictype/match/GenericTypeMatch.java`, `TypeMatch.java`,
`navigation/multiplicity/MultiplicityMatch.java`):

- Candidates with the wrong parameter count are out.
- For each remaining candidate, a `FunctionMatch` is built: for every parameter, a
  `GenericTypeMatch` of the argument's type against the parameter's type, and a
  `MultiplicityMatch` of the argument's multiplicity against the parameter's. A parameter that
  cannot match makes the candidate not a match at all.
- Candidates are ordered by `FunctionMatch.compareTo`: first ALL the type matches, parameter by
  parameter, left to right; only if every type match ties, ALL the multiplicity matches, parameter
  by parameter. The smallest wins. Several smallest: the compile error "Too many matches".
- `GenericTypeMatch.compareTo`: the raw type match first, then the type-argument matches, then the
  multiplicity-argument matches.
- `TypeMatch` ordering, from best to worst: an exact match (distance 0); a simple match at
  distance *n* (the number of generalisation steps from the argument's class to the parameter's;
  smaller is better); a non-concrete match (the parameter is a type variable); then relation-type
  and function-type matches (each compares its own column/parameter matches); a null match last.
- `MultiplicityMatch` ordering, from best to worst: exact (both bounds at distance 0); the
  non-concrete match (the parameter's multiplicity is a variable); then by upper-bound distance,
  and only then by lower-bound distance; a null match last.

This ordering is why the reference picks `isEmpty(Any[0..1])` for a `[0..1]` argument (exact
multiplicity beats the `[*]` overload's distance), `max(Integer[1..*])` over `max(Integer[*])`,
`average(Integer[*])` over `average(Number[*])` (type distance 0 beats 1), and
`between(DateTime…)` over `between(Date…)`.

**1.4 What we do today, for contrast.**

- Candidates (`NameResolver.resolveCallCandidates`): the section's wildcard imports, then the
  function's OWN package, then the core import group, each spelled as `pkg::name` and kept only
  if the universe knows it; empty falls back to the element resolver. What is still bare at the
  typer goes through `BareNames` (handler surface, core group, form-owned FQNs) and
  `FunctionCompiler.functionsAt`, which merges catalog natives with model bodies behind a
  hand-owned list and a conformance-stereotype check.
- Choice (`InferenceKernel.resolveOverload`): one number per candidate, the SUM over parameters
  of `typeScore × 20 + multScore`, highest wins; ties broken by "all same shape", then
  native-over-module, then a most-specific rule over class-typed parameters only. A sum cannot
  express "type first, then multiplicity, parameter by parameter", and the tie-breaks are the
  category rules the program is deleting.

**1.5 The measured gap** (`tools/reference/join.py`, 2026-09-25, jar 4.138.5 vs our pin 4.145.0):
over 10,161 bodies both compilers type, 66,608 calls resolve to the same overload, 28 to a
different package, 799 to a different overload, 104,399 are not checkable (forms and non-call
nodes). Every one of the 799 is explained by 1.3. The 28 need individual reading; the
differential lists each with its function.

## 2. What we actually do

### 2.1 Task #47 — the kernel chooses like the reference

File: `core/src/main/java/com/legend/compiler/spec/InferenceKernel.java`.

- Add a `Match` value per candidate: per parameter a type match (exact / distance *n* /
  non-concrete / relation / function / none) and a multiplicity match (exact / non-concrete /
  upper distance, lower distance / none), computed with the SAME unifier the kernel already has
  (`unify`, `unifyMult`) so a match is never computed twice in two ways.
- `resolveOverload`: count filter; build the matches; order by the reference's `compareTo`
  exactly (types first across all parameters, then multiplicities); smallest wins; several
  smallest is a `TypeInferenceException` "Too many matches for <call>" listing them with their
  signatures.
- Delete in the same commit: `score`, `paramTypeScore`/`paramMultScore` as scores (they become
  the match constructors), `mostSpecific`, `moreSpecific`, the "all same shape" and
  native-over-module branches.
- Read before coding, in the pinned tree: `MultiplicityMatch.newMultiplicityMatch` (how the two
  bound distances are computed, and the null/parameter behaviours), `TypeMatch.newTypeMatch`
  (how `typeDistance` counts generalisation steps and treats `Any`/`Nil`), `FunctionMatch.
  newFunctionMatch` (how lambda arguments are matched before their types are known: the
  `lenient` flag).
- Gate: rerun the differential — overload disagreements 799 → 0; package 28 → each explained
  or fixed; corpus rosters LOST 0; conformance unchanged; census not grown.

### 2.2 A1 — the candidate set is a set of declarations, and the category gate dies

Files: `NameResolver.java`, `FunctionCompiler.java`, `BareNames.java`, `PlatformTypes.java`,
`protocol/spec/AppliedFunction.java`, the typer's `candidatesOf`.

- `resolveCallCandidates` becomes the reference's rule: qualified → that package's functions of
  that name; bare → the section's import group ∪ the implicit imports (the core group, generated)
  ∪ root, each looked up in the World's index of declared functions by package and name — ONE
  index built once per World, not 33 spelled lookups per call. The function's own package leaves
  the rule (the reference does not use it); the differential says whether any corpus call needs it.
- The candidates on the call node are declaration identities (`FunctionId`), one per overload,
  not package spellings. A bare spelling with zero candidates is a bind error at the call's span.
- The engine's handler surface is applied by the binder ONLY when the input is engine text
  (queries and models over the wire: DataCube); `BareNames` becomes that one rule for that one
  input and stops serving the typer for Pure source.
- `FunctionCompiler.functionsAt` reads `declarations().at(id)` for the candidate ids and nothing
  else. A bodied declaration and a catalog native under the SAME id is one declaration in the
  table, and the implementation table's row says the platform runs it natively, so the body never
  joins a candidate set. Delete in the same commit: `PlatformTypes.isPlatformOwnedFunction` and
  `PLATFORM_OWNED_FUNCTIONS`, the conformance-stereotype check and `addModelOverloads`'s
  suppression, `SUPPRESSED_ONCE` and its console lines, `BareNames.fqns` tiers 2 and 3 as a typer
  path.
- Gate: the differential (package 0 after #47's fixes); corpus rosters LOST 0; conformance
  unchanged; census not grown; FUNCTION_CATEGORY_CHECK 13 → 10 or lower; CATALOG_LOOKUP_BY_NAME
  down by the deleted sites; corpus per-pass time back to the program's start (DuckDB 32/37s,
  H2 19/55s alone) — task #46 closes here because the 33 lookups are gone.

## 3. What could go wrong, and how we would know

- **Strictness.** The reference's "Too many matches" is an error where our sum picked a winner.
  Since the reference compiles every corpus body, every real tie is already resolved by its rule;
  a new tie on our side means our type representation differs (a distance computed differently),
  and the differential names the call.
- **Our types are not its types.** Relation types with column lists, function types, `Number`
  vs `Integer` distances, `Any`/`Nil`: each has an ordering rule above; a wrong one shows up as a
  disagreement, never as a roster loss, because most overloads lower alike.
- **Version drift.** The jar is 4.138.5; our sources are 4.145.0. Rows for declarations that
  exist on one side only are excluded by the join; the 28 and the 799 are all in bodies both
  sides have. A 4.145.0 reference would need legend-pure's own jars from Maven Central; noted, not
  needed for these two steps.
- **The own-package tier.** If removing it breaks a corpus call, that call is one the reference
  resolved through an import we are not reading, which is a binder bug to fix, not a tier to
  keep.

## B. Report: GraphQL as the object-query frontend (research agent, verbatim)

Research stopped on the coordinator's instruction (credit conservation). Below is everything verified so far; gaps are marked "not checked".

### 1. GraphQL spec status (2026)

- **Latest edition: September 2025** (announced 2025-09-08; first since October 2021; >100 commits). Adds OneOf input objects, Schema Coordinates, descriptions on executable documents, broader `@deprecated`, full Unicode. The announcement explicitly pitches document descriptions and schema coordinates for "AI assistants, codegen tools, and agents". https://graphql.org/blog/2025-09-08-september-edition/ Working draft: https://spec.graphql.org/draft/ (no 2026 edition found).
- **Governance/licence**: spec is "a deliverable of the GraphQL Specification Project, established in 2019 with the Joint Development Foundation"; GraphQL Foundation (Linux Foundation) formed 2019. Spec licence **OWFa 1.0** (patent + copyright), source code MIT, data sets CC0 (https://spec.graphql.org/draft/, relicensing history https://engineering.fb.com/core-data/relicensing-the-graphql-specification/, membership https://graphql.org/foundation/join). Foundation 2025 spend $601k (mostly GraphQLConf), member dues $219,667, 2026 budget cut to $266k, GraphQLConf 2026 "right-sized"; Graphile paid as "community gardener" for spec, GraphQL.js and GraphiQL. https://graphql.org/blog/2026-04-09-graphql-foundation-budget-2026/
- **graphql-js**: MIT; **v17 GA 2026-06-15**, first major since 2021. https://graphql.org/blog/2026-06-15-introducing-graphql-js-v17/ Tests live in `src/__tests__` (README https://cdn.jsdelivr.net/npm/graphql@17.0.2/README.md) and are the de-facto reference corpus (parser/validation/execution), MIT.
- **graphql-java**: MIT, ~6.2k stars. https://github.com/graphql-java/graphql-java Test framework (Spock/Groovy?) not checked.
- **Conformance suite**: **graphql-cats** (https://github.com/graphql-cats/graphql-cats) — language-independent YAML scenarios + `.graphql` schemas, **Unlicense**, self-described "infant phase", drivers listed for Sangria, Hot Chocolate, graphql-java (PR); commit page shows last activity **Nov 2018** (https://github.com/graphql-cats/graphql-cats/commits/master) — effectively dormant. No official Foundation conformance suite exists. Apollo's compatibility suite is Federation-only (https://www.apollographql.com/blog/new-apollo-federation-spec-compliance-tools-for-graphql-server-maintainers). An MIT text-to-GraphQL dataset (10,940 train / 957 test schema+query+NL triples) exists (see §4).

### 2. Spec gaps and de-facto filter/sort/page/aggregate dialects

No standard. Dialects found:
- **Hasura v2**: `where: { name: { _eq: "Sidney" } }`, `_and/_or`, relationship filters `where: { articles: { rating: { _gt: 4 } } }`, `{}` = TRUE, `_cast`; `_eq: null` is a type error since v2.0. https://hasura.io/docs/2.0/queries/postgres/filters/index/ (`order_by`, `limit/offset`, `distinct_on`, `<table>_aggregate`: from the linked pages, not re-checked).
- **Hasura v3/DDN**: same `where/_eq/_and/_or`, `limit/offset`, `order_by` (https://hasura.io/docs/3.0/graphql-api/queries/filters/index/, https://hasura.io/docs/3.0/graphql-api/queries/pagination/). What changed: operators are now declared per type in metadata (`BooleanExpressionType` scalar/object with `dataConnectorOperatorMapping`, `OrderByExpression`) https://hasura.io/docs/3.0/reference/metadata-reference/boolean-expressions, https://hasura.io/docs/3.0/reference/metadata-reference/orderby-expressions; aggregates renamed `<field>Aggregate`, "differ slightly from v2", connector-dependent https://hasura.io/docs/3.0/graphql-api/queries/aggregation-queries/, https://hasura.io/docs/3.0/upgrade/feature-availability/api-features.
- **PostGraphile v5**: built-in `condition` (equality only, indexed columns, `@behavior filterBy`); docs say generic filtering is "strongly discouraged". Plugin `postgraphile-plugin-connection-filter` (MIT) adds `filter: { createdAt: { greaterThan: "2021-01-01" } }` with `equalTo/notEqualTo/distinctFrom/lessThan/greaterThanOrEqualTo/in/notIn/isNull`, `and/or/not`, relation filters opt-in. https://postgraphile.org/postgraphile/5/filtering, https://github.com/graphile-contrib/postgraphile-plugin-connection-filter
- **Prisma**: `findMany({ where, select, include, orderBy, take, skip, cursor, distinct })`, `_count` inside select/include, `equals/contains/startsWith/endsWith`, `AND`, relation `some` (https://www.prisma.io/docs/orm/reference/prisma-client-reference). Note: **Prisma Next (early access) replaces this with a chained API** `.where().orderBy().limit().offset().cursor()` (https://www.prisma.io/docs/orm/prisma-client/queries/filtering-and-sorting) — even Prisma's object-query dialect is not stable.
- **Relay Cursor Connections**: `first/after`, `last/before`, `edges{node,cursor}`, `pageInfo{hasNextPage,hasPreviousPage,startCursor,endCursor}`; page states no licence/version (https://relay.dev/graphql/connections.htm); relay repo is MIT (https://github.com/facebook/relay).
- **AWS AppSync/Amplify**: `filter: ModelPostFilterInput` with `ModelStringFilterInput { ne eq le lt ge gt contains notContains between beginsWith }`, `and/or/not`, `limit`, `nextToken`, `ModelXConnection { items nextToken }`; no total count, no page numbers. https://docs.amplify.aws/cli-legacy/graphql-transformer/model/, https://docs.amplify.aws/react/build-a-backend/data/query-data/ (`attributeExists`: not checked).
- **Pothos prisma-utils**: "highly experimental", only building blocks (`builder.prismaFilter`). https://pothos-graphql.dev/docs/plugins/prisma/prisma-utils
- **Neo4j GraphQL**: three incompatible generations — v3–5 `name_CONTAINS: "Keanu"` (https://neo4j.com/docs/graphql/3/filtering/); v6 `name_EQ`, `actors_SOME`, `NOT: {...}`, `options:{}` → top-level `limit/offset/sort`, aggregates moved to `moviesConnection { aggregate { count { nodes } } }` (https://neo4j.com/docs/graphql/6/migration/); v7 nested `name: { contains }`, `AND/OR/NOT`, relationship `some/all/none/single`, `<rel>Connection: { aggregate }` (https://neo4j.com/docs/graphql/current/queries-aggregations/filtering/).
- **Shopify**: string `query:` argument (`title:Caramel`, `:<`, `:>=`, implicit AND, `OR`, `-`/`NOT`, `*`), `sortKey`, Relay connections; invalid fields are silently ignored with a warning in `extensions`. https://shopify.dev/docs/api/usage/search-syntax
- **GitHub**: `search(query: String!, type:, first/after)` with GitHub search syntax; per-type `orderBy: { field: IssueOrderField, direction: ASC|DESC }`; `first/last` 1–100. https://docs.github.com/en/enterprise-server@3.17/graphql/reference/search, https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api
- **Standardisation**: none. Composite Schemas spec (Proposal Stage) covers only subgraph/supergraph directives, composition, distributed executor — nothing on filters (https://github.com/graphql/composite-schemas-spec/blob/main/ROADMAP.md, https://graphql.org/blog/2024-05-16-composite-schemas-announcement/). OpenCRUD (Prisma-v1 era) is dormant (site returned 503; https://discuss.dgraph.io/t/suggestion-why-not-using-opencrud-specification/14584). No graphql-wg filter RFC found. The Hasura `where/_eq/_and/_or/limit/offset/order_by` shape is the most-copied, and it is what legend-engine adopted (§5).

### 4. Agent adoption

- **Apollo MCP Server** (MIT, 315 stars): operations become MCP tools from `.graphql` files, persisted-query manifests, GraphOS collections, or **schema introspection** (`introspect`, `search`, `validate`, `execute` tools behind `--introspection`). https://www.apollographql.com/docs/apollo-mcp-server, https://www.apollographql.com/docs/apollo-mcp-server/guides, https://github.com/apollographql/apollo-mcp-server. Apollo's own blog gives **no measured numbers**, recommends curated operation collections and trimmed descriptions. https://www.apollographql.com/blog/building-efficient-ai-agents-with-graphql-and-apollo-mcp-server
- **Shopify**: Dev MCP (`@shopify/dev-mcp`, local, no auth) gives agents `introspect_graphql_schema` + validation so generated GraphQL matches the live schema (https://shopify.dev/docs/apps/build/devmcp, https://shopify.dev/apps/build/devmcp); shopper-facing Storefront MCP exposes **curated tools** (`search_shop_catalog` → `search_catalog` on `/api/ucp/mcp`), not raw GraphQL (https://shopify.dev/docs/apps/build/storefront-mcp/servers/storefront, https://shopify.dev/docs/agents/catalog).
- **Hasura PromptQL**: the LLM writes a query *plan* executed in a Python runtime over DDN metadata — Hasura does **not** have the LLM write GraphQL; the "100% accuracy" claim is admitted to "not technically hold water"; benchmark is only vs tool-calling. https://promptql.io/blog/how-promptql-achieves-100-accuracy-for-ai-on-enterprise-data, https://promptql.hasura.io/spec
- **Papers**: IBM EMNLP 2024 Industry text-to-GraphQL dataset (MIT): 10 LLMs, **best ≈50% accuracy with one in-context example**; motivation: LLMs have seen few public GraphQL schemas → invalid queries. https://aclanthology.org/2024.emnlp-industry.117/ NAACL 2025 SNAIL: schema-aware example selection, up to +20% on some query classes. https://aclanthology.org/2025.naacl-industry.76/ IBM RGEval: semantically equivalent GraphQL differs syntactically, complicating evaluation. https://researchweb.draco.res.ibm.com/publications/robust-evaluation-of-llm-generated-graphql-queries-for-web-services Text2GQL-Bench is ISO-GQL, not GraphQL (4% zero-shot → ~50% 3-shot) https://arxiv.org/abs/2602.11745v1. **No head-to-head GraphQL-vs-SQL LLM benchmark found**; SM3-Text-to-Query (NeurIPS 2024) covers SQL/Cypher/SPARQL/MQL only https://arxiv.org/abs/2411.05521.
- **Practitioner signals**: 70–80% token-reduction claims are unmeasured (tianpan, citing a Medium post); one team reported agents producing malformed GraphQL and switched to purpose-built tools https://blog.buildbetter.ai/mcp-vs-rest-api-product-teams-switching-2026/; GraphQLConf 2026 "GraphQL Meets LLMs" deck (Starbucks) is illustrative only https://hosted-files.sched.co/graphqlconf2026/5b/GraphQL_Meets_LLMs_Final.pdf (text not extracted).
- **Verdict**: typed schema + introspection is universally used as the *grounding* step (introspect → validate → execute), but production patterns converge on curated/persisted operations rather than free-form generation; no rigorous evidence GraphQL beats SQL for LLM accuracy; non-standard filter dialects and many equivalent spellings are cited as hurting generation and evaluation.

### 5. legend-engine's GraphQL extension

- **Tree**: `legend-engine-xts-graphQL/` with modules `-grammar` (ANTLR `GraphQL.g4` at `legend-engine-xt-graphQL-grammar/src/main/antlr4/org/finos/legend/engine/language/graphQL/grammar/from/antlr4/GraphQL.g4`, derived from antlr grammars-v4 "slightly modified"), `-grammar-integration` (embedded `#GQL{ ... }#` value specification), `-protocol`, `-compiler`, `-pure-metamodel` (`core_external_query_graphql_metamodel/{sdl,introspection}/`), `-pure` (`core_external_query_graphql/transformation/transformation_graphFetch.pure`, `transformation/dynamic/{main,metamodel,utility}.pure`, `dynamic/operators/{eq,in,lt,lte,gt,gte,contains,eqIgnoreCase,exists}.pure`, `dynamic/expressions/{and,or,field}.pure`, `binding/{fromPure,toPure}/{sdl,introspection}/`), `-http-api` (`GraphQLExecute.java` @ `graphQL/v1/execution`, `GraphQLGrammar.java`, `GraphQLDebug.java`), `-generation-http-api`, `-relational-extension` (`TotalCountDirective.java`, ServiceLoader `IGraphQLDirectiveExtension`). Design doc: `docs/graphQL/graphQL.md`. https://github.com/finos/legend-engine/tree/master/legend-engine-xts-graphQL, https://raw.githubusercontent.com/finos/legend-engine/master/docs/graphQL/graphQL.md Tutorial https://legend.finos.org/docs/tutorials/graphql-tutorial, GS blog https://developer.gs.com/blog/posts/introducing-legend-graphql
- **Semantics** (package `meta::external::query::graphQL::{metamodel::sdl, transformation::queryToPure, binding}`): a synthetic root class (e.g. `demo::Query`) is the Query type; its functions are root fields (`allFirms() {demo::Firm.all()}: demo::Firm[*]`, `firmByLegalName(legalName: String[1])`). `graphQLExecutableToPure` builds a `RootGraphFetchTree`; `extractLambdaFromQuery` → one lambda + execution plan **per root field**; `addDynamicFilter` reads a `where` argument and maps `_and,_or,_eq,_exists,_in,_contains,_lt,_lte,_gt,_gte,_eqIgnoreCase` to `->filter()`. Introspection auto-generates Hasura-style `<Class>_bool_exp`, `<Scalar>_comparison_exp`, `<Class>_exists_exp` inputs and adds `where: <Class>_bool_exp` to root fields. Limiting functions (`slice/drop/limit/take/paginated`) in the function body are allowed only after `sortBy`/`sortByReversed` (assert "Any limit function should be preceded by sorting function"). Tests use `allEmployees(where: { firstName: { _contains: "Jo" } }, offset: 1, limit: 1) @totalCount` — how `limit/offset` args bind (function parameters?) not checked; no `order_by`/sort argument found.
- **`@totalCount`** (relational extension): second plan named `<field>@totalCount` = same filter minus limiting function, `groupBy` count; result goes into the response `extensions` keyed by root field/directive; "currently supported at a root level field". A test `echo` directive also exists.
- **Mutations**: `isMutation()` flag and variables are plumbed, but design doc says mutation/subscription "coming later"; introspection tests report `mutationType: null`. **Introspection** is served through the execute route when the root field is `__schema`. **Routes**: `POST /api/graphQL/v1/execution/{generatePlans|execute}/{dev/{projectId}/[group]workspace/{ws}|prod/{groupId}/{artifactId}/{version}}/query/{queryClassPath}/mapping/{mappingPath}/runtime/{runtimePath}[/binding/{bindingPath}]` and `.../dataspace/{path}`. Known limits: args must be in Pure-parameter order (tutorial bug); input types unsupported; multi-root-field result merge in `GraphQLExecute.execute` looks buggy on reading (unverified).

Not checked (stopped): graphql-java test framework; Hasura v2 `distinct_on`/`_aggregate` exact pages; AppSync `attributeExists`; Stack Overflow GraphQL figure; OpenCRUD site; legend-engine `limit/offset` binding and `isMutation` effect; licence of relay.dev spec page.

## C. Report: the alternatives to GraphQL (research agent, verbatim)

Scope note: web research stopped early at the coordinator's request; items marked **not checked** were not researched, items marked *unverified* rest on one secondary source or memory.

### 1. OData v4.01 / 4.02 (+ Data Aggregation)
**(i)** URL query protocol over a CSDL entity model.
`GET /Firms?$filter=startswith(legalName,'A')&$select=legalName&$expand=employees($select=name;$orderby=name;$top=5)&$orderby=legalName&$top=10&$skip=20&$count=true`
`GET /Employees?$apply=groupby((firm/legalName),aggregate($count as n))`
**(ii)** OASIS OData TC (editors from Microsoft, SAP, IBM, Progress). 4.01 Parts 1–2 = OASIS Standard 23 Apr 2020 (https://docs.oasis-open.org/odata/odata/v4.01/os/); 4.0 = ISO/IEC 20802-1/-2:2016 (https://www.vde-verlag.de/iec-normen/225004/iso-iec-20802-2-2016.html); 4.02 only at Committee Spec Draft 02, public review Aug 2026 (https://docs.oasis-open.org/odata/odata/v4.02/csd02/); Data Aggregation 4.0 is CS04, Nov 2025, not an OASIS Standard (https://docs.oasis-open.org/odata/odata-data-aggregation-ext/v4.0/odata-data-aggregation-ext-v4.0.md).
**(iii)** TC runs in OASIS "RF on RAND" IPR mode (https://www.oasis-open.org/committees/odata/ipr.php). Test corpus: ABNF grammars with positive/negative test cases for core, aggregation and temporal (https://github.com/oasis-tcs/odata-abnf; e.g. https://docs.oasis-open.org/odata/odata/v4.0/errata01/csd01/complete/abnf/odata-abnf-testcases.xml) — **syntax only**, no result-based conformance suite found; Part 1 §13 defines conformance levels in prose. Oracles: Apache Olingo (Apache-2.0, Java, OData 4.0 only) was **retired Dec 2025 → Attic** (https://attic.apache.org/projects/olingo.html); Microsoft ODataLib .NET is active (releases every 2 months, URI parser + test suites; 732 stars; license file not read, MIT *unverified*) (https://github.com/OData/odata.net).
**(iv)** Humans: Microsoft Graph ("single unified API across Microsoft 365", https://www.oasis-open.org/?p=1787), SAP (OData is the S/4HANA API protocol, "hundreds of OData APIs"; SAP Graph on OData v4, https://groups.community.sap.com/t5/technology-blogs-by-sap/graph-intro-series-part-8-use-graph-with-odata-v4/ba-p/13641190), Dynamics/Dataverse Web API, Azure DevOps Analytics (https://learn.microsoft.com/sl-si/azure/devops/report/extend-analytics/odata-supported-features). No usage counts found. Agents: no first-party generic OData MCP from Microsoft; Dataverse MCP server (GA Dec 2025) exposes `list_tables/describe_table/read_query`, not OData syntax (https://learn.microsoft.com/en-us/power-apps/maker/data-platform/data-platform-mcp); "Microsoft MCP Server for Enterprise" (Entra, preview) generates Graph calls (https://learn.microsoft.com/graph/mcp-server/get-started); community bridges: oisee/odata_mcp_go (v2+v4, "universal tool" mode, https://mcpservers.org/servers/oisee/odata_mcp_go), GutjahrAI SAP OData MCP, CData commercial (https://cdn.cdata.com/help/RDN/mcp). No text-to-OData benchmark found.
**(v)** Best structural fit of the URL-style candidates: CSDL has entity types with inheritance (type-cast segments), navigation properties = associations, complex types; `$expand` returns nested JSON.
**(vi)** `$filter` (full expression grammar, `any/all` lambdas), `$orderby`, `$top/$skip/$skiptoken/$count`, `$select/$expand` (nested, `$levels`), `$compute` (computed fields, 4.01), `$search` (server-defined semantics), `$apply` groupby/aggregate/filter/compute (extension).

### 2. JSON:API 1.1
**(i)** JSON media type + URL conventions for resource graphs.
`GET /firms?filter[legalName]=Acme&fields[firms]=legalName&include=employees&fields[employees]=name&sort=-legalName&page[number]=2&page[size]=10`
**(ii)** Community spec, no SDO; 1.1 final 2022-09-30, 1.2 "upcoming" (https://jsonapi.org/).
**(iii)** CC0-1.0 (https://github.com/json-api/json-api, 7.7k stars). No conformance corpus; the implementations page states none are verified for compliance (https://jsonapi.org/implementations/). Oracle candidates: Drupal core module (GPL), Elide/Crnk (Java) — each adds its own filter grammar.
**(iv)** ~86 client / ~118 server libraries listed; Drupal 10+ ships it on by default; Ember Data; Rails. Agents: community Drupal MCP servers over JSON:API (https://github.com/peximo/drupal-mcp-server); no benchmarks.
**(v)** Typed resources with to-one/to-many relationships fit associations; no inheritance; `include` flattens related resources into a side `included` array with linkage, not a tree.
**(vi)** `include` (dot paths), `fields`, `sort`, `page` family (strategy unspecified); **`filter` is only reserved** ("agnostic about the filtering strategies", https://jsonapi.org/format/); a non-normative recommendation gives `filter[post]=1,2` (https://jsonapi.org/recommendations/). No aggregation, no computed fields.

### 3. PostgREST / Supabase
**(i)** URL DSL over a Postgres schema with FK-inferred embedding.
`GET /firms?select=legalName,employees(name,age)&legalName=like.A*&employees.order=name&order=legalName.desc&limit=10&offset=20`
**(ii)** No standard; the docs are the spec (https://docs.postgrest.org/en/v14/references/api/tables_views.html); PostgREST maintainers, Supabase sponsors.
**(iii)** MIT, 27.7k stars (https://github.com/PostgREST/postgrest). Tests are Haskell hspec/IO tests coupled to a fixture schema (contents not inspected). Oracle: PostgREST + Postgres, free and deterministic.
**(iv)** Supabase: 1.8M devs / 3.5M databases (Apr 2025, https://www.bigdatawire.com/2025/04/24/supabases-200m-raise-signals-big-ambitions), 4M devs (Oct 2025), 9M devs (Jun 2026, single source https://itbrief.co.uk/story/supabase-raises-usd-500-million-in-series-f-round). `@supabase/postgrest-js` 20.2M npm downloads/week (api.npmjs.org, 2026-10-10..16). Agents: official `@supabase/mcp-server-postgrest` with a `request` tool and SQL-to-REST converter (https://playbooks.com/mcp/supabase-postgrest); LLMs emit supabase-js chains fluently (training-data effect; no benchmark found).
**(v)** Tables/views + FKs, M:N via junction; no inheritance; computed columns via SQL functions; nested JSON out.
**(vi)** Rich filters (`eq, gt, like, in, is, cs, ov, fts, not., or=()`), filters/order on embedded resources, `limit/offset`/Range, nested `select` with aliasing/casting/spread, `!inner` joins; aggregates `select=amount.sum()` (v12+, off by default) — docs were rate-limited, *from memory, unverified*.

### 4. MongoDB MQL / aggregation pipeline
**(i)** `db.firms.aggregate([{$match:{legalName:/^A/}},{$lookup:{from:"persons",localField:"_id",foreignField:"firmId",as:"employees"}},{$project:{legalName:1,"employees.name":1}},{$sort:{legalName:1}},{$skip:20},{$limit:10}])`
**(ii)** No formal standard; defined by server behavior. Linux Foundation DocumentDB (MIT, 25 Aug 2025) explicitly aims to "establish a new open standard for NoSQL" (https://www.linuxfoundation.org/press/linux-foundation-welcomes-documentdb-to-advance-open-developer-first-nosql-innovation).
**(iii)** Server SSPL. `mongodb/specifications` (driver specs + unified YAML tests) is **CC BY-NC-SA 3.0 US** — non-commercial (https://github.com/mongodb/specifications); MongoDB's 2023 letter to FerretDB asserts the same for docs/wire spec (https://blocksandfiles.com/wp-content/uploads/2025/04/Letter-from-MongoDB-to-FerretDB_3-Nov-2023-signed.pdf). Free oracles: FerretDB (Apache-2.0, 11.1k stars, https://github.com/FerretDB/FerretDB) and DocumentDB (MIT, 3.5k, https://github.com/documentdb/documentdb) — both already compile MQL to Postgres. NL corpora: `mongodb-eai/natural-language-to-mongosh` (Apache-2.0 per file page, https://huggingface.co/datasets/mongodb-eai/natural-language-to-mongosh); SM3-Text-to-Query 10K pairs/language, CC-BY-SA (https://arxiv.org/abs/2411.05521); TEND 1,210 tasks (license not stated, https://github.com/Jinwei-Lu/Text-to-NoSQL).
**(iv)** Humans: `mongodb` npm 8.8M/week; compatible engines (AWS DocumentDB, Cosmos, Oracle API) from the prompt, not independently re-verified. Agents: official MCP server, Apache-2.0, 1.1k stars, `find/aggregate/count/explain…` (https://github.com/mongodb-js/mongodb-mcp-server). Accuracy: SM3 (Llama3-70b, 5-shot+schema): SQL 57.5, Cypher 57.1, **MQL 40.4 (±17)**, SPARQL 30.5; BM25 few-shot GPT-3.5: SQL 88.6, MQL 78.7, Cypher 78.3 (https://arxiv.org/html/2411.05521). TEND: direct prompting 28.9% EXC, best method 35.8% — "LLMs strong at NL2SQL degrade substantially" (https://arxiv.org/html/2502.11201).
**(v)** Document model: no schema, inheritance or typed associations; `$lookup` is a hand join. Fit requires a convention (collection per class, `$lookup` over associations).
**(vi)** Very rich filter, sort, skip/limit, `$project` with expressions (computed), `$group`, `$lookup` sub-pipelines, `$unwind`, `$facet`.

### 5. EdgeQL (Gel, ex-EdgeDB)
**(i)** `select Firm { legalName, employees: { name } filter .age > 30 order by .name limit 5 } filter .legalName ilike 'a%' order by .legalName offset 20 limit 10;`
**(ii)** No standard; docs plus a 2025 paper giving static and dynamic semantics of the graph-relational model (https://arxiv.org/abs/2507.16089). **Gel Data Inc. shut down 2 Dec 2025, team joined Vercel; Gel Cloud closed 31 Jan 2026; OSS continues** (https://www.geldata.com/p/sunset).
**(iii)** Apache-2.0, 14.2k stars; `tests/` holds 53 `test_edgeql_*.py` suites (query → expected JSON; extractable with effort) (https://github.com/geldata/gel/tree/master/tests). Oracle: Gel server (compiles to Postgres), free.
**(iv)** Niche; ~$19M raised (*secondary*); no customer figures; abandonment risk. Agents: community MCP only (https://glama.ai/mcp/servers/christian561/gel-mcp-server); no benchmark; thin training-data presence.
**(v)** Closest semantic match to a Pure class model: object types, inheritance and polymorphic queries, links with backlinks, computed properties, cardinality typing, nested shapes returning trees.
**(vi)** filter/order by/offset/limit (also inside nested shapes), computed `alias := expr`, `count/sum/math::mean`, `group … using … by` returning `{key, grouping, elements}` (https://docs.geldata.com/database/edgeql/group).

### 6. PartiQL / SQL++
**(i)** `SELECT VALUE {'name': f.legalName, 'employees': (SELECT VALUE e.name FROM f.employees AS e WHERE e.age > 30)} FROM firms AS f WHERE f.legalName LIKE 'A%' ORDER BY f.legalName LIMIT 10 OFFSET 20`
**(ii)** Amazon-owned spec (AsciiDoc in https://github.com/partiql/partiql-lang); SQL++ (UCSD), Couchbase N1QL and AsterixDB are cousins, not one standard.
**(iii)** Spec under a custom "PartiQL Specification License": copy/distribute/implement free, royalty-free patent grant, **no modification or derivatives** (https://raw.githubusercontent.com/partiql/partiql-spec/main/LICENSE). `partiql-tests` Apache-2.0 with `success/fail/eval/eval-equiv` (https://github.com/partiql/partiql-tests); Rust reference impl Apache-2.0, "experimental" (https://docs.rs/crate/partiql/latest); Kotlin "preview" (license not read). Couchbase Server BSL 1.1 (https://www.couchbase.com/blog/couchbase-adopts-bsl-license/); AsterixDB Apache (not fetched).
**(iv)** DynamoDB (subset, https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ql-reference.html), Redshift SUPER (*unverified*), QLDB retired 31 Jul 2025. Agent use: **not checked**.
**(v)** Nested data first-class but no class model: no inheritance; associations are nested collections or explicit joins; result shape hand-built.
**(vi)** Full SQL (WHERE/ORDER BY/LIMIT/OFFSET/GROUP BY/subqueries/computed) plus `SELECT VALUE` object construction, UNPIVOT/PIVOT.

### 7. ISO GQL (brief)
ISO/IEC 39075:2024 (Apr 2024; Cor 1:2026 in progress), paywalled (~€376 BS edition, https://technickenormy.cz/en/bs-iso-iec-39075-2024-information-technology-database-languages-gql). RETURN yields a binding table (vendor doc, https://ultipa.com/docs/gql/binding-tables-and-working-tables); record/list value types exist but no shape/tree projection facet — *unverified against normative text*. Adds nothing over the existing Cypher island for object trees.

### 8. JPQL / JDQL / OQL / LINQ / Prisma / Drizzle (brief)
Jakarta Persistence 3.2 (EE 11) JPQL and Jakarta Data 1.0's JDQL (strict JPQL subset, https://jakarta.ee/specifications/data/1.0/) are being unified in Jakarta Query 1.0, still under development (https://jakarta.ee/specifications/query/1.0/); results are entity graphs via fetch joins, no JSON shaping, pagination is API-level; TCKs exist (licenses **not checked**). ODMG OQL: historic, spec is a book — **not checked**. LINQ: C#-embedded, no open spec. Prisma `findMany({where, include|select, orderBy, take, skip})` and Drizzle `db.query.firms.findMany({with:{employees:true}})` are JSON-object query APIs with enormous LLM familiarity — prisma 11.4M and drizzle-orm 17.8M npm downloads/week (api.npmjs.org, 2026-10-10..16) — but no spec and no corpus beyond their own tests.

### 9. Cube / Malloy (brief)
Cube's JSON query `{measures, dimensions, filters:[{member,operator,values}], timeDimensions, order, limit, offset}` returns **flat rows**; Cube Core Apache-2.0 backend / MIT client, 21k stars (https://github.com/cube-js/cube). Official Cube MCP server is Cube Cloud Premium/Enterprise only and exposes one natural-language `chat` tool, not the JSON query (https://docs.cube.dev/docs/integrations/mcp-server); community MCPs expose `execute_query`. Malloy: MIT, 2.6k stars (https://github.com/malloydata/malloy); `nest:` returns nested arrays per parent row with `limit` inside nests (https://docs.malloydata.dev/documentation/language/nesting); `malloydata/publisher` serves models over REST + MCP. Both are measure/dimension semantic models over joins, not class models.

### 10. Other emerging / adjacent
- JSONPath RFC 9535 (IETF 2024) with a BSD-2 compliance suite `cts.json` (https://github.com/jsonpath-standard/jsonpath-compliance-test-suite); JMESPath spec + JSON compliance tests (license not found, https://github.com/jmespath/jmespath.test; npm 4.9M/week); JSONata, jq — single-document transformers, usable only as a post-projection facet.
- OpenAI file-search attribute filter DSL `{type: eq|ne|gt|gte|lt|lte|in|nin, key, value}` + `{type: and|or, filters}` — a tiny, widely copied agent filter convention (https://developers.openai.com/api/docs/guides/retrieval).
- Open Semantic Interchange (Snowflake/Salesforce/dbt, 23 Sep 2025; v0.1 YAML spec; foundation governance promised, not delivered) — semantic-model exchange, not a query language (https://www.snowflake.com/en/blog/open-semantic-interchanges-specs-finalized/).
- LF DocumentDB is the only live "open standard" bid for a JSON query language (see §4).
- **Not checked:** Datomic Pull/EQL, JSON-LD framing, SPARQL JSON, Dgraph DQL, Google Vertex filter syntax, W3C/IETF object-query efforts.

**Headline:** OData is the only candidate that is simultaneously a ratified open standard, class-model-shaped (inheritance + associations + `$expand` trees), widely adopted by both humans and agent integrations, and expressive through `$apply`; its weakness is the oracle situation (Olingo retired; ODataLib .NET is the live reference, and there is no result-based conformance corpus, only ABNF test cases). ## D. Report: the agent side of choosing an object-query language (research agent, verbatim)

### 1. Empirical evidence on LLM query-generation accuracy by language

**SQL is the only language with mature, contested leaderboards.** BIRD's official board (fetched 2026-10-18) shows top test execution accuracy of 82.95% (GrainSQL, Sep 2026), 82.39% (Huawei DataGallery), 82.28% (Tencent); the single-trained-model track tops out at Gemini-SQL2 80.04%; human baseline 92.96% (https://bird-bench.github.io/). Spider 2.0 (enterprise warehouses, 1,000–3,000-column schemas, 100+ line solutions) is where it collapses: "GPT-4o's success rate is only 10.1% on Spider 2.0 tasks, compared to 86.6% on Spider 1.0"; today's agentic systems reach 76.23% on Lite and 65.6% on DBT (https://spider2-sql.github.io/). These are multi-step agent pipelines with execution feedback, not single-shot generation.

**Other languages, same-question comparisons:**
- **SM3-Text-to-Query (NeurIPS 2024)** is the only benchmark asking identical questions in four languages. With schema, 0-shot: "SQL performs best (best model: 47.05%), Cypher and MQL perform average (best models: 34.45% and 21.55%), while SPARQL performs worst (best model: 3.3%)". With BM25 5-shot retrieval SQL reaches 88.55% but "SPARQL, Cypher, and MQL cannot reach the same performance as SQL (MQL has the highest score with 78.70%)". Authors correlate this with Stack Overflow volume (SQL 673K posts, MongoDB 176K, Cypher 33K, SPARQL 6K) and explain MQL underperforming Cypher by verbosity: Cypher uses "only 25% of tokens and 50% of keywords" of the equivalent MQL (https://arxiv.org/pdf/2411.05521, extracted from the PDF).
- **TypeDB 2026 benchmark** (vendor-run, 39 questions, Claude Sonnet 5 / DeepSeek V4 Pro): unaided SQL 62.4%, Cypher 58.1%, TypeQL 24.8%; with a skill document + examples 82.1 / 74.4 / 75.2; with 4 retries TypeQL reaches 92.3% because the typed language "rejects most wrong queries before they run", whereas SQL/Cypher "run and return a wrong answer silently" (https://typedb.com/blog/benchmarking-llm-query-generation-across-sql-cypher-and-typeql).
- **Cypher:** CypherBench zero-shot EX: claude-3.5-sonnet 61.58%, gpt-4o 60.18%, best open model 41.87%; dominant errors are reversed relation direction, entity linking, pattern misalignment (https://arxiv.org/html/2412.18702v2).
- **GraphQL:** IBM's EMNLP-2024 Industry dataset (10,940 train / ~957 test); secondary summaries report zero-shot 0–10% and ~50% best with one example (https://research.ibm.com/publications/graphql-query-generation-a-large-training-and-benchmarking-dataset) — numbers UNVERIFIED against the paper. Text2GQL-Bench (ISO-GQL, not GraphQL): ≤4% zero-shot, ~50% 3-shot (https://arxiv.org/abs/2602.11745).
- **MongoDB:** TEND (1,210 tasks, nested docs) (https://arxiv.org/pdf/2502.11201); EvoMQL reports GPT-5 ~0.59 and Gemini-3-pro up to ~0.90 on different splits (https://arxiv.org/pdf/2604.13045) — metric definitions UNVERIFIED.
- **ES|QL (Elastic, BIRD questions re-targeted):** gpt-5.5 59.0% single-shot with only mappings; parse failures 7/500; a compact language reference adds ~9–10 points for weaker models and *subtracts* 10 for the strongest (https://www.elastic.co/search-labs/blog/text-to-esql-benchmark).
- **SPARQL:** DBpedia-2025 researcher agent best 0.22 (https://arxiv.org/pdf/2608.07700, UNVERIFIED).
- **OData:** OmniOData (ACL 2026 Industry) calls it "under-researched" and trains 1.5–3B models on synthetic execution-grounded data to match GPT-4o (https://researchr.org/publication/BaiLSD26).

**Verdict:** reliability tracks pretraining exposure, not typedness. No evidence that a JSON-shaped language is *easier*; SM3's MQL result points the other way (verbosity hurts). Evidence for "typed + introspectable" is indirect: schema in the prompt roughly doubles accuracy for private schemas (SM3), and a compiler that rejects wrong queries makes retry loops pay off (TypeDB).

### 2. What interface shape the agent ecosystem is converging on

- **Protocol:** MCP tools are `name` + `description` + `inputSchema` (JSON Schema); since 2025-06-18 also `outputSchema`/`structuredContent` (https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
- **Anthropic guidance:** "More tools don't always lead to better outcomes"; consolidate low-level calls into task-level tools; prefer search over list; "enforcing with strict data models" and enums (https://www.anthropic.com/engineering/writing-tools-for-agents). 58 tools ≈ 55K tokens before the first turn; Tool Search raised Opus 4.5 MCP-eval accuracy 79.5→88.1%; tool-use examples raised complex-parameter accuracy 72→90% (https://www.anthropic.com/engineering/advanced-tool-use). Code-execution-with-MCP: agents write code against servers, 150K→2K tokens (https://www.anthropic.com/engineering/code-execution-with-mcp). Skills: progressive disclosure of `SKILL.md` plus reference docs and scripts (https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills).
- **OpenAI guidance:** "Aim for fewer than 20 functions"; "We recommend always enabling strict mode"; defer via tool search (https://developers.openai.com/api/docs/guides/function-calling); structured outputs support recursive schemas (https://developers.openai.com/api/docs/guides/structured-outputs); ChatGPT deep-research connectors accept only `search` + `fetch` (https://developers.openai.com/api/docs/guides/deep-research.md).
- **What vendors actually expose:**
  - *One query-string tool + schema tool + read-only guard:* Supabase `list_tables`/`execute_sql` with read-only mode (https://github.com/supabase/mcp); Neo4j `get-schema`/`read-cypher`/`write-cypher` (https://hub.docker.com/mcp/server/neo4j-cypher/tools); Google BigQuery MCP `execute_sql_readonly` — "Prefer this tool over execute_sql" (https://docs.cloud.google.com/bigquery/docs/reference/mcp); Anthropic's archived reference Postgres server: single `query` tool, "Run a read-only SQL query" (https://hub.docker.com/mcp/server/postgres/overview); Datadog moved from retrieval tools to SQL over logs, runs "about 40% cheaper" (https://www.datadoghq.com/blog/engineering/mcp-server-agent-tools/).
  - *JSON query object:* MongoDB `find`/`aggregate` with JSON filter/pipeline, `readOnly`, `indexCheck` (https://github.com/mongodb-js/mongodb-mcp-server).
  - *Generic API gateway + search:* Stripe `stripe_api_search/details/read/write` plus NL→SQL `stripe_analytics`, "without increasing the context window unnecessarily" (https://docs.stripe.com/mcp); GitHub toolsets/dynamic toolsets to "avoid situations where the model gets confused by the sheer number of tools" (https://pkg.go.dev/github.com/github/github-mcp-server).
  - *GraphQL:* Apollo offers three patterns — saved operations as tools, persisted queries, or `introspect`/`search`/`validate`/`execute` where "Agents can construct arbitrary queries" and `validate` lets them "iterate on query construction without making costly API calls" (https://www.apollographql.com/blog/connect-ai-agents-to-your-graphql-api-using-mcp-and-type-safe-tool-configuration). Shopify's Storefront MCP is narrow typed tools (`search_catalog`, `get_product_details`, `get_cart`, `update_cart`), not GraphQL (https://shopify.dev/docs/apps/build/storefront-mcp/servers/storefront); its Dev MCP validates GraphQL against schemas (https://shopify.dev/docs/apps/build/devmcp).
  - *RAG over curated calls:* Microsoft Graph MCP for Enterprise: `microsoft_graph_suggest_queries` (semantic index of example OData calls) → LLM picks `GET /users/$count` → `microsoft_graph_get`, plus `microsoft_graph_list_properties` (https://learn.microsoft.com/graph/mcp-server/overview).
  - *Code generation:* Hasura PromptQL — "PromptQL programs are Python programs" generated by LLMs, executed deterministically, artifacts kept out of context (https://promptql.hasura.io/spec, via search summary).

### 3. Textual language vs JSON query object

No controlled head-to-head exists. Indirect evidence: (a) SM3's MQL-vs-Cypher verbosity finding above; (b) Elastic replaced Query-DSL + Python post-processing (Text-to-ES Bench, https://aclanthology.org/2025.acl-long.971) with textual ES|QL because `LOOKUP JOIN` "lets the model join inside a single query" (https://www.elastic.co/search-labs/blog/text-to-esql-benchmark); (c) the format-restriction debate: "Let Me Speak Freely" found strict JSON hurts reasoning (https://arxiv.org/abs/2408.02442) but dottxt's prompt-controlled rerun found structured ≥ unstructured (GSM8K 0.78 vs 0.77) (https://blog.dottxt.ai/say-what-you-mean.html) — so JSON output per se is fine; the cost is that a JSON *query dialect* has no pretraining. Practitioners split: a Neo4j-affiliated post argues "with today's models, the flexible tool wins" (https://towardsdatascience.com/one-flexible-tool-beats-a-hundred-dedicated-ones — 403 on fetch, summarized from search results); Bonnard argues narrow tools plus a schema-discovery step (https://dev.to/maxbonnard/how-bonnard-builds-agent-friendly-mcps-n4i). Market behaviour: every database vendor above passes text SQL/Cypher in a string; only MongoDB passes JSON, because that *is* its native language.

### 4. Semantic layer for agents

Three query shapes coexist, none standardized:
- **NL in, vendor SQL out:** Snowflake Cortex Analyst (REST `messages`, returns `sql`; semantic view "used only for SQL-query generation") (https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst); Databricks Genie Conversation API returns "generated SQL, query results, and visualizations" (https://docs.databricks.com/aws/en/genie/conversation-api); Google Conversational Analytics API (NL, "authored context", returns SQL artifacts) (https://docs.cloud.google.com/gemini/docs/conversational-analytics-api/overview); Fabric data agents do NL2SQL/NL2DAX/NL2KQL per source (https://learn.microsoft.com/en-us/fabric/data-science/concept-data-agent).
- **Metric-query JSON:** dbt MCP `list_metrics`/`get_dimensions`/`get_entities`/`query_metrics`/`get_metrics_compiled_sql` (https://glama.ai/mcp/servers/@dbt-labs/dbt-mcp/tree); Cube (`/v1/load` with measures/dimensions/filters; "the agent asks for certified metrics and dimensions instead of inventing SQL") (https://cube.dev/articles/analytics-mcp-server); AtScale list/describe/run-query (https://www.atscale.com/blog/enterprise-ai-mcp-semantic-layer/); Looker toolbox `query` over LookML with fields/filters (tool shapes UNVERIFIED) (https://docs.cloud.google.com/looker/docs/2514/connect-ide-to-looker-using-mcp-toolbox); Malloy Publisher MCP (https://docs.malloydata.dev/documentation/user_guides/publishing/mcp_agents).
- **SQL with semantic constructs:** Snowflake `SELECT … FROM SEMANTIC_VIEW(v METRICS … DIMENSIONS …)` (https://docs.snowflake.com/en/sql-reference/constructs/semantic_view).

**OSI:** announced Sep 2025 (Snowflake, Salesforce, dbt, BlackRock, RelationalAI); v1 published 27 Jan 2026 as YAML/JSON covering "data sets, metrics, dimensions, relationships, and contexts"; Databricks, AtScale, Qlik joined; **no query interface** — model definitions only (https://www.snowflake.com/en/blog/open-semantic-interchanges-specs-finalized/, https://github.com/open-semantic-interchange/OSI); now renamed Apache Ossie (https://ossie.apache.org/updates/osi-april-2026-community-update/).

### 5. Google / Anthropic / OpenAI / Microsoft positions

No vendor has published "agents should speak language X". Revealed preferences: **Google** — raw SQL (read-only preferred) for BigQuery; narrow typed tools for Data Commons (`search_indicators`, `get_observations`, …) (https://docs.datacommons.org/mcp/); NL for Conversational Analytics. **Anthropic** — general tool-design guidance only; its reference DB server used one SQL `query` tool. **OpenAI** — connectors are `search`/`fetch`; <20 tools; strict schemas. **Microsoft** — RAG over curated REST/OData examples for Graph, NL→native language for Fabric. A $200M Anthropic–Snowflake deal is reported by secondary sources only (https://vantagepoint.io/blog/ai/claude-data-platform-connectors-snowflake-databricks, UNVERIFIED).

### Implications for choosing an agent-friendly object query language

- **Surface syntax should borrow SQL/GraphQL spelling.** Zero-shot accuracy tracks pretraining volume (SQL 47% vs SPARQL 3% on identical questions); a novel syntax starts near zero and only recovers with a skill doc + examples (TypeQL 25→75%). Ship the language reference as a Skill and a few-shot set *with* the tool.
- **Expose 3–4 tools, not many:** `describe_schema`/`search_schema`, `validate`, `query` (read-only, paginated/truncated), optionally `explain`. This is the Supabase/Neo4j/BigQuery/Apollo shape and matches Anthropic's and OpenAI's guidance.
- **Validation before execution is the biggest accuracy lever** (TypeDB's retries, Apollo's `validate`, Shopify's validator). Legend-lite's typed compiler with its eight `LegendCompileException` phases is exactly the asset to expose — make compile errors actionable text.
- **Text in a string beats a JSON query object**, absent evidence to the contrary: verbose JSON dialects underperform (MQL), and every SQL/Cypher/GraphQL vendor passes text. A JSON AST is still worth offering as a validated interchange form (MCP args are JSON; strict/recursive schemas can constrain it).
- **Results should be nested JSON trees with named fields**, and the language should let agents ask for named metrics/dimensions over a governed model (the semantic-layer trend; OSI/Ossie as a model-export target, since no query standard exists to adopt).

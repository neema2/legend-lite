Two facts that frame everything below:

* `PlanMaker.plan` (non-writing) plans ONE expression: `TypedQuery.resolve` inlines the whole body with
  `UserCallInliner.inlineBody`, which refuses any non-let statement before the last
  (`compiler/spec/UserCallInliner.java:204-207`: "only let statements may precede the query expression"). So a
  body with an assert, an effect or a value statement before its last statement can only reach the product road through
  `PlanMaker.program`, and `program` is chosen only when `query.writes()` (PlanMaker.java:57).
* The test road never calls `TypedQuery.lower/lowerer/plan` or `PlanMaker.plan/program`. It calls only these
  PlanMaker helpers: `PlanMaker.sql` (JudgePlans.java:139, 530, 557), `PlanMaker.rowsOrGridKeyed`
  (JudgePlans.java:112), `PlanMaker.keyed` (JudgePlans.java:154, 573), `PlanMaker.serversFor` (JudgePlans.java:71),
  `PlanMaker.readsGridReport` (JudgePlans.java:342). Every other planning step is its own.

## 2. DIFFERENCES: where the test road plans differently from PlanMaker.plan/program

Effect column: TEXT = the SQL text of a statement changes; NUM/ORDER = the number or the order of statements changes;
JAVA = only what Java does with rows (or a value Java holds) changes. Class column: see section 3 ((a) product feature
the product lacks; (b) database-judge assert semantic; (c) host-judge comparison rule; (d) optimization; (e)
unclear/historical; T = an explicit test-only construct, kept but to be named).

**Where it is composed.** At a segment's close: `BodyCompiler.Segments.closeVerdicts` (driver/BodyCompiler.java:340-357)
runs the segment's queued value statements first (:341-345), then `AssertVerdicts.flush` (driver/AssertVerdicts.java:138-140)
-> `VerdictBatch.flush` (judge/VerdictBatch.java:285-429). The batch is made per segment by `BodyDriver.newVerdictBatch`
(driver/BodyDriver.java:245-248) with three things the driver supplies:

* the FUSION `com.legend.lowering.VerdictSql::batch` (lowering/VerdictSql.java:1048-1094);
* the JUDGE `DatabaseJudge::verdictOf` (driver/DatabaseJudge.java:227-258);
* the RUNNER `JudgePlans.runner(env)` (driver/JudgePlans.java:331-349): `plan(statement, fused)` = `rowsPlan(statement,
  fused ? VerdictSql.batchSchema() : VerdictSql.schema(), env)` -> `PlanMaker.rowsOrGridKeyed` (a typed RELATION, or a
  Keyed one when the statement reads a raw grid's report); `keyed(statement)` = `PlanMaker.readsGridReport`;
  `chars(statement)` = the rendered length (a census).

A new batch opens for the next segment (BodyCompiler.java:354-356). A segment is closed by an effect statement
(:120-123), a test-data generator statement (:107-110) or the body's end (:205-206). Under HOST and BOTH modes there is
no batch (BodyCompiler.java:246; `AssertVerdicts.databaseMode`, :779-781).

**What goes into it.** Each statement-root assert opens a Root (`batch.open`, AssertVerdicts.java:108); its arm plans
both sides (R8: identity lane, canon-wrapped, frames referenced as `frame_<let>`), composes ONE verdict statement per
check with `VerdictSql` (answering `__verdict, __expected, __actual, __unjudged, __lenient`, VerdictSql.java:1179-1191)
and `defer`s it with the session it must run on and an optional APPEAL (VerdictBatch.java:210-226). A static outcome
(a kind gate, a static column mismatch) or a planning-time UNJUDGED is a `Resolved` step
(`batch.resolve(deferred)`, AssertVerdicts.java:125-128). A wall discards the open root and flushes what came before
(:117-121).

**Composition at the flush** (VerdictBatch.java:295-382):

1. Pending statements grouped by session (`Pending.on`): one fused statement per session (:295-302).
2. Members whose statement (with the batch's frames attached) reads a raw grid's report are a group of their own, each
   with its own keyed wrapper, run as `Verdicts(verdicts-with-wrappers, fused=null)` (`keyedGroup`, :440-481).
3. The rest: `fusion.fuse(queries, frames)` = `VerdictSql.batch` -- the FRAMES the members reference as MATERIALIZED
   CTEs first (:1053-1063), each member's own CTEs hoisted to ONE top-level WITH and renamed `<name>_<i>` (identical
   CTE bodies after renaming hoisted once, :1064-1085), each member's row a `UNION ALL` branch carrying its index
   `__ix` (`indexed`/`derived`, :1100-1135). Planned by `runner.plan(..., true)` (`typed` requires a TdsResult, :484-490).
4. The plan value: `ExecutionPlan.Verdicts(verdicts, fusedPlan)` where each `ExecutionPlan.Verdict(name, armOf(name),
   wantEqual, base=List.of(), wrapper=null)` (:349-353) -- the members carry NO base sides and NO wrapper.
5. Run: `PlanRunner.program(new ExecutionPlan(List.of(), group), ..., Judging.DATABASE, sink)` under the BODY origin
   with the body's trace (:375-381); the runner maps rows by `__ix` (exec/PlanRunner.java:326-343).

**The split rung.** Two places:

* at PLANNING: a `DialectCapability` while planning the fused statement -> `spelled(...)` plans each member fused alone
  (:494-505); the spellable members are fused again; the others are left to their place in the root loop; if nothing
  fuses, `fallback(e)` is counted and the group skipped (:323-347).
* at RUN: the database rejects the fused statement -> the runner calls `sink.fused(group, e)` and clears the rows
  (PlanRunner.java:344-350); as the members have no wrapper, the runner hands `verdict(each, null)`; the batch counts
  it (`fallback`, :361-364). The root loop (:383-428) then runs every member whose row is missing by
  `VerdictBatch.executeOne` (:520-557): `runner.plan(FrameCtes.attach(query, frames), false)` as a one-verdict group
  under the FALLBACK origin, a `DialectCapability` or `DataError` counted UNJUDGED with the database's words and
  re-raised.

**Appeals.** `Pending.appeal` is consulted only when the judged row FAILED (:396-405); today the SQL-text arms supply it:
the row is `VerdictSql.textEquals(golden, ours)` and the appeal is the rows leg plus the referee replay
(SqlTextVerdicts.java:1360-1373, 1015, 1690).

**Unjudged reasons.** Three sources:

## 5. COVERAGE: where PlanMaker.plan/program would refuse or mis-plan a test-body kind

Gate facts first:

* `PlanMaker.plan` takes `program` only when `query.writes()` (PlanMaker.java:57; TypedQuery.java:189-198: a store
  write, or a staged let). Any other multi-statement body goes to `query.lower` -> `TypedQuery.resolve` ->
  `UserCallInliner.inlineBody`, which REFUSES every non-let statement before the last:
  `throw new NotImplementedException("only let statements may precede the query expression")`
  (compiler/spec/UserCallInliner.java:204-207). That covers every body with an assert, an effect or a value statement
  that is not its last.
* `PlanMaker` emits only `Sequence`, `Update`, `Check`, `TdsResult`, `Keyed` (PlanMaker.java:60-173, 252-343). It never
  emits `Effect` or `Verdicts` (grep: `new ExecutionPlan.Effect` only at BodyDriver.java:972, PlanRunner.java:473,
  TestDataGenerator.java:509; `new ExecutionPlan.Verdicts` only at HostSides.java:78 and VerdictBatch.java:353, 458,
  530).
* `PlanRunner.program` refuses more than one result step (exec/PlanRunner.java:227-230) and steps naming different
  targets (:218-224) -- a body's statements on the system route and on the user session cannot be one program.

## 7. Findings worth a decision (from the reading above)

1. The test road shares almost nothing with `PlanMaker.plan/program`: its own Lowerer configuration
   (`BodyPlanner.lowererFor`), its own resolver, its own target (`JudgePlans.target`), and five PlanMaker helpers.
   The product road cannot plan a test body at all: a read-only multi-statement body is refused by the inliner
   (UserCallInliner.java:204-207), and `program` emits no `Effect` or `Verdicts`.
2. Most Lowerer differences are product features the product road lacks (D4, D6, D9, D10, D13, D14, D15, D16), read
   from a from()/execute context the product road never reads. One is unexplained: the exists-join form is always on
   for test bodies and off for temporal reads in the product (D5).
3. The database judge's sides are always on the identity lane (`__id`, `__type`, `__canon`, per-node ids from one
   body-wide minter; D1, D2, D20), so a database-judge side is NOT the product's statement plus a wrapper: its inner
   SQL differs too.
4. DATABASE mode reorders statements: a segment's value statements, including store writes and the streamed last
   answer, run before the segment's fused verdict statement (D33). Because a store write does not close a segment,
   an assert written before a write in one segment is judged on the post-write state (whether the corpus has such a
   body is unverified).
5. Three host fallbacks run inside the database judge: the grid-pair arm, class-instance `assertEq`, and the engine-text
   asserts' sides (D43). They run at the assert, outside the fused statement.
6. Values computed by the database feed later planning in three places: the test-data generator (D38), computed
   effect arguments (D39), and an eager `execute(...)` met while inlining another statement (D15). A plan made before
   anything runs cannot hold these without a step whose rows fill a later statement.
7. A value side is planned with the RELATION shape and then trimmed in Java (D27). The product's VALUE shape may make
   the trim unnecessary (unverified).
8. Stale or dead: the "wire reconciliation" comments (D21), `BodyDriver.evalValue` (no caller), two unjudged reason
   texts that say "AssertVerdicts.side" (DatabaseJudge.java:116-117, :298), and the JudgePlans javadoc that names a
   "two-branch if" calling `evalSide` (JudgePlans.java:438): no such caller exists (the only callers are in
   SqlTextVerdicts).

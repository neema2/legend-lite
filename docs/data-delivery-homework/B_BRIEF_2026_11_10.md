## 9. Decisions for the user

1. **The generator's empty starting set: RULED (the user, 2026-11-10, "1&2 yes"):** follow upstream: an empty seed is no
   filter, so the root fetch takes its 20 rows unfiltered.
2. **The generator's row order: RULED ("1&2 yes"):** every level ordered by its key (all columns where there is none), so
   the one statement picks the same rows throughout; upstream is unordered: a register row.
3. **The generator's output: RULED (the user, 2026-11-10, "Yes"): faithful to the real data, line breaks included.**
   Every value is written exactly: a value holding a comma, a double quote or a line break is a quoted cell (RFC 4180:
   `""` is one quote), a single quote as is; nothing replaced, nothing lost (upstream's Pure writer replaces `'` with a
   space, `,` with `;` and a line break with a space). For that, lite's test-data reader (`CsvSeed`, which today splits
   on line breaks before reading quotes, `CsvSeed.java:151, :168`) reads records with the same quote-aware record reader
   the file loads use (`base/CsvCells` rules: a quoted cell keeps its line breaks), at planning. Upstream's layout is
   kept otherwise (columns sorted by name, tables in fetch order, `---null---`, `-----`). Check in B2d whether upstream's
   engine reader takes a quoted line break in test data: if not, lite's reader is a strict extension (everything
   upstream accepts reads the same): a register row. The `assertTestData` goldens differ only where the data holds those
   characters: counted when built, a register row.
4. **The generator's reload checks: RULED (the user, 2026-11-10, "4 yes"):** planned as SQL, the slice's tables made
   from the generator's own queries, never the generated text parsed in Java.

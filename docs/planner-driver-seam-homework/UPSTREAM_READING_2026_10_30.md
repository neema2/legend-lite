**Precise statement:** upstream never executes a test body as a plan. ## 6. Does planning ever need the database?

- Plan generation is pure Pure over the model: `CPURE/executionPlan/executionPlan_generation.pure` and `CPURE/platform/executionPlan/executionPlan_generation.pure` contain **zero** calls to `executeInDb`/`fetchDb*` (counted: `0` and `0`); `RPURE/pureToSQLQuery/pureToSQLQuery.pure` (the SQL generator, ~11k lines) contains **zero**; `RPURE/sqlQueryToString/dbExtension.pure` contains **zero**. The only two `executeInDb` calls in `RPURE/relationalMappingExecution.pure` are at `:492` (`executeQuery`, the Pure-runtime execution path used when Pure itself runs the query, not plan generation) and `:761` (a key-lookup helper on the same execution path).
- The Java planner is a thin wrapper that only calls those Pure functions and then transforms the Pure plan to protocol: `ENGINE/.../plan/generation/PlanGenerator.java:64-72, 75, 119-126, 145-153`; it takes a `PureModel`, mapping, runtime and extensions — no connection, no `PlanExecutor`.
- The one shape the planner cannot know, the dynamic pivot's column set, is **not probed at planning**: the planner emits `columns = []` ("force a `select *`", `RPURE/pureToSQLQuery/pureToSQLQuery.pure:6481-6484`) and a flag (`isResultColumnsDynamic`, `RPURE/relationalMappingExecution.pure:247`), and the **executor** fills the columns from `ResultSetMetaData` (`REXEC/result/SQLExecutionResult.java:95-105`, `REXEC/result/RelationalResult.java:243-256`).
- Likewise values bound by `let` are not read at planning: a later statement is planned against a `PlanVarPlaceHolder`/`PlanSetPlaceHolder` that carries only name, type/multiplicity or `tdsColumns` (`CPURE/executionPlan/executionPlan_generation.pure:186-191`), and the SQL carries `${var}` holes (`RPURE/sqlQueryToString/dbExtension.pure:624-626`) resolved by FreeMarker at execution (`EXEC/nodes/helpers/freemarker/FreeMarkerExecutor.java:61-88`; `REXEC/RelationalExecutor.java:334`).
- Conditionals that depend on run-time values (the `in` list size, whether a variable is a stream) are planned as `FreeMarkerConditionalExecutionNode`s with both branches present (`RPURE/postprocessor/defaultPostProcessor/processInOperation.pure:177-182`) and decided by the executor (`EXEC/nodes/ExecutionNodeExecutor.java:314-332`).
- Service plans whose shape depends on a parameter are `CompositeExecutionPlan`s: all keyed plans are generated up front and the executor picks one by the parameter value (`PROTO/CompositeExecutionPlan.java:48-73`; `ServiceTestRunner.java:453-456, 540-551`).
- The database is therefore reached only through the executor's `RelationalExecutor` (`REXEC/RelationalExecutor.java:236` `getConnection`, `:87` of `SQLExecutionResult.java` `executeQuery`) or, outside the plan path, through the Pure runtime native `executeInDb` (section 5).

**What this means for lite (reading of upstream):** in upstream the planner never opens a connection, never reads metadata and never evaluates a value; every run-time-dependent decision (a variable's value, a dynamic pivot's columns, a size-dependent temp-table choice, a parameter-keyed plan) is carried into the plan as a hole, a flag, a conditional node or a keyed set of plans, and resolved by the executor against the state or the database.

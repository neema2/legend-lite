## 0. What this product is, and where it lives

**The goal**, as set at the start: rewrite FINOS Legend **DataCube**
from scratch to be bulletproof and extremely fast, running against
**legend-lite**, in **both server and cached-client modes**, and
**backwards compatible with legend-engine**. Clean-room: behaviour is
matched by reading legend-studio's source, never by copying it.

**Standing constraint from the user: do not commit to `main`.**

  no overlap, in-bounds, full coverage.

## 5. Recommended order (unbiased ranking)

1. **Land or revert the pending engine work.** Only real *risk* here.
2. **Differential tests vs legend-engine.** The compatibility claim has
   ZERO evidence. Newly feasible — legend-engine is cloned at
   `~/legend/legend-engine`, and the type census below says exactly
   where they would disagree. The project's own census has called this
   the largest gap since before this work started.
3. **Instrumentation.** "Extremely fast" has no numbers, and an hour
   was spent debating caching on intuition (wrongly, at least once).
   Measure plan vs execute vs materialise.
4. **Cheap residuals**, each an hour or two, all zero-risk:
   - **Plan-cache LRU.** `planner.ts:56` is a plain `Map` keyed by
     grammar text, never evicted — an unbounded leak in a long session.
   - **Predicted refusals.** The context menu offers Group/Sort/Pivot
     on columns we KNOW the engine rejects (the quoted-identifier bugs
     in §6). It fires a query that 500s instead of greying the item
     out with a reason. The disabled-with-a-reason pattern already
     exists — see Undo/Redo and the Email entries.
   - **DOM recycling.** `grid.ts#render` calls `createElement` for
     every row and cell each frame. Scroll is already rAF-coalesced
     and `translateY`-positioned with an `isCovered` short-circuit, so
     this only bites WIDE cubes (20 rows x 200 cols is ~4,000 nodes a
     frame). Pool and mutate `textContent`.
   - **Autosave.** `persist.ts` has `save()` but nothing calls it
     automatically; a tab crash loses a built cube. Debounced write,
     restore on load.
   - **The BIT fix** (§6), once the corpus gates can run.
5. **Schema inference** (see §7). Good design, convenience not urgency.
6. **Server plane.** Needs a planner seam and warehouse dialects;
   should follow the compatibility proof.

## 6. Known defects

### In legend-lite (tracked, not fixed)

Seven, one root cause, listed in `demo/torture.mjs` as
`KNOWN_ENGINE_BUGS` — the suite reports them and **fails if one starts
passing**, so a note cannot outlive the bug. A column DECLARED with
quotes in the Database grammar (`"with space"`, `"quo'te"`,
`"Ünïcødé"`, `"select"`) resolves through `select`, `filter` and
`extend`, and fails through `groupBy`, `sort` and `pivot` — the three
paths that ISOLATE the table scan before resolving. The first two raise
`IllegalStateException`; pivot dereferences null.

Reproduce:
`#>{torture::DB.WEIRD}#->groupBy(~['with space'], ~[m:x|$x.n_float:y|$y->sum()])`

### BIT type disagreement (recorded, deliberately not fixed)

`StoreCompiler` says BOOLEAN, `PreciseTypes` says TinyInt. **Upstream
says BOOLEAN**, in four places (`pureToRelational.pure:56`,
`relationalExtension.pure:146`, `databaseHelperFunctions.pure:202`,
`relationalToPure.pure:214`); the only `Bit → TINYINT` upstream is
COMMENTED OUT in the H2 extension as a workaround. So `PreciseTypes` is
wrong. Not fixed because `pureType` feeds the PLAN PROTOCOL and the
corpus gates could not be run. Needs a `Boolean → "BIT"` arm in
`defaultSpelling`, which currently throws.

### Type-mapping duplication

**Eight sites in core** know the SQL↔Pure correspondence, in different
directions and granularities — which is why they drift instead of being
deduplicated:

```
DatabaseProtocolParser:396   grammar token -> protocol name
RelationalDataType:140       string        -> typed Varchar(n)
StoreCompiler.columnType:246 RelationalDataType -> Pure primitive
PreciseTypes.pureType        RelationalDataType -> precise Pure FQN
PreciseTypes.defaultSpelling Pure          -> SQL DDL spelling
SqlTypeCensus:592            string        -> SqlType.Scalar
RelOpTranslator:183          SQL name      -> Pure name
Executor:960                 JDBC name     -> runtime value
```

Plus `duckdb.ts` (`typeName`, `converterFor`) and `remote.ts`
(`inferType`) on the TS side. It has already cost a bug: DECIMAL once
answered Float in one path while the column-kind table said Decimal
(audit 2026-09-15 P3-5). `TypeMappingAgreementTest` now guards this.

## 7. legend-engine findings (verified, not inferred)

Recorded because they took real digging and I got them wrong three
times before grepping for construction sites.

**`TabularFunction` can only be called with ZERO arguments.** Grammar
(`RelationalParserGrammar.g4:154`) accepts `columnDefinition` only;
the protocol class carries a literal `//TODO params ?` and has no
field; introspection sets columns only. The metamodel DOES declare
`parameters : FunctionParameter[*]` and four dialect processors take
it — but **nothing anywhere constructs one**. The single construction
in the repo is `^TabularFunction(schema=…, name='ID')`.

**UDTF generation is unrelated.** SnowflakeApp / MemSqlFunction
activation emits `CREATE OR REPLACE SECURE FUNCTION …(params) RETURNS
TABLE (…)` as **templated DDL text**; it never builds a
`TabularFunction`. So Legend can CREATE a parameterised UDTF and
cannot CALL one.

**Consequence:** `read_parquet('s3://…')` from a model is a NEW
capability, not a gap to fill. The upstream-compatible pattern is a
zero-arg function whose body lives in the warehouse
(`CREATE MACRO T() AS TABLE SELECT * FROM read_parquet(...)`), which is
the same logical/physical split as a view.

**Schema introspection IS a first-class upstream feature**, and
deliberately NOT part of plan: `SchemaExportation` lives in the
*execution* module, `SchemaExplorationApi` is its own HTTP endpoint.
The REPL composes `load <path> <conn> <table>` (file → table) with
`db` (introspect → `Database`). Note it does **not** infer a Store from
a file — it materialises the file into a table first, so there is ONE
inference path.

**lite already has the raw material**: `fetchDbSchemasMetaData`,
`fetchDbTablesMetaData`, `fetchDbColumnsMetaData`,
`fetchDbPrimaryKeysMetaData` natives, composed by `CatalogGrids` as SQL
over `information_schema` with JDBC `DatabaseMetaData` column names. So
introspection would be: run the existing grids through `QueryService`,
convert rows → `Database` **via `RelationalDataType`** (so no ninth type
mapping), expose as `/engine/introspect` beside `/engine/execute`.

**Why `plan` needs no Connection but still picks a dialect:** two
meanings of "Connection". `dialectOf(ctx, runtimeFqn)` reads the
Runtime ELEMENT → Connection ELEMENT → `type: DuckDB` from the model
text. No socket. A second overload takes a `java.sql.Connection` and
probes the live product, used at execution to reconcile H2 versions.

## 8. Architecture notes a newcomer will need

- **One planner, no fallback.** legend-lite compiles snapshot → Pure →
  SQL. A guardrail test asserts `Planner` is implemented in exactly one
  shipped file. Injecting a stub in a test is fine; runtime selection
  is banned.
- **Reachability guardrail.** `src/app.ts` must import and CALL each
  module. Phase 6 shipped features no user could reach; this exists so
  it cannot recur.
- **`CubeRefusal`** distinguishes "your cube is not a question" from
  "we have a bug".
- **Epoch discipline** keeps answers correct; **cancellation** keeps it
  fast. Both are needed — an HTTP response already on the wire cannot
  be stopped.
- **Pivot separator `__|__`** is OUR delimiter appearing in THEIR data.
  Never infer arity by counting it.
- **A convenience constructor that defaults a new record field silently
  drops it at every rebuild site.** This bit twice in one change
  (`NameResolver.resolveDatabase`, `TypedTableReference.withInfo`).
  When adding a field, grep every construction AND every `with*`.

## 9. legend-lite in WASM — MEASURED, and it looks tractable

Investigated 2026-09-20. Numbers, not opinions.

### The planner needs java.base ALONE — proved at runtime

`jdeps` on the whole core reports three modules: `java.base`,
`java.sql`, `jdk.httpserver`. Restricted to the planner packages
(`parser`, `lexer`, `compiler`, `normalizer`, `resolver`, `lowering`,
`sql`, `model`, `protocol`, `values`, `builtin`, `error`, `plan`) it
reports **`java.base` only**.

Then proved dynamically: the full pipeline — parse, type, resolve,
lower, render — run under `--limit-modules java.base`, one module
visible, `java.sql` absent, producing correct SQL.

**ONE LINE was in the way, and it was not an obvious one.** A
`catch (java.sql.SQLException)` in `Compiler.metadata` made the whole
class unloadable without the module, PLAN SURFACE INCLUDED, because
the JVM verifier resolves catch-clause types at LINK time. A JDBC type
in a method *descriptor* resolves lazily and is harmless. The body
moved to `com.legend.exec.JdbcMetadata` — where `Compiler`'s own
comment already said the boundary was — and the property is now
guarded by `PlannerNeedsOnlyJavaBaseTest`.

### The numbers

| | |
|---|---|
| planner closure | **1,505 classes, 9.2 MB** bytecode |
| everything else | 198 classes, 1.3 MB |
| cold plan (classload + prelude) | **359 ms** |
| warm plan p50 / p95 | **1.38 ms / 2.55 ms** |
| `prelude.pure` parsed at startup | 293 KB, 7,009 lines |

Warm planning at 1.4ms **beats an HTTP round trip to localhost**. That
is the whole argument for the port: not "it would be neat", but that a
WASM planner plus the DuckDB-WASM already in the page is a completely
offline cached-client plane, with per-interaction latency BELOW what
the network costs today.

### Reflection and the other hazards — censused

**Reflection is already zero and banned**, with a pin of ZERO in
`CodeShapeGuardrailTest` and the ban stated in `Json.java`. The only
two grep hits were a method *named* `newInstance` and comments
describing the ban. Also zero: JNI/native, charset defaults,
wall-clock/random in the planner, `ProcessBuilder`.

Real hazards remaining in the planner closure — four, all small:

| Site | Issue | Fix |
|---|---|---|
| `parser/SectionGrammarRegistry:113` | genuine `ServiceLoader` for extension grammars | static registration |
| `builtin/Prelude:42` | `getResourceAsStream("/…/prelude.pure")` | bundle, or inline as a constant |
| `sql/dialect/DuckDb:217` | `java.nio.file` + `java.net.URI` | only `sourceUrl`'s `file:` scheme; `data:` unaffected |
| one site | `ZoneId.of(zone)` | pulls the tz database — payload, not correctness |

Everything else was a false positive: `System.getProperty` across 11
files is exactly two debug flags (`legend.mapping.trace`,
`legend.spec.trace`); the "threads" hits are `synchronized
fillInStackTrace()` and `Thread.dumpStack()` with **no thread ever
spawned**; `ConcurrentHashMap` is a cache with no concurrency behind
it; `\bCalendar\b` was matching the fiscal-calendar class
`CalendarAgg`.

### What to worry about, ranked

1. **Payload.** 9.2 MB of bytecode, tree-shaken, next to duckdb-wasm.
   This is the gate, not JDBC.
2. **Java 21 language level.** Records, sealed interfaces, pattern
   switch and GUARDED patterns (`case X t when …`) are used
   throughout. GraalVM handles them; **TeaVM's Java 21 support is the
   open question**, and TeaVM is the toolchain most likely to win on
   size.
3. **Cold start.** 359 ms on a JVM, much of it JIT warmup (which AOT
   removes) plus parsing 7,009 lines of prelude. The boot layer is
   already "normalized ONCE per process, content-addressed by the hash
   of its Pure source" — so **pre-baking the boot layer at build time
   is the obvious cold-start fix** and probably the single highest-value
   follow-up.
4. **Exceptions as control flow.** `UnfoldableRef` drives the
   isolate-or-loud resolution strategy; typing throws routinely. Works,
   but stack-trace machinery is a known WASM cost.
5. **Regex**, used in spellings and messages — heavy in WASM runtimes.

### Next steps

1. **Pre-bake the boot layer** — kills most of the 359 ms and removes
   the `getResourceAsStream` hazard at the same time.
2. **TeaVM spike** on the narrowest target: one model, one query, a
   SQL string out. No executor, no server, no resource I/O. If it
   compiles and runs, the rest is engineering.
3. **Measure the artifact.** Size decides.
4. Static-register the section grammars (kills `ServiceLoader`).

**Do not port the executor.** The browser already has DuckDB-WASM.
Only the planner crosses.

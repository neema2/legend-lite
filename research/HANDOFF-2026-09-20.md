## 6. Known defects

### In legend-lite (tracked, not fixed)

Seven, one root cause, listed in `demo/torture.mjs` as
`KNOWN_ENGINE_BUGS` — the suite reports them and **fails if one starts
passing**, so a note cannot outlive the bug. A column DECLARED with
quotes in the Database grammar (`"with space"`, `"quo'te"`,
`"Ünïcødé"`, `"select"`) resolves through `select`, `filter` and
`extend`, and fails through `groupBy`, `sort` and `pivot` — the three
paths that ISOLATE the table scan before resolving. The first two raise
`IllegalStateException`; pivot dereferences null.

Reproduce:
`#>{torture::DB.WEIRD}#->groupBy(~['with space'], ~[m:x|$x.n_float:y|$y->sum()])`

### BIT type disagreement (recorded, deliberately not fixed)

`StoreCompiler` says BOOLEAN, `PreciseTypes` says TinyInt. **Upstream
says BOOLEAN**, in four places (`pureToRelational.pure:56`,
`relationalExtension.pure:146`, `databaseHelperFunctions.pure:202`,
`relationalToPure.pure:214`); the only `Bit → TINYINT` upstream is
COMMENTED OUT in the H2 extension as a workaround. So `PreciseTypes` is
wrong. Not fixed because `pureType` feeds the PLAN PROTOCOL and the
corpus gates could not be run. Needs a `Boolean → "BIT"` arm in
`defaultSpelling`, which currently throws.

### Type-mapping duplication

**Eight sites in core** know the SQL↔Pure correspondence, in different
directions and granularities — which is why they drift instead of being
deduplicated:

```
DatabaseProtocolParser:396   grammar token -> protocol name
RelationalDataType:140       string        -> typed Varchar(n)
StoreCompiler.columnType:246 RelationalDataType -> Pure primitive
PreciseTypes.pureType        RelationalDataType -> precise Pure FQN
PreciseTypes.defaultSpelling Pure          -> SQL DDL spelling
SqlTypeCensus:592            string        -> SqlType.Scalar
RelOpTranslator:183          SQL name      -> Pure name
Executor:960                 JDBC name     -> runtime value
```

Plus `duckdb.ts` (`typeName`, `converterFor`) and `remote.ts`
(`inferType`) on the TS side. It has already cost a bug: DECIMAL once
answered Float in one path while the column-kind table said Decimal
(audit 2026-09-15 P3-5). `TypeMappingAgreementTest` now guards this.

## 7. legend-engine findings (verified, not inferred)

Recorded because they took real digging and I got them wrong three
times before grepping for construction sites.

**`TabularFunction` can only be called with ZERO arguments.** Grammar
(`RelationalParserGrammar.g4:154`) accepts `columnDefinition` only;
the protocol class carries a literal `//TODO params ?` and has no
field; introspection sets columns only. The metamodel DOES declare
`parameters : FunctionParameter[*]` and four dialect processors take
it — but **nothing anywhere constructs one**. The single construction
in the repo is `^TabularFunction(schema=…, name='ID')`.

**UDTF generation is unrelated.** SnowflakeApp / MemSqlFunction
activation emits `CREATE OR REPLACE SECURE FUNCTION …(params) RETURNS
TABLE (…)` as **templated DDL text**; it never builds a
`TabularFunction`. So Legend can CREATE a parameterised UDTF and
cannot CALL one.

**Consequence:** `read_parquet('s3://…')` from a model is a NEW
capability, not a gap to fill. The upstream-compatible pattern is a
zero-arg function whose body lives in the warehouse
(`CREATE MACRO T() AS TABLE SELECT * FROM read_parquet(...)`), which is
the same logical/physical split as a view.

**Schema introspection IS a first-class upstream feature**, and
deliberately NOT part of plan: `SchemaExportation` lives in the
*execution* module, `SchemaExplorationApi` is its own HTTP endpoint.
The REPL composes `load <path> <conn> <table>` (file → table) with
`db` (introspect → `Database`). Note it does **not** infer a Store from
a file — it materialises the file into a table first, so there is ONE
inference path.

**lite already has the raw material**: `fetchDbSchemasMetaData`,
`fetchDbTablesMetaData`, `fetchDbColumnsMetaData`,
`fetchDbPrimaryKeysMetaData` natives, composed by `CatalogGrids` as SQL
over `information_schema` with JDBC `DatabaseMetaData` column names. So
introspection would be: run the existing grids through `QueryService`,
convert rows → `Database` **via `RelationalDataType`** (so no ninth type
mapping), expose as `/engine/introspect` beside `/engine/execute`.

**Why `plan` needs no Connection but still picks a dialect:** two
meanings of "Connection". `dialectOf(ctx, runtimeFqn)` reads the
Runtime ELEMENT → Connection ELEMENT → `type: DuckDB` from the model
text. No socket. A second overload takes a `java.sql.Connection` and
probes the live product, used at execution to reconcile H2 versions.

## 8. Architecture notes a newcomer will need

- **One planner, no fallback.** legend-lite compiles snapshot → Pure →
  SQL. A guardrail test asserts `Planner` is implemented in exactly one
  shipped file. Injecting a stub in a test is fine; runtime selection
  is banned.
- **Reachability guardrail.** `src/app.ts` must import and CALL each
  module. Phase 6 shipped features no user could reach; this exists so
  it cannot recur.
- **`CubeRefusal`** distinguishes "your cube is not a question" from
  "we have a bug".
- **Epoch discipline** keeps answers correct; **cancellation** keeps it
  fast. Both are needed — an HTTP response already on the wire cannot
  be stopped.
- **Pivot separator `__|__`** is OUR delimiter appearing in THEIR data.
  Never infer arity by counting it.
- **A convenience constructor that defaults a new record field silently
  drops it at every rebuild site.** This bit twice in one change
  (`NameResolver.resolveDatabase`, `TypedTableReference.withInfo`).
  When adding a field, grep every construction AND every `with*`.

## 9. The new question: legend-lite in WASM

Not investigated. Starting framing only:

legend-lite is **Java 21**, using records, sealed interfaces, pattern
matching, and JDBC (DuckDB/H2 drivers). Routes worth costing:

- **TeaVM** — Java→WASM/JS AOT. Mature-ish, but Java 21 language level
  and reflection/JDBC are the risk.
- **GraalVM native-image → WASM** — native-image is proven for this
  kind of compiler workload; the WASM backend is the newer, riskier
  part.
- **CheerpJ** — runs a JVM in WASM. Highest compatibility, heaviest
  payload.
- **Do not port the executor.** The browser already has DuckDB-WASM;
  only the PLANNER needs to run client-side. That is the narrow, and
  much more tractable, target: parse + compile + lower + render, with
  no JDBC and no execution.

The honest feasibility question is whether the planner alone can be
carved out with no JDBC dependency — `Compiler.plan` already needs no
`java.sql.Connection`, which is the strongest signal that it can.
Start by measuring the dependency closure of `Compiler.plan`.
